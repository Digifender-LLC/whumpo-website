## The registry

Each entry is keyed by the **current** column (`table.column`) so a mixed table is counted once and never double counted. Fields: `sourceFile` (the schema file that defines the table, verified against the composed inputs), `onDelete`, `class`, `subject` (`account`, `workspace` or `mixed`), `retarget`, `roles`, `status`, `evidenceLevel`, `key` (intended key/disposition), `basis`, `evidence` (repository files and contract anchors, resolved by the gate) and, where an owner answer matters, `questions`.

- **Classes**: `account`, `workspace`, `workspace+actor`, `workspace+custody`, `workspace+payer`, plus `typed-subject` (`content_risk_evidence`, `content_risk_reversals`: one current column, two intended typed columns `account_id`/`workspace_id`) and `split` (`photo_scan_tickets`: one current column, two intended tables). The two mixed shapes list their intended outputs beside the current column; the gate refuses an intended column or table that already exists. `retarget` is `keep`, `hand-written`, `typed-subject` or `split`; **no entry claims a mechanical `RENAME COLUMN`**, which is invalid (three renames failed and at least 22 bodies stayed silently wrong in the feasibility spike).
- **Roles stay separate.** `account` keeps `REFERENCES users`; `tenant`, `actor`, `custody` and `payer` are distinct intended columns (`workspace_id`, `actor_ref`, `authorizing_actor_ref`, `payer_actor_ref`); none stands in for another, and the gate rejects entries that share a column or give a tenant class an account role.
- **Statuses**: `proposed` (engineering classification awaiting the child-1 schema review), `undecided` (the class or key cannot be accepted until a named owner question is answered; the class shown is the working proposal) and `accepted` (reserved for the schema review; no entry is accepted). Six entries are `undecided`: the four Stripe tables (payer on transfer; the invoice table also late-payment continuity) and `inference_budgets`/`inference_calls` (the funded-workspace bound). `evidenceLevel` is `review-spike` for the 102 entries classified by the October 8 feasibility review (classified by review reasoning; the spike was one mechanical in-memory rename of 97 tenant keys with 22 schema-wide assertions, 19 passing, and did not exercise each entry's disposition, so a `review-spike` entry is not fixture-proven either) and `source-reading` for the nine from the source-only follow-up (seven formerly undecided entries plus the two refinements), **not fixture-proven**.
- **Questions**: the six product questions the contract has asked, keyed by stable semantic IDs (`payer-on-transfer`, `member-only-accounts`, `retention-and-closure-window`, `member-limit`, `late-payment-continuity`, `funded-workspace-bound`) so renumbering the contract never re-points an entry. `member-only-accounts` and `member-limit` carry `ownerAnswerRecorded: true` with the dated answer and the contract section that records it ([owner decisions](workspace-collaboration.md#owner-decisions-recorded)); they only had one dependent entry (`welcome_onboarding.user_id`, still `proposed`, whose representation is a schema-child detail) and no undecided entry. The other four are open, numbered 1 to 4 as in [remaining product questions](workspace-collaboration.md#remaining-product-questions), and hold all six `undecided` entries. The gate rejects an answer flag without a dated answer and resolvable anchor, an answer on an open question, a number on an answered one, and numbering that does not run 1 to N; the registry never infers an answer.
- **Indirect tenants and exclusions**: `derived` lists the 109 tables without a `users` key by the method recorded in the file (78 reach `projects` or a `users`-keyed table: 38 through a `project_id` foreign key and 40 through a longer chain; 31 have no tenant path, 29 at `ca17c6a` plus the two WH-050 operator receipt tables; 6 carry a textual `project_id`). `textualIdentity` lists the non-foreign-key identity columns and the four custody-context files that a mechanical rename must not touch. The gate fails when the schema derives a different list.

## Gates and what makes them fail

`check` fails (exit 1) on: an unclassified or stale `users` foreign key; a changed defining schema file or delete action; a class/role/subject mismatch; an intended column or table that collides with an existing one; an undecided entry without a named question; an unknown question; an unresolved evidence file or contract anchor; drift in the derived or textual inventories; a changed schema fingerprint (`baseline.reviewedSchemaSha256`, from the same inventory SQL `tools/current-schema.mjs` uses) until the change is reviewed against the registry; and any body-validator problem below. A change to the composed schema therefore requires touching the registry in the same change whenever the gate is run; the deploy build does not run it (see [Commands](#commands)).

### Schema freeze preflight

`freeze` is plain arithmetic over the registry: it passes only when every entry is `accepted`, every question has a recorded owner answer and the registry status is `frozen`. It currently refuses (111 entries not accepted, four open questions, status `proposed-not-frozen`), and the refusal is itself tested. `check` enforces the same progression, so the steps are reachable and cannot be skipped: an entry may leave `undecided` only once every question it names is answered (and must then be reviewed to `proposed`), may be `accepted` only with no open question, and the registry may be `frozen` only when every entry is accepted and every question answered. A synthetic clone walks that path in the test and passes both `check` and `freeze` at the end; the committed registry is never accepted by a test. (The first 1a revision required `proposed-not-frozen` and `ownerAnswerRecorded: false` in `check`, so a reviewed, fully answered registry could pass `freeze` only by failing `check`.) Passing it would not authorize a cutover; that needs the owner ([releases](releases.md)).

## Trigger and view validator

SQLite accepts `CREATE TRIGGER`/`CREATE VIEW` bodies naming unknown columns and fails only when a statement that fires or reads them is prepared, so the artifact check (execute plus `foreign_key_check`) is blind to stale bodies. `tools/schema-body-validator.mjs`:

1. **Reparse.** Rebuilds the tables, indexes and views in a disposable in-memory database, installs each trigger **alone**, **prepares** the INSERT/UPDATE/DELETE that fires it (never steps it), and drops it; prepares `SELECT *` for each view in dependency order so a view broken only through another is attributed to the right one. No row is written and no trigger body runs; the validated database is not modified. `UPDATE OF <missing column>` is silently inert in SQLite, so the OF list is checked against the table and the body is still compiled through a variant without the missing names.
2. **Cross-type lint.** `tools/sql-structure.mjs` tokenizes and parses each body, resolves every column reference (aliases, `OLD`/`NEW`, correlated and nested subqueries, derived tables, views, `excluded`) to its base column and reports comparisons (`=`, `IS`, `IN`, `BETWEEN`, `NULLIF`, `CASE` operands, row values element by element) where one side can carry an `account` type and the other a `workspace` type (a `COALESCE` or a `UNION` view column that can be either counts as both). A view's own comparisons are recorded once, for the view; an object that only reads the view is not charged with them. Types come from the foreign-key graph (`users` → account, `workspaces` → workspace), plus on the **current** schema an overlay from the registry saying which `users` references are really tenants. This is a resolver over a parsed tree, not a text match, but it is not a proof: see limits.

### Baseline on the current schema

Reparse: all 648 triggers and 28 views compile; no `UPDATE OF` names a missing column; no body is unsupported. Lint: 5,284 comparisons, **49 cross-type findings in 45 objects**, recorded by stable fingerprint in [`docs/tenant-checks-baseline.json`](tenant-checks-baseline.json). They are **not defects today** (every tenant is also an account, so they behave correctly) and are **not fixed here**: they are the exact worklist packet 1b must rewrite by hand, and 1b's exit requires the baseline to be empty. Twenty-two of the 45 objects are the 19 retention guards (`EXISTS (SELECT 1 FROM users WHERE id = OLD.…)`) and the three hold triggers the feasibility spike found by renaming (the test asserts all 22 by name); the other 23 are objects the spike called uncounted, for example the `safety_held_projects` and `operator_contained_projects` views, plus `operator_containment_retained`, the WH-050 retention guard added on main after `ca17c6a`, which compares a hold's `subject_user_id` with the contained project's `owner_user_id` exactly as the `safety_hold_*` triggers do. A fingerprint is `sha256(object | sorted resolved sides | operator | occurrence)`; line moves, aliases, formatting and message text do not change it, a changed comparison does. A new finding fails; a baseline exception that no longer matches fails. The first 1a revision reported 5,512 comparisons and 50 findings in 46 objects: it also recorded each view's comparisons in the first trigger that read the view, so two view findings were charged to `contact_submission_guard` and `safety_hold_contact_retained` (which only read `operator_contained_projects` and `safety_held_projects`) and depended on object order. Columns the registry classifies `typed-subject` or `split` are typed `mixed` (neither side), so their comparisons are counted, not reported; their hand rewrite is owned by those entries.

## SQLite authorizer probe (report only)

`sqliteD1({probe:true})` (or `databaseFixture({probe:true})`) installs Node 24's `DatabaseSync.setAuthorizer` on the in-memory fixture. Inside `fixture.authorizer.scope(name, body)` it records the tables and columns each prepared statement reads, inserts, updates or deletes, tagged **direct**, **trigger** (trigger name) or **view** (view name). It always allows the action and never changes a result; unused, the fixture is unchanged (same shape, same code path). `close()` removes the hook. Node cannot read an existing authorizer, so removing means clearing: a second probe on the same database is refused, but an authorizer set by other code cannot be detected and would be replaced and then cleared, so the probe is only for databases nothing else hooks (the fixtures create their own). Scopes are one shared label, so concurrent async work prepared while a scope is open is attributed to it. In `--d1` (miniflare) fixtures it reports **unavailable** (`authorizer.available === false` with the reason), because D1 prepared statements are opaque; reading its actions or calling `references()` there throws, so an assertion that a statement does *not* reference a column cannot pass vacuously.

It **reports references; it does not prove isolation.** It cannot see predicates or bound values, covers only paths a test executes, and statement labels have string literals masked. `tests/sqlite-authorizer.mjs` demonstrates the gap with two workspaces and unique markers: a correctly scoped query, a tautology (`owner_user_id = owner_user_id`) and a correct query with the wrong bound value produce **identical** authorizer reports, but only the scoped one keeps workspace B's marker out of workspace A's result. The probe does catch a statement that never references the tenant column, which is its useful signal.

## SQL surface report (AST)

`tools/tenant-sql-surface.mjs` parses `src/**/*.ts` with the TypeScript 7 syntax tree (`typescript/unstable/sync`, the method the WH-004 [boundary audit](boundary-audit.md) uses; it parses and never runs the source). It classifies every `.prepare(...)` (and `['prepare'](...)`) argument as literal, static template, interpolated template (flagging table-name interpolation, including a template nested inside an interpolation), concatenation or non-literal; counts the tenant-taking helper calls by name; names the tables in literal SQL; and shows per-worker reachability by import.

At this baseline: 1,311 `.prepare` calls (985 literal, 65 static templates, 237 interpolated; 1,307/983/65/235 at `ca17c6a`), of which **17 interpolate a table name and 24 pass a non-literal** (41 dynamic sites, unchanged by the later main commits). The contract's earlier text inventory said 984 literal and 23 non-literal: one `'SELECT '+fields+' FROM …'` concatenation starts with a quote and was counted as a literal by that text method; the syntax tree is authoritative. Helper counts match the contract (`assertWorkspace` 81 calls in 32 files, 77 in 31 outside `admission.ts`; `assertFeature` 50/21; `featurePredicate` 33/20; `requireFeature` 9/4; `connectionInclusion` 2).

**Allowlist.** Each of the 41 dynamic sites is an entry in the baseline file with a stable fingerprint (file, enclosing symbol, kind, argument text; not line numbers) and a reviewed reason that records what the source shows. A new dynamic site fails the gate, a reviewed statement edited in place fails (new site plus stale entry), and an entry that no longer matches fails. Counts of ordinary literal sites are reported, not gated, so adding a normal statement does not fail the gate. **The other 220 interpolated templates are not gated either**: a placeholder list, column or predicate fragment interpolated into a new statement is counted but passes. A table interpolation is recognised at a table position, read from the SQL token stream: directly after `FROM`, `JOIN`, `INTO`, `UPDATE` (past `OR <conflict action>`) or `TABLE`, and after each comma of a `FROM` list at that `FROM`'s own parenthesis depth (`FROM a x, ${t} y`, after a join condition, after a subquery table, inside nested subqueries, CTEs and `UPDATE … FROM`). Commas in function arguments, `IN` lists, the `SELECT` list, `ORDER BY`/`GROUP BY`/`LIMIT`, strings and comments are not table positions, and `a IS DISTINCT FROM b` is not a table list. The check is by position, not a ban on interpolation: a placeholder list or a column or predicate fragment is still counted, not gated. A name built another way (`PRAGMA table_info(${t})`, `CREATE INDEX … ON ${t}`, `ALTER TABLE … RENAME TO ${t}`, a table assembled outside the template) is not recognised. A template the SQL tokenizer cannot read is gated as a table interpolation rather than assumed clean. The comma-list fix found no new site: the counts and the allowlist are unchanged.

**Cannot prove all tenant access.** SQL passed to anything but `.prepare`, composed in another function, written by triggers (four tenant-bearing tables are never named in static SQL, for example `gateway_spend_buckets`) or run from `tools/` is invisible or only listed; helpers are matched by name without type resolution; bound parameters are not followed. Treat the report as a map, never as evidence that every tenant access is scoped.

## Limits (all of the above)

- Evidence is local: source, in-memory SQLite and the syntax tree. No D1 `--d1` probing, no deployment, no Stripe, GitHub or Cloudflare observation.
- The validator proves bodies resolve against the schema, not that they are correct; each trigger is compiled in isolation, so nested chains are checked per trigger.
- The lint compares column operands it can resolve; function results, `CASE` branches, `CAST` results, literals and parameters are untyped and never reported; assignments (`SET`, `INSERT … SELECT`) are not compared; same-type columns can still join the wrong rows.
- Unsupported SQL (`WITH`, window functions, `RETURNING`, `NATURAL`/`USING` joins, `IN <table>`, row values or `IN (SELECT …)` whose widths the resolver cannot pair) is reported and fails the gate; it is never skipped. None occurs in the current schema. The parser is a hand-written reader for the subset these bodies use, checked by the tests' canaries and by parsing all 676 current bodies with no unsupported result; it is not a complete SQLite grammar, and the reparse check (SQLite itself) remains the authority on whether a body is valid.
