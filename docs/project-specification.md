# ADR: versioned project specifications and supported changes

**WH-064 — September 30, 2026. Decision contract and offline prototype, based on `b19d149`.** Configure maintained capabilities first; custom source and infrastructure proposals require a demonstrated missing capability. The scope is the specification/operation contract, not a production compiler, new module API, migration or provider activation. WH-065–068 deliver those separately. [Task specification](https://github.com/zemdregon/whumpo/issues/12); the owner-requested architecture extension is recorded in [roadmap PR #1](https://github.com/zemdregon/whumpo/pull/1).

Whumpo's maintainer serves authenticated owners. Visitors, form submissions, scheduled customer rules and webhooks cannot start maintainer inference, borrow its context/tools/credentials or draw on its funding. Standard runtime actions must function when maintenance inference is unavailable. Optional customer runtime AI is the separate WH-079 contract; there is no AI operation in this initial specification.

**Implementation follow-up:** WH-065's [capability planner](capability-planner.md) is deployed in test. WH-066A adds the [typed schema and deterministic content compiler](project-specification-compiler.md), with exact artifact locks, pure edits and legacy site import. That library is locally verified but not mounted as an API; durable proposals, apply/restore and forms/API delivery remain open. The decision and prototype descriptions below retain their original scope.

## Specification v1

The [complete synthetic detailing fixture](../tests/fixtures/project-specification/detailing.json) is a valid example. JSON contains only the fields below; every object is closed. Unknown keys fail rather than being discarded. Canonical serialization sorts object keys, preserves array order and hashes UTF-8 bytes with SHA-256. The whole specification is at most **32 KiB**, with at most **32 levels** of JSON nesting. Bounds below are contract ceilings, not customer allowances or proof of current resource provisioning.

| Field | Exact contract |
| --- | --- |
| `schemaVersion`, `name`, `design` | Version `1`; name 1–100 characters; design contains only `theme: ocean | clay | forest`. Text is data, never markup or executable styling. |
| `modules` | At most six unique `{id, version}` pairs. Known initial IDs: `content`, `records`, `files`, `access`, `notifications`, `automation`; only version `1`. These are proposed capability contracts. No remote module URL or version range. `content` is required. |
| `content` | At most 40 unique `{id, text}` records, text at most 1,000 characters. Contains owner-authored site copy, not visitor submissions, credentials or identity records. Referenced component fields retain their stricter limits/nonempty requirements. |
| `pages` | One to four unique IDs and paths. Each page has `id`, `path`, `component: site-page@1`, `audience: public | staff`, four content references (`headline`, `description`, `aboutTitle`, `aboutText`) and at most six `{heading, text}` reference sections. Paths are `/` or a single lowercase slug; platform/service routes are reserved. A private page cannot be emitted to the public static host. |
| `records` | At most four `{id, schemaVersion: 1, fields, read, write}` definitions. One to eight fields use the existing bounded form field contract, including unique safe keys, fixed choice options and optional text. Read/write are `owner | staff`; staff write requires staff read. This defines schemas, not record values. |
| `forms` | At most four `{id, recordId, title, description, buttonLabel, submit, uploadCollectionId}` definitions. Title/description/button bounds match the existing form validator. Fields resolve from the record definition. Submit is `public | visitor`. An attachment collection requires `visitor` submission and a known collection. Public submission does not grant read access. |
| `files` | At most four `{id, read, upload, maxBytes, mimeTypes}` collections. Read is `owner | staff`; upload is `visitor`. At most 5 MiB and a unique nonempty subset of `image/jpeg`, `image/png`. Private bytes still require actual format validation, scanning and current object-level permission. Public delivery is deliberately absent from this first collection policy. |
| `access` | Only `roles: [] | ["staff"]`. Owner authority is implicit and cannot be removed or replaced in config. Role membership is separately authorized server state and is never supplied by the model. |
| `integrations` | At most two logical `{id, capability: email.staff}` slots. No provider/account/resource ID, recipient address, token, sender domain or credential. A private server registry later resolves an authorized project connection; a slot is not a connection or spending grant. |
| `rules` | At most eight deterministic rules: `{id, trigger: {type: form.accepted, formId}, effect: {type: notification.send, integrationId, recipient: staff, template: submission-link@1}}`. The referenced form/record must be staff-readable. The template sends a bounded link notice, not uploaded bytes or visitor field interpolation. No AI, arbitrary URL, free-form expression, sender/recipient override or executable step. |

Local IDs are 1–40 lowercase letters/digits/hyphens, start with a letter, and exclude reserved prototype keys. Provider identities and tenant ownership do not belong in this document. A target project ID is a separate route/tool argument; the server verifies it against the authenticated owner before reading the specification or resolving any reference.

### Compatibility rules

- `records` depends on `content`; `files` and `notifications` depend on `access`; `automation` depends on `records`, `notifications`, and `access`. A used capability must be declared. Unknown versions and missing dependencies fail closed.
- Staff audiences/policies and authenticated visitor forms require the access contract. Staff write cannot coexist with owner-only read. Public submission plus private upload is rejected; a separately reviewed public-upload contract would be required.
- Every page content, form record, upload collection, rule form and integration reference must resolve inside the same validated specification. Runtime record/file IDs must also pass current project and actor authorization; config references do not replace that check.
- Initial changes can **add optional text fields only**. Required additions, removal, renaming, type changes and defaults need a separately reviewed data compatibility/migration contract. Existing records are not rewritten by a schema change. Future validators must distinguish absent optional data from a value rather than inventing backfills.
- Module/compiler versions are immutable. Production proposals must resolve an exact catalog lock containing artifact digests, dependency versions, schema compatibility and withdrawal state. Unknown or withdrawn entries cannot become an invented module. Current installed instances need an explicit upgrade/recovery policy under WH-076; immutable old artifacts are never rewritten.

## Operation protocol

### Authority and inputs

Resolve session/job authority before parsing a proposal: verified actor kind, user, owned project, current authorization revision and capability grants. A maintainer job can propose for its authenticated owner; it cannot impersonate that owner at a confirmation endpoint. Visitors, deterministic jobs and webhooks have no specification-maintainer entry point. Actor/owner IDs, permission flags and integration credentials in a model payload are unknown fields and are rejected. Schema validation is not a content/secret detector; owner-authored text and uploaded artifacts still require the applicable safety/privacy gates.

`propose(projectId, {id, expectedRevision, operations})` accepts a UUID request ID, exact nonnegative project revision and one to eight operations. No generic JSON Patch endpoint is provided:

| Operation | Fields after `type` | Additional required review |
| --- | --- | --- |
| `content.replace` | `contentId`, `text` | None for private draft; publication remains a separate exact review. |
| `design.setTheme` | `theme` | None for private draft; publication remains separate. |
| `records.addField` | `recordId`, `field` | Schema compatibility review; only optional text additions in this version. |
| `files.setPolicy` | `collectionId`, `read`, `upload` | Permissions review even when narrowing access. This does not edit role membership. |
| `pages.setAudience` | `pageId`, `audience` | Permissions review; compilation/publication must also select the correct authenticated/public delivery path. |
| `rules.put` | complete `rule` | Integration and spending review. Private approval records configuration intent only; it does not authorize sending, credit spending or account upgrades. |

Create/bootstrap requires its own server-validated initial specification under the existing new-project/onboarding contract; arbitrary replacement is not an editing escape hatch. Operations are applied to a detached candidate and validated as a whole. An invalid later operation leaves the current version and earlier candidate changes unapplied. Generated source, SQL, publication, provisioning, purchases and module installation are unsupported operation types.

### Results and invariants

1. **Propose/validate:** check owner/project, request replay identity, current revision and all shape/reference/compatibility rules. Return or persist a proposal with `id`, `projectId`, `expectedRevision`, `baseDigest`, `nextDigest`, immutable semantic `diff`, a `preview`/`previewDigest`, required review classes, acceptance evidence, expiry and a digest over the complete proposal. Input changes cannot reuse a committed request ID. Diff arrays show whole ordered old/new values; this is a review artifact, not an executable patch language.
2. **Preview:** WH-064 supplies a deterministic **configuration summary**, including route/audience and module references. It is explicitly `activation: not-configured`. The validator artifact digest pins the prototype plus the existing bundled component/form contracts. It is not a runtime module lock, rendered multi-page release or successful permission/notification acceptance. WH-066 must produce isolated rendered artifacts, exact byte digests, catalog/compiler locks, relevant tests and visible effects before its production apply route is enabled.
3. **Approve:** an authenticated owner with a recent session reviews the stored proposal and required classes. Approval names the exact proposal digest and complete required class set. A model cannot approve, remove a class or substitute a digest. This private configuration approval does not supersede publication, application activation, data migration, provider destination/permission or funded spending reviews. Those reviews bind their own exact current resource snapshots.
4. **Apply/version:** `{id, proposalId, proposalDigest, expectedRevision}` reads the saved candidate, never client-supplied replacement JSON. Recheck current session/project authority, base revision/digest, proposal expiry, artifact/catalog compatibility and required approval receipts. Atomically store the next specification/version, increment the revision, and save the idempotent apply receipt. Two proposals for one base cannot both apply. A saved apply ID replays the same outcome after a lost response; a different payload conflicts. The prototype models this transition in memory; production D1 concurrency/late-result tests are still required.
5. **Activation/publication:** compiled content and capabilities remain private/inactive until their separate current reviews and all safety, provider, budget and lifecycle prerequisites pass. No side effect is dispatched merely because a spec version exists. Real integration/permission/funding approvals must pin destination, limits, expiry and current authorization again at dispatch. Unknown provider outcomes retain their receipt/hold rather than triggering a new write.
6. **Recover:** a timeout reads the existing request/proposal/version. A stale base requires new owner-aligned review; never rebase a permission/data change automatically. Restore is a new reviewed forward revision, with current compatibility, deletion/revocation and safety checks. Historical role grants, secrets or removed data do not come back with an old specification.

Return fixed error codes with a safe schema path and correlation ID, not input values, credentials, visitor data or raw provider errors. `INVALID_SHAPE`, `UNKNOWN_FIELD`, `MISSING_FIELD`, `INVALID_TEXT/ID/NUMBER/LIST/DIGEST`, `INPUT_TOO_LARGE/DEEP`, `DUPLICATE_ID`, `UNKNOWN_MODULE`, `UNSUPPORTED_VERSION/OPERATION`, `MISSING_REFERENCE`, `INCOMPATIBLE`, `MIGRATION_REQUIRED`, `NO_CHANGE` are 400/422 contract errors. `FORBIDDEN` is 403; foreign/missing projects/reviews both return `NOT_FOUND`/404. `STALE_REVISION`, `ID_CONFLICT`, `REVIEW_CHANGED`, `REVIEW_REQUIRED` and `EXPIRED` are 409; `QUOTA` is 429. A future adapter's unknown external result is a recoverable unresolved state, never one of these validation failures.

## Detailing-site review examples

The fixture is synthetic and describes **appointment requests**, not availability/reservations/payments. No booking engine or email provider is claimed.

| Owner request | Validated change | Negative case and activation boundary |
| --- | --- | --- |
| “Open Saturdays, 8 to 6.” | Replace the `hours` content record; current static renderer produces escaped updated copy. | Missing reference, wrong base revision and forged owner fail. Live hours change only after the exact publication review. |
| “Ask which vehicle they drive.” | Add optional text `vehicle` to the appointment schema; the current form validator accepts the resulting bounded shape. | Duplicate/reserved field keys, required addition and incompatible types fail. Real record/form API work remains WH-067; no existing visitor documents are changed. |
| “Only staff should see uploads.” | Set the private collection read policy to `staff`. Owner access remains inherent; role membership stays separate. | Public reads, anonymous attachment intake and missing access module fail. Actual staff file serving must enforce project/role, quarantine and revocation on every request. |
| “Email staff about new appointment requests.” | Add `form.accepted → notification.send`, using `team-email` and the fixed staff link template. | Unknown integration, staff-inaccessible records, AI/shell/webhook effects and inline credentials fail. Setup, approved recipients/sender, consent, cost limits and deterministic job receipts are WH-068/069; private spec approval sends nothing. |

All four are expressible without generating a new authentication/storage/application stack. This demonstrates contract expressiveness and compatibility with selected existing validators, not that the detailing portal is implemented. WH-080 remains the connected proof with real shared modules and separately admitted provider/media/device paths.

## Persistence, lifecycle and delivery handoff

WH-066 should implement a project head, immutable specification versions, bounded proposal/preview evidence, exact approval links and apply receipts. Reuse the current immutable version/review patterns rather than appending metadata to historical site rows. Keep site artifact IDs, application revisions, role/permission revisions, integration grants and spec revisions distinct; a spec revision is not a database migration or publication revision. The initial prototype keeps at most 32 proposals and 25 versions per project solely to bound fixture state. Customer entitlements, expiry cleanup and retention remain separate decisions under WH-009/023/076; do not delete pending/unknown receipts to recycle capacity.

An adapter can import an owned existing `site-page@1` configuration into content references with an origin version/digest. It must preserve every rendered string/theme, leave original immutable bytes alone and make no live change. Photo, CMS, custom backend and visitor state need their own explicit adapters; do not flatten them into text or silently migrate data. CMS testing remains owner-deferred. Do not deploy this prototype as an API or treat its trusted fixture actor objects as authentication.

WH-065 has published the maintained capability/version/compatibility/readiness catalog and bounded planner. WH-066's schema/content compiler is implemented; next it connects durable proposals, real preview delivery, version transactions and existing approvals. WH-067 adds narrow shared records/access/files APIs; WH-068/069 implements configured notifications and deterministic rules. Dedicated project storage, broader execution and optional runtime AI retain their separate roadmap gates.
