# Customer-configured runtime AI: boundary decision (WH-079)

**Decision record, October 31, 2026 UTC (D62, orchestrator plan batch 5.4).** This document states the rules a customer-configured runtime AI capability must meet before anyone builds it. It selects no implementation, adds no route, adds no table, and activates nothing. The capability stays **deferred until customer demand** exists and until WH-075 is reconciled (see rule 9). It extends [project specification](project-specification.md), [workload placement](workload-placement.md), the caller classes in [connectors](connectors.md) and the processing rules in [inference privacy](inference-privacy.md).

## What it is

A customer may later let their own published site or app call **an AI provider the customer chose and pays for**: either a provider account with the customer's own key, or an AI route the customer exposes from their own Cloudflare account (an AI Gateway or Workers AI route). It is separate from the owner maintainer (the Chat assistant that builds and edits the project). It is not part of default deterministic capability delivery, and no plan includes it.

## Rules

Each rule names the boundary that enforces it. "Future test" means the check does not exist yet because no route exists; it must be written with the adapter and is part of that task's acceptance, not this one's.

1. **Opt-in, per project, default off.** A project has runtime AI only after its owner confirms an exact review (see rule 5). The setting belongs to the project, is off for every project that has never confirmed, and is off again after a restore, a copy or an import until reviewed. Boundary: an owner-only review in the existing review-and-confirm pattern. Future test: a restored or copied project reports runtime AI disabled.
2. **Its own adapter, credentials and identity.** Runtime AI calls go through a dedicated, project-scoped adapter with its own configuration type. That adapter **never imports or invokes** the maintainer path (`src/ai.ts` configuration, the owner Chat dispatch, the gateway spend path, the premium wallet or the OpenCode Go key). Visitor and service requests carry no owner identity, so no owner context, tools, memory or prompts are reachable from them. Boundary: module import graph (checked the way the email-change module is checked, with an esbuild import-graph test) and the caller classes in [connectors](connectors.md#authority-classes). Future test: the adapter's bundle does not reach the maintainer modules.
3. **Customer credentials stay server-side.** A customer key is sealed per project in the connection vault class, never sent to a browser, never placed in a log, a model context, an export or a receipt, and revoked when the project is closed or the connection is removed. An exposed Gateway or Workers AI route is the customer's own and is billed to the customer's own account; it is **not** a free model and **not** funded inference. Whumpo's own Workers AI binding and Gateway are never exposed to visitors. Boundary: the existing sealed-vault pattern and the secret-custody registry.
4. **Explicit failure, never a fallback.** When runtime AI is disabled, not configured, over budget, or its provider fails, the request fails with a stable code (`runtime_ai_disabled`, `runtime_ai_not_configured`, `runtime_ai_budget_exhausted`, `runtime_ai_provider_unavailable`) and a plain message. It does not fall back to a Whumpo provider, another model, another project's credential or a cached answer, and it **never wakes the owner maintainer** or spends the owner's funding. Boundary: the adapter has no second route to choose. Future test: with the adapter unconfigured, disabled and exhausted, a spy transport for every Whumpo provider records zero calls (the same shape as [tests/standard-service-no-maintainer.mjs](../tests/standard-service-no-maintainer.mjs)).
5. **Bounded exposure, and the owner sees it before enabling.** Every enabled project has a per-source rate limit on the D1 public-admission counters (not on `SITE_LIMITER`, which has not been seen to enforce live, D51), a concurrency cap, a per-request input and output size cap, and a per-project daily and monthly budget in whole cents that stops the capability when reached. The enabling review shows the provider and endpoint, exactly which data categories are sent (visitor-submitted text only), who can see the responses, the provider's retention and training terms as the provider states them (unknown stays unknown), the caps, and who pays. Boundary: public admission counters, the review pattern, and cost events with a `runtime-ai` workload registered when the adapter is built (event envelope, [cost events](cost-events.md)). Future tests: every cap refuses at its limit; the review lists every field above.
6. **No authority through output.** A model response is untrusted text. It is rendered as plain escaped text, carries no tool calls in the first version, and cannot publish, change infrastructure or ownership, confirm a consent or review, grant a role, or reach maintenance. Boundary: the same untrusted-result rule as provider results in [connectors](connectors.md). Future test: a response containing review, consent and publish commands changes nothing.
7. **Separate request handling and disclosure.** Visitor input and model output are customer-site data, handled apart from the owner's Chat conversation, prompts, tools and memory. The site tells visitors that their text goes to the customer's chosen provider. Receipts hold counts, outcome and digests, never the content. Connected-provider content from a mailbox, calendar or CRM is not a runtime AI input in this decision. Boundary: [inference privacy](inference-privacy.md) lifecycle classes; a new class is registered with the adapter.
8. **The training-enabled route is never a runtime AI route.** The current Whumpo Contributor route trains on its data and is not eligible. Boundary: the model-route gate (`currentModelRoute`) refuses it for anything other than the owner's own synthetic testing.
9. **Implementation waits.** No adapter is selected, scheduled or estimated here. It starts only after real customer demand, after WH-075 is reconciled (its abuse bounds depend on a limiter that has not been shown to refuse live), and after the owner decides who pays for abuse protection.

## Acceptance lines mapped

| Line | Rule and boundary |
| --- | --- |
| A1 Visitor and service calls cannot use maintainer credentials, context, tools, premium wallet or implicit provider fallback | Rules 2 and 4: separate adapter, no import of the maintainer path, no fallback route. Today this holds because no such call exists; the caller classes in [connectors](connectors.md#authority-classes) already refuse visitors, published-site requests, the QuickJS runtime and webhooks, and `tests/standard-service-no-maintainer.mjs` shows published, visitor, preview, contact and scheduled routes dispatch zero maintainer inference. |
| A2 Customer credentials server-side; an exposed Gateway is not itself a free model or funded entitlement | Rule 3. |
| A3 Disabled, unconfigured or exhausted fails explicitly without waking the owner maintainer | Rule 4, with the stable codes and the zero-dispatch test. |
| A4 Rate, abuse and concurrency controls and cost caps bound visitor exposure; the owner gets a provider, data and cost review | Rule 5. |
| A5 Customer AI requests cannot gain publication, infrastructure, ownership or maintenance authority | Rule 6. |

## Verification state (V1 to V3)

- V1 (architecture, credential and budget separation review): this document is that review's record. Its negative route and configuration cases are the "Future test" lines above.
- V2 (synthetic disabled, exhausted and forged-project tests with zero maintainer dispatch): **no such test exists, because no runtime AI route exists to test.** A test written now would assert the absence of a route and would pass whatever the design. The cases must be written with the adapter. The closest standing evidence is the maintainer-isolation suite named under A1.
- V3 (no live provider activation or visitor AI endpoint in this decision task): none was added. No provider was called, no endpoint exists, and no secret, variable or schema changed.

## Consequence for WH-073

[owner-review.md](owner-review.md) item 11 noted that WH-073 line 5 (no customer extension falls back to Whumpo AI) holds only because no extension exists. That is still true. This document turns the missing test into a named requirement (rule 4, future test): the adapter task cannot be accepted without the zero-call check.
