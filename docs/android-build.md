## Mobile API client (WP4)

`com.whumpo.core.api` in `:shared` is the typed client for the frozen [v1 contract](mobile-api-v1.md): `Models.kt` (kotlinx.serialization wire models), `MobileApiException.kt` (one subtype per contract error code), `MobileApiClient.kt` (one method per operation, 34 in all) and `OkHttpEngine.kt`. It has no UI and no sign-in of its own: WP5 supplies the `SessionProvider` (`SessionManager`, below).

- **HTTP stack (decision, 2026-10-29, WP4): Ktor client 3.6.1 core with the OkHttp engine, plus kotlinx.serialization-json 1.12.0.** The plan (platform ADR, Libraries) already named Ktor and kotlinx.serialization. OkHttp is the lightest single engine that runs on both Android and the JVM desktop target, so there is one engine dependency and no per-platform engine code. `MobileApiClient` takes any `HttpClientEngine`, so tests inject Ktor's `MockEngine`. No ContentNegotiation plugin: bodies are encoded and decoded by one strict `Json` instance in the client.
- **Strict responses.** Unknown or missing keys, a version other than 1, a preview path outside the allowlist, or an approvable review whose control does not match its kind fail as `InvalidResponse`. The unknown review `kind` stays a string so the app can show update-required; `Review.present(client)` enables approval only for a control capability the build declared.
- **Errors.** `proof_required` (`ProofRequired.Proof.SIGN_IN` or `FRESH_PASSKEY`), `client_update_required` (426, with `minimumBuild`), `rate_limited` (`retryAfterSeconds`, falling back to `Retry-After`), `stale_revision` (`currentRevision`) and the rest map to subtypes of `MobileApiException`; a gateway page, redirect or unknown code is `Unrecognized`. On an authenticated route, `proof_required` with `signin` or `identity_changed` calls `SessionProvider.onSessionRejected()` before throwing.
- **Request IDs and replay.** Writes take the caller's request, upload or submission ID (`newRequestId()` makes a lowercase UUID). The client never retries and never regenerates an ID. A lost write reply is `Transport(outcomeUnknown = true)`; resolve it by reading (`resolveSend`/`getChatTurn`, `interactionReceipt`, `getPhotoUpload`), and retry only as an explicit owner action with the same ID and payload. `fresh_passkey` is surfaced for the caller to reauthenticate and retry with the same ID.
- **Reauth race.** A native reauth replaces the session row (same token, new authority id), so a request that resolved its identity just before the commit fails `409 identity_changed`. `MobileApiClient` records when its own `reauthVerify` last succeeded and, if an authenticated request then gets `identity_changed` within 10 seconds, repeats it exactly once with the identical body and request ID. `SessionProvider.onSessionRejected()` is not called for the first failure; a second `identity_changed`, or one without a recent own reauth, is a rejected session as before. `proof_required` and every other code are never retried. Every caller (Chat, Projects, sign-in) gets this through the shared client.
- **Interactions.** `interactions/list`, `read` and `resources` return the WH-105 payload as a `JsonObject` (version checked); the contract freezes only the envelopes. `mutate`, `receipt`, `continue`, `stop` and `reconcile` are typed from the fixtures.
- **Single source of truth.** The tests read `tests/fixtures/mobile-v1/*.json`, the same files `tests/mobile-v1-contract.mjs` reads, found by walking up from the module directory. Nothing was copied or moved. `android.yml` now also runs when those fixtures change.

## Local build

You need JDK 17+ and an Android SDK with `platforms;android-36` and build-tools. Set `ANDROID_HOME` or write `android/local.properties` (`sdk.dir=…`). `local.properties` is gitignored. The SDK is not part of the repository.

```sh
cd android
./gradlew assembleLocalDebug assembleDeployedDebug
./gradlew lintLocalDebug lintDeployedDebug
./gradlew :shared:jvmTest :shared:testAndroidHostTest :shared:compileKotlinJvm
./gradlew testLocalDebugUnitTest testDeployedDebugUnitTest
./gradlew assembleLocalDebugAndroidTest assembleDeployedDebugAndroidTest
# With an emulator or device attached:
./gradlew connectedLocalDebugAndroidTest
```

Debug APKs are written to `android/androidApp/build/outputs/apk/{local,deployed}/debug/`. Build outputs (`.gradle/`, `.kotlin/`, `build/`), `local.properties` and signing files (`*.jks`, `*.keystore`) are gitignored.

**Release build (WH-087 prep).** `release` is minified with R8 and resource shrinking (`androidApp/proguard-rules.pro`: kotlinx.serialization, Ktor and Credential Manager rules). The manual `release_bundle` input of the Android workflow builds `bundleDeployedRelease`, uploads the AAB and R8 mapping, then installs the minified APK on an API 36 emulator and runs `android/scripts/smoke-release.sh` (welcome screen renders, the first API call runs, no crash or stripped class in logcat). The instrumented suite still targets debug builds. Signing reads `WHUMPO_UPLOAD_STORE_FILE`, `WHUMPO_UPLOAD_STORE_PASSWORD`, `WHUMPO_UPLOAD_KEY_ALIAS` and `WHUMPO_UPLOAD_KEY_PASSWORD` from the environment; without all four the build uses the debug key and is labelled `-debugsigned` and not for upload. Version: `android/version.properties` plus the workflow run number. Owner steps: [release-checklist](android/release-checklist.md).

## Protected state and backups

- Drafts, the native session (WP5, `SessionManager`) and pending operations are stored by `AccountStateStore` under `noBackupFilesDir/account-state/`. Each record is sealed with AES-256-GCM using a non-exportable [Android Keystore](https://developer.android.com/privacy-and-security/keystore) key. Records are bound to a hashed account key and slot. Raw account IDs never appear in file names.
- Changing account erases the previous account's state. Signing out erases all state and deletes the key. Unreadable or restored state is erased rather than trusted. Late writes for an account that is no longer active are refused.
- `allowBackup="false"`. `data_extraction_rules.xml` (cloud backup and device transfer) and `full_backup_content.xml` exclude the `root`, `device_root` and `external` domains ([Auto Backup](https://developer.android.com/identity/data/autobackup)).

## Photo and share intake (WH-085, emulator and JVM evidence only)

What exists: the system photo picker (no storage permission) and, new in this change, `ACTION_SEND` for one JPEG, PNG or WebP `content://` image or `text/plain`. A share is remembered in memory only (`ShareInbox`) and waits behind the sign-in gate. Nothing is read, prepared, uploaded, fetched or sent until the owner confirms in `ShareDialog`: a photo goes to the project they pick, text goes into the Chat draft (unsent), and a link is never opened. `file://` handles, other MIME types and `ACTION_SEND_MULTIPLE` are not accepted. If the process dies before the owner confirms, the share is gone and nothing was sent.

Upload recovery: the prepared bytes, name, project and upload ID are sealed in the account store (`StateKind.UPLOAD`, `StoredUploadStore`, at most five, each at most 1 MiB) before the first request and removed when the upload is confirmed, dismissed or refused for good. A restarted process lists them as retries of the same request ("won't be added twice"). Sign-out and account change erase the files with the rest of the account state, and the ViewModel drops its in-memory copy when the account changes. If the bytes cannot be stored the upload still goes ahead, but cannot outlive the process.

## Chat and the review-and-confirm sheet (WP6)

- **Where it lives.** `ChatSession` (conversation logic, no Android code), `ChatContent`/`ChatLayout` and `ReviewSheet` are in `:shared` `commonMain` under `ui/chat`. `ChatViewModel` (draft plus session) stays in `jvmCommonMain` because the account-scoped draft store is JVM code. The app only supplies the ViewModel and three hand-offs (preview, update, help).
- **Lost replies (decision, 2026-10-29).** A send takes its request ID once (the turn ID). If the reply is lost the outcome is unknown: `ChatSession` reads `chat/turns/{id}` through `MobileApiClient.resolveSend` and never re-sends. Only an explicit "Send again" re-sends, with the same ID, text and `expectedRevision`. The draft is cleared only once the send is committed, so a lost reply or a stale revision never costs the owner their text. Known limit: the in-flight request ID is not persisted, so after process death the draft is still there and sending it again is a new, explicit owner action.
- **Confirm (decision).** Confirm sends the turn's `revision` as `expectedRevision` and one request ID per review. `proof_required` with `fresh_passkey` calls `ReauthHook.reauthenticate()` once and retries with the same ID. `ReauthHook` is the seam WP5 implements next to `SessionProvider` (Credential Manager plus `reauthOptions`/`reauthVerify`); tests use a fake. Until WP5 lands the app wires a hook that returns false and a session with no token, so Chat reports "Sign in to continue" and still keeps the draft. A lost confirm reply is checked by reading the conversation, never by confirming again. `stale_revision` or `review_unavailable` leaves a sheet with no enabled confirm.
- **Sheet.** Bottom sheet below 840dp, a side pane (the shell's detail pane) on expanded widths. Order and labels follow D8: the named effect (Publish website, Save private website, Turn on app, Restore app data) is the only primary, Open preview is secondary, Not now is quiet. The disclosure lines are shown verbatim. An unknown review kind or a control this build did not declare shows "Update required" and nothing is enabled.
- **Interactions.** A turn carrying an interaction shows a generic card (status only). No payload is parsed or rendered until WH-105 lands.
- **Haptics and announcements.** `Confirm` on an accepted confirm, `Reject` on a failed send or confirm; no haptic on send. New replies and review outcomes go through one polite live region, and the typing indicator is itself a polite live region with visible words.
- **Tests.** `ChatSessionTest` and `ChatViewModelTest` run against `MockEngine` serving the frozen fixtures (lost reply, stale revision, proof_required, unknown control). `ChatBehaviorTest` checks semantics; `ChatScreenshotTest` records `chat-*` and `review-*` goldens at 360 and 1000dp, light and dark.
- **Open.** None; relative timestamps and Custom Tab previews arrived in polish 1 (below).

## Passkey sign-in, browser hand-off and App Links (WP5)

**What exists.** `com.whumpo.core.auth` (`:shared`, `jvmCommonMain`) is the sign-in logic with no Android types: `AuthController` (state machine), `SessionManager` (the `SessionProvider` for `MobileApiClient` and the sealed storage), `Pkce`, and the `PasskeyAuthenticator` and `BrowserLauncher` interfaces. `commonMain` holds `AuthState`/`AuthActions` and the screens (`ui/auth/AuthScreens.kt`). `:androidApp` supplies Credential Manager (`CredentialManagerPasskeys`), Custom Tabs (`CustomTabsBrowser`), the `AuthGate` composable that decides between sign-in and the shell, and the App Link handling in `MainActivity` (`launchMode="singleTask"`, `onNewIntent`).

**Journeys.** Passkey: `session/login/options`, Credential Manager `getCredential`, `session/login/verify`, `GET /session` (account label), the session sealed in the Keystore-backed store, then `GET /bootstrap`. An unfinished welcome shows "Finish setting up in your browser" and holds the shell shut. Browser hand-off (the fallback, the invite, and an incomplete account): PKCE S256 `session/handoff/start`, the browser page from the server's `browserPath` (the app composes the URL from its constant origin and refuses any path that is not a single-slash path), the verified App Link `https://whumpo.com/app/return?code=...&state=...` back, then `session/handoff/exchange`. A hand-off is single use and held in memory, so the process dying while the browser is open means starting again. Fresh passkey: `AuthController.reauthenticate()` runs `session/reauth/*` with the same Credential Manager call and moves `freshUntil`; WP6 calls it when a control answers `proof_required` with `fresh_passkey`. Sign-out: `session/logout` (best effort, bounded to five seconds), then `AccountStateStore.signOut()` erases every record and destroys the key. A `401 proof_required` with `signin`, `identity_changed` or a local expiry does the same erase and returns to Welcome with "You've been signed out."

**Storage.** The session (token, expiry, `freshUntil`, label) is one `StateKind.SESSION` record in the existing `AccountStateStore`, so it is AES-256-GCM sealed by the Keystore `SecretBox`, in no-backup storage, and excluded from backups. "Signed in" means an account is active in that store. The contract exposes no account id, so the store scope is the masked address label; every sign-in starts from an erased store, so two accounts with the same mask cannot see each other's drafts.

**Assumptions, resolved by the WH-083 server plan (verified against [mobile-api-v1.md](mobile-api-v1.md)).** (1) Return link: `https://whumpo.com/app/return?code=<64 lowercase hex>&state=<as sent>`. The parser is strict: exactly `code` and `state`, each once, a 64-character lowercase hex code and a state equal to the one sent; anything else is refused and the hand-off is spent. (2) Hand-off purpose: after `identity_incomplete` the account already exists, so the app sends `signin` and the browser resumes enrollment or recovery. `signup` is sent only by the explicit invite entry (`startInvite`). The app has no "lost my passkeys" entry, so it never sends `recovery`. (3) Credential Manager's authentication response JSON is sent to `session/login/verify` (and `session/reauth/verify`) as-is. The client enforces the 8 KiB limit on its UTF-8 size first; an oversized credential shows a local "too large" error (`AuthProblem.CredentialTooLarge`) and sends nothing. (4) Still open: the `local` flavor reaches loopback for the API, but the contract fixes the return link to whumpo.com, so a hand-off cannot complete against a local server.

**Not tested in CI, plainly.** Real passkeys cannot run in CI: Credential Manager needs a physical device or a Google-services emulator image with a credential provider, a Google account, and the published `assetlinks.json` for the signing identity. The unit tests drive the state machine with a fake `PasskeyAuthenticator`, a fake browser and the WP4 client on Ktor's `MockEngine`; the screenshot and Robolectric tests cover the screens. App Link verification, the Custom Tab round trip, "Use a passkey from another device" (it re-opens the system sheet; whether it shows the hybrid option when no credential exists is a device check), TalkBack speech and the whole sign-in against a real server are WH-087 device evidence.

**App Links and Digital Asset Links.** `AndroidManifest.xml` declares one verified App Link (`autoVerify`) for `https://whumpo.com/app/return`; polish 1 added the Activity and Projects links. Verification and passkeys both need `https://whumpo.com/.well-known/assetlinks.json`. The repository holds only a template, [`docs/android/assetlinks.template.json`](android/assetlinks.template.json), with a placeholder for the Play App Signing certificate fingerprint. It is **not** published. The owner steps are in [android/assetlinks-setup.md](android/assetlinks-setup.md).

## Projects, Activity, Settings and the notifications client (WP7)

The three screens, their ViewModels and the photo and push seams live in `:shared` (`commonMain` where nothing needs Java; Settings stays in `jvmCommonMain` because it uses the account repository and environment guard). `:androidApp` keeps only wiring: the dependency graph (`AppContainer`), ViewModel factories, the system photo picker launcher, the theme store and the INTERNET permission.

- **Screens.** Each is a stateless `*Content` composable plus a thin stateful wrapper, so goldens render fixed state. Every state goes through the WP3 components via `StateHost` (skeleton, `EmptyState`, `ErrorCard`, `UpdateRequiredScreen`). The signed-out API error shows as an error card with "You've been signed out."; the WP5 session replaces `ShellSessionProvider`.
- **Projects.** `ProjectCard` is the web `ServiceTile` as a card (icon square, name, status badge with icon and word, "Updated 5 min ago"). The card's spoken description carries the absolute UTC time. Compact and medium show list, then detail (back closes the detail first); expanded shows both panes. Detail shows status, the Website and App service tiles, saved versions and photos.
- **Photos.** Add through the system photo picker (`PickVisualMedia.ImageOnly`): no storage, camera or location permission. `PhotoPipeline` matches the web `prepareProjectPhoto`: JPEG, PNG or WebP up to 10 MiB, EXIF orientation applied, fit within 1600 x 1600, flattened on white, baseline JPEG within 1 MiB (quality 85 down to 25), and all APPn and comment segments removed (the same markers `src/photo-format.ts` strips). The upload ID is generated once per pick; a lost reply is resolved with `getPhotoUpload` (404 means nothing committed), and an explicit retry reuses the same ID, name and bytes. Photos show status; only `ready` and `approved` is "Ready". Shortcut: the prepared bytes are held in memory, so a retry after the process dies starts a new pick.
- **Activity.** A cursor-paged feed with relative times; opening a notification calls `ActivityViewModel.openEvent(eventId)`, which reads the event and shows a notice or "This item isn't available anymore."
- **Settings.** Account label (the server's masked label from `GET /session`), Appearance (System, Light, Dark; device preference, kept on sign-out), Notifications, Security and help (browser links to `/workspace/security` and `/workspace/support`), legal links, About, and Sign out with a confirmation. Sign-out calls `logout`, then `SessionProvider.onSessionRejected()` (the only local-clear hook on the WP4 interface), then erases account state. The server call is best effort so sign-out works offline.
- **Notifications client.** `DeviceNotifications` wraps `registerDevice`, `removeDevice` and `getEvent`. Push delivery sits behind `PushMessaging`; this build wires `NoOpPushMessaging`, so Settings says notifications are not available yet. See [android-notifications.md](android-notifications.md) for the owner steps.
- **Tests.** ViewModel tests run against the frozen fixtures through the WP4 MockEngine (`ApiFixtures`); `PhotoPipelineTest` runs the pipeline on Robolectric bitmaps with a crafted EXIF segment; `ScreensScreenshotTest` records Roborazzi goldens for each screen at 360 and 1000 dp, light and dark, plus the project detail at 200% text.
- **Declared controls.** The build declares no review controls (`ClientInfo.current(build, controls = emptyList())`) because nothing here confirms a change; WP6 widens it with Chat.
- **Not in WP7.** Authenticated Custom Tab preview and "Ask about this project" (Chat context) waited on WP5 and WP6; both are in polish 1 (below).

## Polish 1: deep links, Chat times, Custom Tab previews, ask-about-project, accessibility checks, back API

Closes the gaps WP3 to WP7 reported. Verified in GitHub Actions only (no Android SDK here).

- **Deep links.** `AndroidManifest.xml` claims `https://whumpo.com/app/projects/*` and `/app/activity/*` (auto-verified, like `/app/return`). `DeepLink.parse` (`:shared`, `commonTest` covered) accepts only the exact host over HTTPS, no port or fragment, one path segment and a lowercase UUID, and returns nothing for anything else. `MainActivity.handleLink` offers a parsed link to `DeepLinkInbox` (in `AppContainer`); everything else still goes to the hand-off return. `WhumpoApp` sits inside `AuthGate`, so the shell, and therefore the link, only appears for a signed-in account: signed out, the link waits (in memory) and opens after sign-in. The shell selects the destination (`WhumpoShell(requested = ...)`); Projects selects the project, Activity calls `openEvent` and shows the existing notice. A missing or foreign ID shows the existing "isn't available" states. A claimed link with an invalid ID is ignored, not sent to the browser, because a Custom Tab to a verified link would return to the app. Verification still needs `assetlinks.json` on whumpo.com (owner task, [assetlinks-setup](android/assetlinks-setup.md)); the instrumented `DeepLinkTest` calls the same `handleLink` path and cannot prove verification.
- **Relative times in Chat.** `ageLabel` in `ui/common/Time.kt` is the one helper: Activity, Projects and Chat all use `timeLabel`. A turn's `createdAt` shows as "5 min ago" under the owner's message; the content description carries the absolute UTC time. `ChatScreenState.now` is refreshed with each state change (a quiet screen does not tick); goldens pin it. UTC only, as before (`shortcut:` in `Time.kt`).
- **Previews.** The contract does define the handoff: [mobile-api-v1](mobile-api-v1.md) says a Custom Tab preview "uses the browser session" and "the app never injects its bearer into a browser"; a signed-out browser shows normal sign-in and returns to the allowlisted path. So previews open in a Custom Tab through the same `CustomTabsBrowser` as sign-in, with only the allowlisted server path on the constant origin. The default browser is the fallback when no Custom Tabs host exists. Nothing is added to the URL, and there is no preview token endpoint to call.
- **Ask about this project.** A button on project detail calls `ChatViewModel.prefill` with `I'd like to talk about my project "Name". ` and switches to Chat. It never sends, appends after an unsent draft (separated by a blank line) and does nothing before the stored draft has loaded or when signed out. The Projects and Chat destinations share one `ChatViewModel`.
- **Accessibility checks.** `AccessibilityTest` (instrumented, `ui-test-junit4-accessibility` from the Compose BOM) calls `enableAccessibilityChecks()` and runs the Accessibility Test Framework on the sign-in screen and each of the four destinations. Screens are checked in whatever state the emulator reaches with no server (error and empty states). It does not replace TalkBack on a device.
- **Back.** `PredictiveBackHandler` is replaced by `NavigationBackHandler` from `navigationevent-compose` (1.1.0, the artifact Compose Multiplatform already pulls in; stable) in `rememberBackProgress`. The shell still scales and fades with the gesture progress. `compose-ui-backhandler` is no longer a dependency, and the `@Suppress("DEPRECATION")` and `shortcut:` notes are gone.
- **Goldens** for Chat (timestamps) and project detail (new button) were re-recorded through the `record_screenshots` workflow input and reviewed.
