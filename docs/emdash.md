# EmDash CMS support

EmDash is an explicit TownHello workload, added at the owner's request on September 29, 2026. This is a native Astro/EmDash application, separate from the static website templates and the pure-function QuickJS runtime. Do not attempt to execute EmDash inside QuickJS or represent a static blog export as a functioning CMS.

## Implementation

`integrations/emdash` contains a pinned EmDash 1.0.1 + Cloudflare adapter 1.0.1 application. The blog theme, seed, live content loader and pages derive from upstream commit `5de3bdc4310f6bcca013f05002f05a61e208b2a4`; the MIT notice is retained in `UPSTREAM-LICENSE`. The template includes posts, pages, archives, search, RSS, rich content rendering and admin entry links. Content stays in EmDash's own schema. Fonts and cream/green theme defaults follow TownHello; font licenses remain in `docs/licenses`.

Run `pnpm install`, then `pnpm build:emdash` from the repository root. Run `pnpm --filter @townhello/emdash dev` for local development. The existing TownHello deploy command intentionally does not deploy/provision CMS tenants. Each deployment needs an owned project and a separately resolved resource map.

The production profile uses dedicated D1, R2 and Astro session KV resources. It has no public route, workers.dev address or public preview URL. This protects the initial administrator setup while the ownership/bootstrap integration is being developed. The profile checker examines the generated Cloudflare configuration as well as the source, since Astro can insert bindings at build time.

## Cost and plugin boundary

No Worker Loader, Dynamic Workers, Container, email or Images binding is configured. Astro's default Images binding is explicitly avoided with passthrough image handling. Native plugin arrays are empty, and a sandbox runner is not selected. Upstream supports the core CMS without a Worker Loader; installing/executing sandboxed plugins requires the paid-only loader and is unavailable under the owner's current restriction. Never substitute `sandbox: false` or run untrusted plugins in-process to bypass that restriction. Keep this distinction visible in the future customer interface.

Core EmDash supplies passkey-based administration and a REST/MCP management surface. These are CMS capabilities, not automatic authorization for TownHello's agent. WordPress support means reviewed content/media migration, not PHP plugin/theme execution or guaranteed lossless conversion.

## Required integration contract

1. Provision a dedicated Worker/database/media bucket/session namespace for each owned CMS project. Record immutable provider IDs against the project and reconcile retries before creating another resource. Never use the TownHello account database for CMS migrations or share one CMS administrator across tenants.
2. Bootstrap the first administrator through the already authenticated TownHello owner. Do not expose the setup wizard publicly while it can be claimed. Keep CMS passkeys and roles separate unless a reviewed SSO bridge establishes equivalent authority.
3. Give the agent narrowly scoped management access, held server-side. Remote MCP descriptions and CMS content are untrusted data; they cannot widen authority. Do not put CMS credentials, private posts or other tenant data in reusable templates or general shared prompts.
4. Chat must support creating a CMS project, reading its state, creating/editing drafts, previewing and preparing publication. Public publication, deletion, plugin installation, imports and schema changes require exact reviews. The model cannot confirm its own proposal. Changes made in the CMS admin must invalidate stale reviews.
5. Import WordPress WXR/content into an isolated draft staging area with a report of unsupported blocks, themes and plugins. Media fetches need SSRF defenses, size/count budgets and a domain policy. Preserve authorship/licensing, sanitize rich content and preview before publishing. No PHP execution.
6. Back up CMS content, schemas, media references and required settings with versioned provenance. Restore into an isolated instance and verify it before switching traffic. A static HTML ZIP is not a CMS backup. Core upgrades need pinned releases, a migration snapshot and a tested restore path.
7. Reuse the existing domain ownership/routing review flow, with an explicit CMS destination. Add per-project storage/CPU/request admission and plan accounting. Verify native passkeys, media, roles, publish/unpublish, draft privacy, backup/restore and concurrent tenants on Cloudflare before advertising customer-ready support.

## Owned request bridge — September 29, 2026

The CMS now uses EmDash's supported external authentication interface with a TownHello provider. TownHello's own passkeys remain the intended user authentication boundary. This is not a public CMS login route or proof of native CMS passkey enrollment. A private instance must be configured with `TOWNHELLO_CMS_PROJECT_ID`, `TOWNHELLO_CMS_OWNER_ID`, a unique secret `TOWNHELLO_CMS_BRIDGE_KEY` (at least 43 characters, generated from secure random bytes), and canonical `TOWNHELLO_CMS_ORIGIN`. `EMDASH_SITE_URL` must match that origin. Missing configuration denies access. No production owner or bridge credentials have been assigned yet.

`src/cms-bridge.ts` signs and verifies short-lived HMAC-SHA256 assertions bound to project, owner, origin, method, exact path, request UUID, expiry and request-body digest. Assertions last at most 60 seconds; cookies and bearer headers are rejected. The gateway forwards only the signed assertion, JSON content type and the configured same-origin header. The CMS provider derives a pseudonymous owner identity from the pinned owner ID, rather than trusting a submitted email or role. EmDash provisions that owner through its external-auth interface; role synchronization is disabled. Only one configured owner is accepted per isolated CMS.

The initial allowlist permits setup-status, current-owner and collection-schema reads, plus initial setup with a bounded title/tagline and `includeContent:false`. It blocks native setup-admin, public setup/admin UI, plugin operations and all other routes. Setup writes reserve a receipt in the dedicated CMS database before dispatch. An exact retry returns the saved bounded JSON response; a changed request with the same ID is rejected. Lost reservation or execution acknowledgments never cause a blind repeat. Unknown outcomes require reading setup status before preparing another operation. Responses do not relay session cookies. Setup receipts are capped at 100 per instance; this is an initial setup guard, not a final content-operation retention policy.

`src/cms-gateway.ts` is used by the actual Astro Worker entrypoint. The CMS retains its dedicated D1/R2/KV stores and private-only routing. All of this is service-to-service plumbing: no model has a generic CMS signing or transport tool, no public browser can obtain bridge credentials, and project creation/confirmation is connected through the reviewed setup queue described below. Any future operations must be explicitly added with their authorization/review and concurrency contracts; the allowlist must not become an unrestricted REST proxy.

## CMS setup requests and project registry

Migration 0036 connects CMS setup intent to owned TownHello projects. Chat supports `/cms` (or `/cms PROJECT_ID`), `/setup-cms PROJECT_ID | title | optional tagline`, `/cms-review REVIEW_ID` and user-only `/confirm-cms REVIEW_ID`. The agent can list, prepare or read a review; it cannot confirm. Its proposal prose is replaced with the server's exact receipt. Confirmation creates a queued registry entry atomically with review approval. Neither preparation nor confirmation currently creates Cloudflare resources or claims the private preview.

A ten-minute review fixes project, owner, title, tagline and the empty/private setup contract. The dedicated Worker/database names are deterministically derived from the project UUID; the media bucket has its own matching name. Provider resource IDs are initially absent and, once recorded by provisioning, cannot be replaced by a different identity. A queued entry cannot be marked ready without recorded database, session-namespace and deployment version IDs. Concurrent reviews for the same project cannot both approve. Retries return the original approval, and capacity errors roll back the approval/registry transaction. Initial admission is two instances per account and five across the platform; these are explicit beta cost guards, not the final plan entitlements. No additional paid services are introduced.

Authenticated HTTP equivalents: `GET /api/cms`, `POST /api/cms/setup-reviews` with `{id,projectId,title,tagline}`, `GET /api/cms/setup-reviews/:id`, and `POST /api/cms/setup-reviews/:id/confirm`. Requests cannot submit provider IDs or credentials. Guided commands do not consume AI units. Chat offers a setup button only after its complete exact review text is saved and while the review is current and unexpired. Approval removes the button. Reading an existing review remains available through the command/API after an interrupted response.

`test:cms-projects` covers real D1 tenant ownership, immutable reviews, simultaneous confirmations, expiry, replay, deterministic resource identities, initial-state truthfulness, atomic capacity, guided controls and metered AI proposal receipts. `test:cms-projects-http` verifies authenticated same-origin prepare/confirm endpoints against a local Worker. The operator pipeline below connects approved requests to isolated resources and the signed bridge. Confirmation alone reports queued, never ready or public.

## Provisioning consumer: storage allocation

`npm run cms:provision -- --list` reads approved unfinished requests from the production control database using the already authenticated Wrangler account. `npm run cms:provision -- PROJECT_ID --storage-only` allocates and records that approved project's dedicated D1 database, R2 media bucket and KV session namespace. Without `--storage-only`, it continues through the deployment/bootstrap pipeline below. It is an operator command, not an AI tool. Credentials are read into memory through `wrangler auth token --json`; they are not written into registry rows or printed. The fixed account/control-database IDs come from `wrangler.jsonc`.

Migration 0037 adds an immutable creation-intent/receipt ledger. Before reserving a new resource, the consumer checks the paginated provider inventory for collisions. A pre-existing name without a recorded creation intent is not adopted. Only the process that successfully records a fresh intent may dispatch creation. A competing process, lost reservation acknowledgment or later retry only reconciles provider state. Recorded provider IDs are immutable and unique within the account/resource kind; missing/replaced resources and account mismatches stop allocation. Provider errors never trigger plan upgrades, public access or an automatic repeat of an uncertain creation request. An unresolved attempt remains uncertain for reconciliation/operator investigation; the command does not offer a blind reset/retry switch.

The consumer uses Cloudflare's documented [D1 creation](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/create/), [KV namespace creation](https://developers.cloudflare.com/api/resources/kv/subresources/namespaces/methods/create/) and [R2 bucket creation](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/methods/create/) APIs, with bounded paginated inventory reads. Remote control-database statements bind parameters. No database, bucket or namespace is shared across project records.

Three storage receipts still mean `provisioning`, not `ready`. The next stage verifies Worker deployment, per-instance secret installation, platform service binding, signed setup and owner/schema verification before readiness. `/cms` reports the number of recorded storage resources and explicitly identifies unverified deployment/initialization or uncertain provisioning. This operator consumer is not yet a continuously running scheduler.

`test:cms-provision` uses actual local D1 plus a controlled provider to exercise approved-only admission, competing allocators, lost provider and reservation acknowledgments, delayed result reconciliation, collision rejection, changed resource IDs, account pinning and pagination. A production read-only run returned no queued requests. Live inventory reads located the existing private preview database and media bucket. No customer resource was allocated during that check; live creation of a confirmed customer's full instance remains an acceptance gate.

## Private deployment, bootstrap and platform connection

`npm run cms:provision -- PROJECT_ID` now continues an approved request through native EmDash deployment. Migration 0038 records an immutable source digest, signing-key digest, private origin and deployment tag before upload. Only the process that reserves a fresh deployment intent may upload. Lost acknowledgments reconcile the active tagged Worker version; they do not trigger another upload. An existing Worker without an intent is rejected. Changed source, keys, provider accounts or recorded Worker versions stop recovery.

The compiled artifact is retained under ignored `.secrets/cms/PROJECT_ID/artifact`. A random master key in `.secrets/cms/master.key` derives a separate HMAC bridge key for each project, owner and origin. The project receives only its derived key; the main platform receives the master as a Worker secret. Neither key enters database records, public assets, model context or command output. Keep a secure operator backup of the master and frozen artifacts. Missing keys after deployment or missing recorded artifacts require restoring their originals; generating replacements is deliberately refused. Secret rotation and artifact upgrades need a separate reviewed migration workflow and are not implemented by this initial provisioner.

Each instance has dedicated D1/R2/KV bindings, no public routes, no workers.dev or preview URL, and no paid loader or Images binding. Tenant cron triggers are disabled; native scheduled publishing and maintenance scheduling remain open work. A temporary loopback-only remote service-binding probe performs signed setup with the original approved review ID and `includeContent:false`. Every retry uses the same setup receipt. Native setup closure, the exact owner's admin identity, and both posts/pages schemas must verify before the deployment becomes `verified`.

`tools/deploy-platform.mjs` includes all verified/connected CMS bindings in the main platform deployment and checks the active version's binding metadata. A database lease serializes this tool's deployments. The normal `npm run deploy` path uses it, preserving CMS bindings on subsequent releases. Successful provisioning records that platform version, and a database trigger then marks the instance ready. No user or model endpoint can submit deployment receipts. `/check-cms PROJECT_ID` and authenticated `GET /api/cms/:project/status` independently verify native owner/schema status through the platform's private binding.

Verification: `test:cms-deploy` uses actual local D1 and controlled provider responses for lost acknowledgments, immutable inputs, exact setup replay, wrong-owner/missing-schema failures, readiness gating and tenant status isolation. `test:cms-release` checks generated private routing, dedicated bindings, frozen source digests and deployment tags. `test:emdash-bridge` verifies initialization and owner/schema reads against the actual pinned EmDash application. Live customer allocation, Worker upload/bootstrap and binding access remain an acceptance gate because the approved production queue is empty. These tests do not establish content editing, publication, WordPress import, media or backup/recovery support.

## Native private draft creation and reads

The next content stage uses EmDash's own posts/pages API and portable-text storage. Chat supports `/cms-draft PROJECT_ID posts|pages | title | body text`, `/cms-drafts PROJECT_ID`, `/cms-read PROJECT_ID REQUEST_ID` and `/cms-retry PROJECT_ID REQUEST_ID`. The agent supports `cms` actions `draft`, `listDrafts`, `readDraft` and `retryDraft`; replies come from server receipts, replacing unverified model success claims. Guided commands retain the chat's 1,000-character input limit; model-created draft bodies allow up to 2,400 UTF-8 bytes, titles 100 characters and total encoded bridge bodies 4,096 bytes.

Migration 0039 reserves the exact project, owner, collection and canonical draft body before contacting EmDash. Retrying an immutable request ID reaches the same native gateway receipt; changed bodies are refused. A missing response stays unresolved and the user can recover it with `/cms-retry`, which reads the saved intent rather than accepting replacement content. An unknown native write is never dispatched again by the gateway. Saved receipts list up to 90 requests per instance, including unresolved attempts, with a 450-request platform cap. The CMS bridge retains at most 100 write receipts, reserving headroom for setup and later operations. These are beta lifetime caps; retention and expanded content quotas remain work.

The authenticated bridge adds EmDash's required mutation header only after signature and operation checks. The content allowlist admits canonical paragraph-only creation with `status:draft`, plus a read of a native ULID within posts/pages. It excludes client-selected author, publication dates/status, references, plugin data, HTML blocks and arbitrary collection names. Text that contains HTML syntax is stored as portable text, not interpreted as an HTML block. The main platform resolves native IDs only through owned saved requests and requires an initialized, connected CMS. The native draft data stays in that project's CMS database; a private immutable creation intent is also retained in the control database for recovery.

Actual local EmDash tests create and read both posts and pages, verify exact replay and changed-body conflicts, and reject publication requests and public frontend access. Local D1/platform tests cover lost responses, exact recovery, owner isolation, immutable intent, guided chat and server-authoritative agent receipts. The existing deployment tooling builds this updated profile for future approved instances. Existing frozen artifacts are deliberately not rewritten. Editing existing entries, browsing imported/native-admin content outside this receipt registry, rich media, preview rendering and reviewed publication remain the next content gates.

## Revision-bound native draft editing

`/cms-read PROJECT_ID DRAFT_REQUEST_ID` now returns the native revision token. `/cms-edit PROJECT_ID DRAFT_REQUEST_ID REVISION | title | full body text` replaces that private draft's title and paragraph content using the token. `/cms-edits PROJECT_ID DRAFT_REQUEST_ID` lists edit receipts; `/cms-retry-edit PROJECT_ID EDIT_REQUEST_ID` recovers the exact stored edit. The model equivalents are `editDraft`, `listEdits` and `retryEdit`. The agent must read first, preserve unrelated content and use the returned revision rather than inventing one. Publication remains unavailable.

Migration 0040 stores immutable edit intent with its original draft receipt and canonical body. Ownership and private draft state are checked before reserving a new edit. The signed bridge permits a native PUT only for a posts/pages ULID, bounded paragraph content, `status:draft` and a required `_rev`. EmDash enforces that revision during the mutation. Exact retries use the existing gateway receipt; changed intent is rejected, and an unknown dispatch is not repeated. A saved edit result describes the historical operation; a fresh `/cms-read` is authoritative for current content.

Create and edit intents now share the 90-request per-project / 450-request platform beta capacity. The CMS gateway still caps all write receipts at 100. These limits count uncertain and failed reserved operations; quota reclamation and retention remain work. The control database retains private creation/edit text for exact recovery, while EmDash retains native content and revisions in its dedicated database. Editing is restricted to drafts created through TownHello's receipt registry; imported content and rich-text/media editing remain separate gates.

Actual local EmDash tests verify posts/pages edits, changed revision tokens, exact replay, changed-body rejection, missing-token denial, stale revision rejection and simultaneous edits producing one success and one conflict. Platform tests cover lost edit responses, receipt recovery without another update, foreign-owner denial, immutable intent, model receipt replacement and combined capacity enforcement. These checks do not prove public publication or live tenant content editing.

## Private browser previews

`/cms-preview PROJECT_ID DRAFT_REQUEST_ID` (or model action `previewDraft`) offers an **Open private CMS preview** button in chat. The link points to `GET /api/cms/:project/content/:request/preview` and requires the current owner's TownHello session. It reads the latest native EmDash draft each time; it is not a public share token or a frozen publication review. The revision is shown in the footer. The cream/green TownHello article layout renders the supported native paragraph profile, preserving line breaks and escaping text. Unsupported rich content fails explicitly instead of being omitted.

Responses are private/no-store with sandbox CSP, no scripts or external assets, blocked framing, no referrer and no indexing. Tenant strings cannot supply markup, CSS or URLs. Migration 0041 stores immutable owned preview links so the chat can expose buttons only after a completed server receipt; link storage is capped at 100 per user / 1,000 total. Links contain project/request identifiers, never CMS secrets or native preview tokens. They remain subject to ownership checks on every open.

Native integration tests feed actual EmDash posts/pages into the renderer, including HTML-like text escaping. Platform tests verify preview link hydration, ownership and restrictive response headers. HTTP tests reject anonymous, foreign-owner and uninitialized-instance requests. A local browser check confirmed the article layout and inert HTML-like text. These are TownHello previews of native CMS content; custom CMS themes, rich media and frozen publication reviews remain separate work.

## Reviewed native publication

`/publish-cms PROJECT_ID DRAFT_REQUEST_ID` prepares a ten-minute review of the current private native draft. The agent can prepare the same review with `reviewPublication`; it cannot confirm. The review fixes the native revision, content snapshot, article HTML/digest and destination `https://sites.digifender.com/s/PROJECT_ID/cms/posts|pages/NATIVE_ID`. Chat provides a **Review exact CMS article** link and a **Publish reviewed CMS article** button. `/cms-publication REVIEW_ID` reads the stored review; `/confirm-cms-publish REVIEW_ID` is the separate user action.

Migration 0042 makes the review immutable and permits only pending → approved → published transitions. Approval checks the current owner, draft data/revision and expiry. The signed bridge's publish allowlist requires exactly `{_rev}` for a posts/pages ULID; it admits no arbitrary publication dates or lock overrides. Native EmDash then promotes that revision using its normal publish API. The platform verifies the returned published identity/data against the approved snapshot before marking the review published. That final state gates public serving. An uncertain acknowledgment keeps the public route unavailable; repeating the same confirmation recovers the same native gateway receipt rather than dispatching a second publication. Prepared and approved rows are never public.

The public site host serves only the reviewed, digest-verified article HTML from a published row with a current owner and ready CMS. It does not expose the private CMS Worker or route visitor requests into admin/draft APIs. The approved article remains stable if a private CMS draft changes later. The review page is authenticated, private/no-store and sandboxed; public article responses are script-free and no-store. Native administration, plugins, raw content API and drafts retain the private boundary.

Current scope is first publication of a supported paragraph post/page to the platform's public article URL. Republish, reviewed unpublish, article indexes/navigation, CMS custom-domain paths, richer themes and media remain open gates. Existing edit commands intentionally require draft status. Review storage is capped at 100 per user / 500 platform-wide, and native write receipts still share the 100-per-instance lifetime beta cap. Full tenant live onboarding and publication remain unverified because no approved customer instance exists.

Verification: actual EmDash tests publish both collections, reject stale revisions, compare returned data exactly and replay the same publication receipt. D1/platform/chat tests verify immutable reviews, foreign-owner denial, expiry, stale review rejection, agent prepare-only authority, recovery after a lost native response, non-public intermediate states, identical reviewed/served HTML and HEAD serving. No customer article was published during these tests.
