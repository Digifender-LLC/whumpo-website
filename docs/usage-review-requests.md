# Customer usage-review requests

September 30, 2026. Customer-initiated requests and operator responses are deployed in the private test platform. This is a support channel, not evidence of abuse, delivery of a warning, an appeal decision or authorization to restrict an account. Monitor remains non-blocking. It does not change service capacity, billing, provider routes or internal fair-use review records.

## Customer flow

- Type `request a usage review: YOUR EXPLANATION` or `/usage-review YOUR EXPLANATION` in Chat. Statements are bounded to 950 characters; Chat retains its existing 1,000-character message limit.
- `show my usage reviews` or `/usage-reviews` lists the latest 25 requests. `/usage-reviews REQUEST_ID` reads the full owned statement and any customer-visible response; older known IDs remain readable.
- One open request is allowed per account. Read it before opening another. An answered request permits a new follow-up request. No response time, email, external contact or automatic change is promised.
- There are no default dashboard buttons and no model mutation action. Only the customer's explicit guided command submits a request. Guided reads and submissions use no inference or customer credits.

Request insertion shares the transaction with the Chat claim and revision. Replay uses the same Chat ID and exact original content. Lost acknowledgments do not create replacement requests. The database enforces owned guided turns, immutable statements and one terminal response. A racing different answer cannot overwrite the winner. Account deletion cascades; records cannot be independently deleted while the account exists.

## Privacy boundary

Migration 0097 adds a monotonic `ai_context_allowed` flag on Chat turns. Submission, help, list and detail commands in this flow store their turns with that flag disabled. Later orchestrator history excludes them; no acknowledgment model is dispatched for these guided requests. The flag cannot be re-enabled. This does not retroactively remove information the customer separately sends to the AI, nor does it redact secrets pasted elsewhere.

Customer reads select only request identity, statement, creation time, state, customer response and answer time. They do not read internal fair-use notes, observation snapshots or reviewer identities. Operator identity is an audit label, never included in the customer response projection. Operators must write an intentional customer-visible response, not copy private investigation notes.

## Operator response

Use `node tools/respond-usage-review.mjs --input PRIVATE_JSON_FILE` with the existing operator credential for the configured control database. The tool is not mounted on a customer endpoint or exposed to the model. Input/output contain private customer statements; keep them in private operator storage, not model context or public logs.

Input shapes:

```json
{"action":"list","account":"ACCOUNT_UUID"}
{"action":"read","account":"ACCOUNT_UUID","id":"REQUEST_UUID"}
{"action":"answer","account":"ACCOUNT_UUID","id":"REQUEST_UUID","response":"Customer-visible response","operator":"Operator audit label"}
```

An answer first returns the exact request/current record and `applyDigest`. After reviewing the customer-visible response, apply using the same input plus `--apply DIGEST`. Changed input invalidates that digest. The digest binds the response intent; concurrent answers still recheck the stored open state. Identical answer retries return the saved response. An uncertain write must be read or retried with the same identity/text, never replaced blindly. No actual customer response is sent as part of development tests.

## Independent support access (WH-035)

October 4, 2026. **Implemented in source with local test evidence only; not deployed, no live acceptance.** A signed-in account can reach `/workspace/support` and `/api/support/v1` without Chat, the AI provider, the first-project welcome or any AI budget. The routes are mounted before the onboarding gate and read only identity, `usage_review_requests`, `support_deliveries` and the account's own operation rows. Export, recovery and saved-work routes were never behind those gates; the support page links no new dependency on them.

- **Requests.** Two kinds share the existing table: `help` and `usage_review`, from `chat` or `support` sources. One open request per account and kind; an answered one allows a follow-up. Submission is idempotent by client UUID (identical replay returns the saved row, a different body with the same ID is refused), bounded to 950 characters, and creates no Chat turn or inference.
- **Actionable links.** Onboarding, rate-limit and Chat-unavailable error responses carry a `support` link (`/workspace/support?ref=status:CODE`). A request may carry one structured reference: `status:CODE` or `operation:FAMILY:UUID`. An operation reference must belong to the caller. Free-text references are rejected.
- **Stuck operations.** The page lists the account's own unfinished Chat turns, standard AI requests, hosting connections, GitHub backups and DNS changes with state and age (ten-minute attention threshold, matching [maintenance](maintenance.md)). It shows no provider detail, hostnames or Chat content, and never retries anything.
- **Three states.** *Response saved* (an operator answer exists in Whumpo), *notification* (`none` = in-app only, `queued`, `delivered` = provider accepted, `failed`, `cancelled`) and *read* (recorded only after the page displays the response, or after the Chat detail command shows it) are separate columns/tables. A saved response is never reported as delivered, and delivery is never reported as read.
- **Contact model (owner decision, October 4, 2026, issue #135).** Customer contact starts with the customer's Whumpo agent in Chat, which also handles responses back; the support page form remains the path when Chat is unavailable. Lockout problems are handled by email to `hello@whumpo.com`. That public address is fixed source copy (`lockoutContact` in `src/support-shape.ts`, matching the source-copy convention of the approved `enterprise@whumpo.com` pricing action), shown only as a lockout path on the support page and in the signed-out passkey/recovery help. It is not a general channel, and email still does not restore access without a passkey or current kit ([identity recovery](identity-recovery.md)). The former `SUPPORT_CONTACT` Worker variable is removed; no other address is shown.
- **Contact model update (D7, 2026-10-26).** D7 replaces the lockout-only support rule of 2026-10-04: `hello@whumpo.com` is the support address for help, including lockouts, with replies on business days, from the owner as sole operator ([owner decisions](roadmap/owner-decisions-2026-10-26.md)).
- **Hours.** No support hours are published (owner decision). `SUPPORT_HOURS` stays an owner-supplied, non-secret Worker variable and is **unset**; the page then says no hours are set and invents none. No phone number or service level exists.
- **External notifications.** Off. They require `SUPPORT_NOTIFICATION_PROVIDER` naming a provider that has an implemented sender in `src/support.ts` (`implementedNotificationProviders`, currently empty) **and** `SUPPORT_NOTIFICATION_REVIEW` recording the reviewed configuration. `runSupportDelivery` in `src/support-delivery.ts` does nothing otherwise: no row, no send. When enabled it queues only unread responses, sends a content-free notice (account, request ID, recipient, template), claims each attempt before sending, backs off 5 minutes doubling to 6 hours, stops after five attempts (`exhausted`) or on a non-retryable rejection (`rejected`), and is at-least-once. It is not scheduled anywhere; selecting a provider, reviewing it and adding a trigger are separate owner-authorized work. This adds no paid service.
- **Operator workflow.** `node tools/respond-usage-review.mjs --input FILE` gains `{"action":"queue","state":"open"|"answered"}` (cross-account, oldest first, private output; `answered` shows delivery and read state). Answering remains preview then `--apply DIGEST`. Maintenance reports two new queues, `support_open` (72-hour internal attention threshold) and `support_delivery`; the thresholds are internal and promise customers nothing. Support hours, escalation and incident communications are in [incident runbooks](incident-runbooks.md#15-support-hours-escalation-and-customer-communication).
- **Privacy.** Customer projections exclude reviewer identity, fair-use reviews/observations and finance data; cross-account reads return 404. The operator queue is reachable only through the operator tool with the control-database credential. WH-016's restricted safety-case intake is separate: this generic support does not detect abuse or handle safety cases, and says nothing implying it does.

## Chat help intake and response readback (WH-035)

October 4, 2026. **Implemented in source with local test evidence only; not deployed, no live acceptance. Requires the pending empty-D1 schema cutover** (the `usage_review_requests` source check and insert trigger changed). This implements the owner decision on [issue #135](https://github.com/zemdregon/whumpo/issues/135): customer contact starts through the customer's Whumpo agent, which also carries responses back. It reuses the existing support store, states and operator workflow; there is no second support store.

- **Intake.** The owner agent's `interaction requestSupport(statement)` issues the maintained `support-request@1` Chat form through the [WH-105 interaction protocol](chat-interactions.md#support-help-intake-and-readback--october-4-2026-utc): one required 950-character `statement` field whose model-prepared text is a visible *Suggested by Whumpo* default, submit binding `support.request@1`, no continuation and no project. The model prepares only. Creating, rendering, reading and draft saves create no support request. Only the owner's explicit **Send to support** (`/api/chat/interactions/v1/mutate`, operation `submit`) commits, in one transaction, the immutable form submission and one `usage_review_requests` row (`kind=help`, `source=chat_form`, `id` = the submission ID). No agent action can submit, confirm or alter it.
- **Database invariant.** A `chat_form` row is refused unless an owned, submitted, project-less `support-request@1` submission with that ID exists and its submitted `statement` equals the stored statement. Support-page rows cannot reuse a submission ID. One open help request per account and the 200-request test capacity apply to both paths (preparation and submission refuse with `support_open`; the refused form keeps its answers editable). Exact replay returns the original receipt; a changed body with the same request ID conflicts.
- **Readback.** `interaction readSupport(requestId|null)` is a bounded lookup (the existing single follow-up): `null` lists up to ten of the owner's own requests with state, a 160-character help preview and response-saved/notification/read states; an exact owned ID returns one help request's full statement and saved customer-visible response. `interaction showSupport` issues the fixed `status@1` support view whose `support.requests@1` card reads the same customer projection as the Support page. The workspace context carries counts only (`openHelpRequest`, `openUsageReview`, `unreadResponses`), so the agent can mention a waiting response without seeing its text.
- **Saved, delivered and read stay distinct.** An operator answer saved with `tools/respond-usage-review.mjs` is *response saved*. Chat display is in-app, not an external notification, so *notification* is unchanged. *Read* is recorded only when the owner opens the saved response in the Chat support view or on the Support page (both use the existing `/api/support/v1/requests/:id/read` receipt). The agent's lookup is not a read receipt, and reading the card does not record one.
- **Model context.** The owner's own help-request statement and the customer-visible response may enter the bounded follow-up when the owner asks; the lookup is stored in the existing `agent_inspections` class. Reviewer identity, fair-use evidence, provider detail and account IDs never do. Usage-review text keeps its existing exclusion from model context (`textAvailableToModel:false`); the owner reads it in the Chat view or on the Support page. The form and prompt tell owner and agent never to include passwords, keys, recovery codes or payment details; this is guidance, not a secret detector.
- **Fallback.** Chat intake is not the only path. The Support page and `/api/support/v1` still need only the signed-in account, list Chat-created requests and responses, and record reads when Chat is unavailable, a usage limit applies or the welcome is unfinished. Chat forms themselves keep the existing workspace, welcome and `core.editing` admission. The lockout line remains `hello@whumpo.com` only.

## Remaining launch work

Customer-requested support is not the full enforcement appeal system. Verified notices, restriction scope/expiry and appeals bound to actual restriction decisions remain required before enabling restrictions; the independent entry and authorization they need now exist as the support page. A browser operator interface, an owner-selected notification provider, a scheduled delivery trigger and service-level commitments are not configured; no hours are published by owner decision. General help requests now start in Chat through the agent-prepared, owner-submitted form above, with readback in Chat; the support page remains the fallback. Real-model selection quality, browser/device acceptance of the new Chat card and the empty-D1 cutover remain open.
