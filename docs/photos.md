## Upload contract

`PUT /api/projects/PROJECT_ID/files/UPLOAD_ID` requires a signed-in owner and matching Origin. The UUID is stable across retries. The request contains a prepared `image/jpeg` body a URI-encoded `x-photo-name` header, and `x-whumpo-photo-handoff`. The last header is explicit JSON `null` for the direct project uploader or an exact `{interactionId, definitionDigest}` for a maintained Chat uploader. Missing or malformed upload context is rejected. API names are plain text, at most 100 characters; they never become storage paths. The browser accepts JPEG, PNG and WebP inputs up to 10 MiB, decodes orientation, resizes to fit 1600 × 1600, flattens transparency onto white, and encodes JPEG. The shared [Photos/Chat uploader](../frontend/src/project-photo-upload.tsx) writes account-scoped exact request metadata before sending; storage failure prevents dispatch. Prepared bytes stay in memory only. See the current recovery contract below.

The browser and server share the unchanged [JPEG envelope implementation](../src/photo-format.ts). The server bounds the entire body to 1 MiB and accepts a constrained baseline JPEG envelope. It checks marker boundaries, dimensions, baseline scan framing and the final end marker; removes APP and comment segments, including EXIF/GPS, embedded thumbnails and profiles; then stores a checksum of the cleaned bytes. It does not fully decode JPEG pixels or scan image content. Invalid entropy data may still produce an unreadable image, but data is served only as image/jpeg with nosniff and sandbox headers. SVG, animated formats, progressive JPEG and arbitrary files are not accepted directly by the API. Browser preparation converts supported inputs to the accepted format.

## Ownership and storage

`project_files` records an immutable project, name, server-generated object path, checksum, dimensions and size. A pending reservation is written to D1 before R2 is called. D1 atomically enforces 20 photos per project, 50 per account and 500 across the test platform, including pending reservations. With 1 MiB per file, active photo storage is bounded to 500 MiB. There is no public bucket URL. The public-site Worker uses its private bucket binding only after checking the current publication’s exact photo references.

R2 writes use a create-only condition. Concurrent identical requests either create the object or verify its existing checksum and length. Different bytes, names or Chat handoffs under the same upload ID are rejected. The immutable `project_files.handoff_json` records the original upload context. New Chat reservations require an owned, open, unexpired maintained uploader and current feature admission; the insert transaction fences dismissal/replacement. An existing exact reservation can finish after that uploader closes, while current identity, ownership and feature eligibility still apply before storage and ready-state commit. A successful storage write is followed by an atomic D1 ready-state/audit commit. Lost R2 or D1 acknowledgements can be retried without overwriting or duplicating a photo. Pending reservations are not automatically expired; retry the original upload to finish them. After losing in-memory bytes, the owner can reselect the original file; its prepared checksum, dimensions and size must match before an explicit same-ID retry. If the original cannot be reproduced, operator recovery remains necessary.

`GET /api/projects/PROJECT_ID/files` lists owned metadata; `GET /api/files/FILE_ID` rechecks the owner and ready state before reading R2. Responses are private/no-store and same-origin. Other owners receive 404; anonymous callers receive 401. These APIs do not reserve AI units.

## Cleanup

Deleting a project or account cascades D1 photo rows into a durable cleanup queue. The workspace Worker's daily 03:17 UTC handler retries up to 100 queued object deletions older than an hour. It also reads the at-most-500 retained object keys and scans up to 1,000 photo objects, batch-deleting old unreferenced objects. This catches a late object write after a deletion acknowledgement; the grace period avoids interfering with recent uploads. Large backlogs are drained over successive runs. Cleanup requires the scheduled handler to run successfully; it is not an immediate deletion guarantee. Individual unused-photo removal is described below. Customer account deletion and removal of saved versions are not exposed yet.

## Versioned use and operation budgets

Use in website or `/photo FILE_ID` creates a private immutable page version without inference. `photo-page@1` supports up to four ready photos from the same project. AI edits can change those references and alt text; the model sees photo names and dimensions, not pixels. Photo bytes never enter the generic component catalog.

Private previews embed verified JPEG data URLs under a sandboxed CSP. Publication reviews disclose photo exposure; public assets are available only while referenced by the current published version. Restore switches the references with the saved HTML. Source ZIPs include exact JPEG dependencies under `public/assets`; unavailable or mismatched files fail the export. See [the version contract](photo-publication-plan.md).

Atomic monthly counters cap application R2 reads at 100,000 and writes at 10,000. Reservations count attempted operations, including retries. A photo allowance error leaves text HTML available. The small daily cleanup workload is outside these counters. These caps do not cover other applications or constitute an account-wide billing limit.


## Reviewed photo removal

`/photos [PROJECT_ID]` lists owned photo IDs, pending/ready state and saved-version counts in chat (latest project by default). “Open project photos” or the Project photos screen opens the photo panel. `/files` lists saved metadata in Chat. “Review deletion” sends `/delete-photo PHOTO_ID`; the reply names the exact photo/project and warns that removal is irreversible. `/confirm-photo-delete REVIEW_ID` or its confirmation button applies the review within ten minutes. Both commands are free, explicit guided user actions; no model proposal can confirm a removal.

Migration 0021 saves owner-scoped reviews. The confirmation, chat receipt, photo-row deletion, durable R2 cleanup key and activity event commit atomically. Expiry and ownership are checked again at mutation time. Confirmation replays recover the original chat result. Applied reviews prevent the original upload ID from resurrecting a removed photo; a deliberate new upload requires a new ID. These receipts remain while the project/account exists.

A photo used by **any** saved version cannot be removed, including private drafts and old versions. A database guard protects against a version attaching the photo between review and confirmation. Removing a photo from a newer draft does not remove older references. Existing project/account cascades remain possible for operator cleanup. A future saved-version deletion policy is required before a customer can remove retained assets.

Pending uploads can also be removed. Access stops when confirmation commits, but physical R2 deletion waits for the daily queue and orphan sweep. A late in-flight upload cannot restore its deleted metadata; the orphan sweep eventually removes its bytes. Cleanup failures retain the queue for retry. Active file rows **plus queued deletions** count toward the 500-object platform capacity, so deleting/uploading repeatedly does not evade that capacity while cleanup is pending. Project/account active-photo limits still apply separately.

## Chat upload handoff and exact recovery — October 2, 2026 UTC

**Source/local implementation; not deployed.** `interaction/requestPhotoUpload` offers a maintained project-scoped Chat view. The agent cannot supply files, URLs, names, bytes, defaults or answers. It uses the same explicit upload control as Photos, with no secondary upload handler, automatic model continuation, website edit or publication. Current safety holds apply; scanner implementation remains deferred.

`GET /api/projects/PROJECT_ID/files/UPLOAD_ID` returns current exact upload metadata or `photo:null`, with repeated owner/identity checks and no R2 access. The current response always includes `closedHandoff`, normally null. A recovery read may supply the original `x-whumpo-photo-handoff`: only a matching owned, closed handoff and no file reservation can return that exact closure proof. Repeated file reads fence a concurrent reservation. The insert trigger prevents a late request from starting under a closed handoff; absence alone never authorizes clearing recovery. A pending reservation is not ready; absence is not proof that an earlier request stopped. The client validates the current closed response and every saved metadata field before resolving recovery. A ready result confirms private storage, independently of pending/approved/blocked safety status. Held photos are never loaded by this handoff.

The browser keeps one unresolved operation per project, up to 50, under the current account in `whumpo.photo-upload-recovery` sessionStorage. Records contain IDs, name, SHA-256, dimensions, size and the original handoff identity/digest (or explicit null for a direct upload). No image bytes, provider data, URLs or object keys are persisted or sent to the model. Records survive closing the card and reloading the same browser session. They have no draft expiration; matching ready readback or matching server-confirmed closure of an unreserved handoff clears them. Account changes and sign-out clear them, and late replies cannot restore cleared state. Browser session restore and same-origin scripts can read these metadata records; they are not an encrypted backup or cross-device recovery mechanism.

Reopening an interrupted uploader checks status only. A retry requires an explicit click, the original ID/name and matching cleaned image bytes. A different image is refused before HTTP dispatch. Discarding or expiring the Chat handoff only removes the interaction; it leaves files and unresolved upload metadata under their existing lifecycle. The Photos surface can reopen the same project's upload recovery. History distinguishes a view from answer submission and makes no claim that a photo was saved or cleared.


## Task-linked upload results — current source, October 3, 2026 UTC

The original submitted website task can issue the maintained private uploader through `requestPhotoUpload`, restricted to that exact project. Its Chat turn retains the original task progress receipt. This action neither uploads bytes nor changes a website. Subsequent natural-language task questions use the existing `resumeTask` lookup and get `photoResults`: current linked file IDs, names, dimensions, upload status and safety status, with an observation timestamp. File digests, keys, URLs, image bytes, unrelated direct uploads and other tasks/projects are excluded. These observations do not select a file for website use or grant clearance.

`pending` upload means unconfirmed; `ready` means saved privately. Pending safety means held, blocked means unavailable, and approved still requires explicit selection and a separate website review. Scanning remains unavailable and deferred. Current read permission, ownership and observed file/safety state are fenced at inference dispatch and reply commit. A removed file or changed clearance cannot leave a successful stale model reply. Empty results do not prove that a prior upload stopped or that no file exists elsewhere. Dismissing the uploader does not remove a reserved file's results.

A browser returning through another uploader preserves the original unresolved request. It checks status without dispatching bytes or invoking inference. If a request never obtained a reservation and its original handoff has closed, matching server closure evidence releases the browser's recovery slot; the owner may then explicitly choose a new file. Reserved uploads keep the original handoff and retry identity after dismissal. No handoff rebinding or old-protocol reader is supported.
