# Natural-language Chat and agent knowledge

**Implemented September 30, 2026; verification and deployment evidence below.** This is the current customer Chat contract. It supersedes slash-command, command-help and guided-navigation instructions in earlier chronological feature documents. It preserves the existing owned action/review contracts and the owner-facing maintainer boundary: configure maintained capabilities first, and keep visitor/runtime work separate from the maintainer AI.

## Conversation and explicit actions

**Accepted next direction — October 1, 2026:** [Chat as the primary workspace](roadmap/chat-first-experience.md) plans persisted interactive forms, bounded custom composition and agent-managed views in WH-105–112. The [v1 interaction decision](chat-interactions.md) and offline fixtures are now defined; the production storage, renderer and agent adapters remain unimplemented. The current controls and approval rules below remain authoritative until those implementations are accepted; submitting form answers will not confer review approval.

The composer submits ordinary text to `POST /api/chat`. Slash-prefixed strings, file paths and URLs are literal message content; they cannot dispatch the internal command interpreter. The model may interpret a request, inspect owned state and propose a validated capability action. It cannot approve its own reviews. Normal requests use the configured Muse test route, with standard AI fair use and no customer credit charge. If inference is unavailable, Chat says so and saves no pretend success; Dashboard controls remain available.

Two privacy-sensitive natural-language requests retain a deterministic path: requesting/reading a private usage review, and downloading saved Chat history. Operator statements and their replies remain excluded from later model context. These paths accept the documented natural phrases, not slash syntax, and make no model call. The knowledge catalog explains how to reach them. They do not send external messages or change enforcement/billing.

Browser navigation phrases no longer intercept composer text. The sidebar and Dashboard provide direct navigation. Chat's help prompt asks the agent what it can do. Routine app-status, visitor-management and page-design buttons are removed from Chat; the user asks the agent or uses an already requested workflow shortcut. Completed-work previews, requested downloads and critical approvals remain available. Website source downloads appear when requested, rather than on every draft.

`POST /api/chat/actions` accepts a closed `ChatControl` union: exact review approvals, typed app recovery/maintenance confirmations, exact source/test inspection for a review, saved workflow shortcuts, Dashboard domain ownership controls and preparing website withdrawal. It rejects arbitrary command strings, unknown fields and malformed identifiers. These requests reuse the existing idempotent receipt handlers; their internal command adapters are not a public chat interface or a model tool. Model proposals go through `prepareSiteAction` and cannot select a `ChatControl`.

Current ownership, expiry, expected revision, exact resource checks and recent-sign-in requirements still apply. Application restore/upgrade/rollback/cancellation requires the existing fresh-session and rate-limit gate before dispatch. UI approval authority comes from server-issued review metadata, never text or model-generated links. Validated backend handlers save immutable owned reply-digest links, so a naturally requested saved review can expose its current approval control. Current owned review state and exact receipt text are rechecked before displaying it; edited, expired, foreign or stale reviews cannot acquire an active control. No natural phrase such as “yes” or pasted confirmation command bypasses the review. Request IDs and original payloads survive disconnects, workspace navigation and reloads through account-bound browser session storage. A restored request waits for a fresh Chat read: an exact saved ID, text, typed action (or null for a human message), and original revision clears the local uncertainty without another send; otherwise only explicit Retry reuses the original ID/revision/payload. Reload never automatically submits a request, and current server ownership/review/expiry gates still apply. Unsent drafts expire after 24 hours since their last edit; unresolved request details persist until resolution, sign-out or browser session-storage removal. Account changes discard the previous account’s record. Storage failure displays a warning and leaves the mounted workspace usable. Browser session restoration can retain the tab’s data; this is not cross-device or guaranteed tab-close recovery. See [browser data lifecycle](data-lifecycle.md#storage-outside-those-148-control-tables). Read retries preserve loaded history and do not resubmit messages. Changed payloads cannot reuse a committed ID.

### Current receipts and remaining reply cleanup

**Current source change, October 1, 2026 — deployment pending.** Typed controls save their plain-language label in `chat_turns.user_text` and their canonical closed action in `action_json`; ordinary human messages have a null action. Internal command strings select the existing domain handler but are not saved as the current control request. Request rendering displays saved text literally. There is no old-command request renderer or command-to-action conversion for persisted receipts.

Schema update `0118_chat_action_receipts.sql` adds immutable action identity. Directory, domain-proof removal, website-specification and service-client transaction guards require the exact typed action/review fields rather than a command string. Specification/service-client approval also checks the exact proposal digest and integer revision. Request recovery compares the original ID, revision, label and action together; changing the review while keeping an identical label cannot reuse an accepted request. An action request cannot be recovered as a human message with the same visible words. Browser recovery uses only version 2 under `whumpo.chat-recovery`; retired records are not imported.

Application/page and application-data-restore presentation requires an immutable owned reply-digest receipt. A matching turn ID or recognizable command in saved text cannot substitute for that receipt. Current review state, exact reply bytes, ownership, expiry and revision still determine whether controls are offered. Historical applied receipts remain evidence of the current operation, not permission to apply again.

This schema is a current-only cutover, not a mixed-version rollout: schema and platform/frontend must move together before test traffic resumes. Old command turns are not converted into typed approval receipts. Saved current approvals and uncertainty records retain their existing authorization/reconciliation requirements; the change does not imply approval or redispatch an operation. The owner permits obsolete test-data reset. No paid service or customer publication is required. Permanent recovery-point deletion remains operator/internal until an exact customer review control exists.

**Remaining WH-120 work:** some reply producers still emit command-style instructions and `chat-language.ts` still rewrites those replies for display. Those producers and the reply filter must be replaced together; this slice removes request rendering and review-selection fallbacks only. Do not mark the full Chat cleanup done yet. The internal `sendChat` dispatch and fixture adapters remain private; only `sendConversation` is mounted at the public message endpoint.

Existing validated tools remain the execution surface: owned project details, website drafts/edits/versions/comparisons/exports, health and traffic, plan/usage metadata, domain/DNS/hosting reviews, GitHub backup reviews, bounded backend/library/test/application actions, CMS capabilities and user-requested workspace layouts. This change adds a photo-removal review action and owned connection/photo metadata inspection. Photo inventory reads at most 20 entries plus a has-more indicator, without object keys, URLs or bytes. Connection metadata is a saved authorization snapshot, not a live provider-health claim.

The `knowledge` action selects one of nine platform-authored topics: overview, websites, applications, publishing, domains, backups, account, usage and safety. Each entry includes version and repository contract references. It documents actual capabilities, prerequisites, unsupported work and approval boundaries. It is bundled with the release and reviewed with source changes; no remote document, customer message or imported code can redefine it.

Knowledge lookup participates in the existing bounded inspection continuation: at most two sequential model calls for the original request, with the same Muse route, inference receipts and budget reservation. Lookup data is explicitly separated from system policy. The final step may answer or propose one allowed action; it cannot create an unbounded tool loop or approve a review. A direct fallback gives readable guidance rather than a raw knowledge envelope. This is a small capability-reference tool, not a general filesystem, web browser, shell or arbitrary SQL skill.

## Retrieval decision

Use direct owned database reads for current resources, status, permissions, usage and reviews. Use the small versioned knowledge catalog for product guidance. Neither needs a vector index now. This avoids embedding stale billing/permission state and keeps credentials, private visitor records and safety cases out of a search corpus.

A vector pilot is worthwhile when there is a substantial approved documentation/content corpus and measured questions that the catalog and exact lookups cannot answer. Cloudflare [Vectorize metadata filtering](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/) can narrow retrieval by tenant metadata; [AI Search](https://developers.cloudflare.com/ai-search/) is another candidate for a managed retrieval pipeline. These are candidate delivery paths, not enabled services. Checked September 30, 2026; account entitlement, indexing, storage, embedding and inference costs require verification before activation.

The pilot must enforce server-derived tenant/project scope, recheck ownership and current approval on every retrieved document, exclude credentials/visitor data/quarantined material, pin source revision/digest and citations, propagate removal and revocation, and treat retrieved content as untrusted data. A similarity score grants no permission. Keep platform-authored shared guidance separate from tenant content; never reuse private customer answers across accounts. Benchmark relevance and full indexing/query expense before adoption. No Vectorize/AI Search resource, model route or premium funding change is part of this release. The roadmap's search pilot remains deferred.
