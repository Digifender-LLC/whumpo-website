# Isolated current restore admission

**WH-117C / DP-03, October 2, 2026 UTC. Source and synthetic local evidence only.** `tools/restore-admission.mjs` checks a recovered current-format database while it is offline. It has no deployment, publishing, provider-operation or SQL-write path. It is a bounded input to WH-008/019/059; it does not implement their independently operated suppression store, data scrubber, whole-platform restoration or service activation.

## Current manifest

`captureRestoreManifest` reads the complete current schema in one bounded data-read transaction. It verifies the exact schema and both maintained compiler locks against current source, then records:

- Current format and test environment, snapshot ID and independent stream checkpoint.
- Current schema fingerprint/object count, compiler identities/digests and `wv2` cipher format.
- Required ciphertext key IDs and the active write-key ID.
- Every current table's name, row count and whole-table digest.

The manifest contains no row bodies, owner IDs, object keys, plaintext credentials or encryption material. It is still restricted operational metadata. Capture does not register a permitted restore source or prove backup custody. The independent archive inventory must pin its exact digest and checkpoint separately. Changing restored rows requires a newly reviewed manifest and independent registration; the checker never rewrites a manifest or silently accepts a changed copy.

The isolated bound is 10,000 rows per table and 64 MiB of serialized row data. Overflow refuses verification; no partial page becomes a complete inventory. This is an operator/local checker, not a request-time Worker scan or a performance forecast for a large database.

## Independent evidence interface

`inspectIsolatedRestore` receives an **operator/server-selected service capability** and an independently configured stream ID. There is no customer/model endpoint for supplying a source, URL, approval flag or receipt. The service must own an authenticated, separately retained permitted-archive inventory and current suppression/outcome history. The restored D1 copy is not that authority. No deployed adapter/store or live backup registration is configured by this work.

The checker sends a current version-2 read request to the fixed internal `/v2/check` path, with the snapshot ID, exact manifest digest and a fresh challenge. The response must contain exactly:

| Field | Required meaning |
| --- | --- |
| `version`, `streamId` | Version `2` only and the independently configured source identity |
| `snapshotId`, `manifestDigest`, `challenge` | The exact registered archive and this fresh request |
| `archiveState` | `permitted`; expired, unknown or withdrawn sources fail |
| `keyBackup` | Exact independently registered encrypted backup ID, SHA-256 digest and key IDs for this archive; no values, file paths or recovery key |
| `capturedSequence` | The archive's registered checkpoint, matching its manifest |
| `baseSequence`, `currentSequence`, `events` | Complete cumulative sequence `1…currentSequence`, starting from base zero; at most 512 events / 256 KiB. Missing, reordered, truncated or compacted history fails. A future compacted baseline requires a separately reviewed current contract. |
| `issuedAt`, `expiresAt` | Millisecond timestamps: issued no more than ten seconds ago, not in the future; unexpired, with at most a 30-second lifetime |

The response describes facts obtained by the selected independent service; its freshness fields are not a substitute for operating that service correctly. A self-labelled JSON document or an old copied receipt cannot replace the service capability. Missing/unreachable evidence keeps the candidate held. The entire fetch/body read has a ten-second deadline, including when an injected service ignores the request's abort signal; a stalled body is cancelled. The synthetic service in the test has its own SQLite archive/event registry outside the candidate database. It does not demonstrate independent provider retention, availability or disaster recovery.

### Current constraints

- `owner-erased`: the owner cannot remain in the recovered database. Foreign-key integrity is checked separately. This does not execute account-wide erasure or prove removal from external copies.
- `identity-epoch`: monotonic evidence must match the current recovered account epoch; its sessions/grants cannot retain another epoch. Suppressed sessions, credentials, invitations or records must be absent.
- `record-suppressed`: a fixed current table and exact primary-key selector must be absent. Suppression is permanent for that identity. SQL fragments, unknown tables and partial/composite-key mismatches fail.
- `record-current`: the latest independent constraint for that exact record must match its complete row digest. It can represent the current consumed invitation, cancelled review or other authority receipt. It grants no invocation permission.
- `publication-withdrawn`: the named website/backend/app surface must be absent or withdrawn. A later exact independent current-publication receipt can supersede an earlier withdrawal; a recovered old publication cannot authorize itself.
- `external-effect`: unknown outcomes hold the entire isolated candidate. Reconciliation requires the exact effect ID and a matching current terminal receipt in the declared GitHub backup, Cloudflare DNS/hostname, standard/premium inference or Stripe subscription-order store. A credential row, arbitrary user row or approval flag is not a terminal receipt. OAuth exchanges require the exact `connection_oauth_outcomes` ID and complete row digest, independently recorded as reconciled. Only a direct confirmed rejection or known-token revocation creates that terminal receipt. Client/owner/provider/key/revision differences fail the digest check; an unresolved exchange row still holds the candidate. No adapter can resolve an irretrievably lost response without additional provider evidence.

- `preservation-hold` (WH-132, source and local tests only): the current source is refused while any [preservation hold](content-safety.md#restricted-safety-cases-and-preservation-holds--source-foundation-local-only) is unreleased, a disclosure is requested or approved, or an evidence capture is unfinished. An isolated candidate's object verification must also find every stored, undisposed `restricted/safety-evidence/` object with its exact size and sha256. A restore must not roll held material or case records back.

The checker also refuses actual unresolved credential exchanges/revocation claims, unfinished key rotations, provider dispatch/uncertain states and applicable billing/inference reservations in the recovered rows, even if the independent stream has no newer event. Native CMS resources/import objects require their deferred recovery adapter and keep this candidate unavailable. No CMS/scanner functional test or access is introduced.

## Keys, objects and final readback

The operator supplies a process-local `keyBackup` capability returned by `verifyConnectionKeyBackup`, after reading/decrypting a private encrypted backup using its separately held recovery file and independently recorded digest. Plain keyrings and unknown input fields are rejected. The independent version-2 evidence response must pin that exact backup ID/digest/key list; a copied JSON verification report cannot replace the local capability. The checker reopens and decrypts the saved bytes, rather than using a cached original keyring. Its recovered active ID must match current policy, supplied ID/material fingerprints must match immutable registration, and all five token/PKCE/refresh stores must authenticate with the actual current vault primitive and owner/provider/purpose/record context. Missing/wrong/unknown keys and substitutions fail. An interrupted rotation cannot claim readiness; retaining an old current-format key permits authentication but does not settle its journal. No plaintext or old-format reader exists.

Each referenced project object must be present in the isolated private object source with exact byte length and SHA-256 digest. D1 restoration cannot supply an absent R2 body. This dependency check grants no serving, export or safety approval; those domain boundaries remain separate. Native CMS object dependencies are not handled by the project-object adapter.

After key/object checks, the tool rereads the database inventory and requests fresh evidence using another challenge. The pinned backup must remain unchanged in both independent responses. The encrypted backup and recovery file are read again before the final result; loss, replacement or new permission failures hold the candidate. Candidate changes or new/changed independent evidence hold the result. It never retries an external operation. Every result, including `status: verified`, carries `servingAllowed: false`, `providerDispatchAllowed: false` and `retirementAllowed: false`. Operational admission needs the broader restore/suppression/authority adapters and separately reviewed cutover. A successful local read is not a reusable activation token.

## Persistent operator inventory — October 2, 2026 UTC

`tools/restore-inventory.mjs` supplies the version-2 evidence interface from a **separate private SQLite file**, outside every repository checkout. It is not part of the application schema or its backups. The operator selects its current stream ID and file; opening a missing, mismatched, corrupt, replaced, linked or permissive file fails. It never creates a replacement inventory during a restore. The current operator-file schema is version 2; obsolete inventory files are refused and must be replaced through explicit test setup, with no old reader or migration. The evidence protocol remains version 2.

The inventory persists four kinds of metadata: its stream identity, permitted archive manifests with record identities/digests and encrypted-key-backup references, permanent archive withdrawals, and a cumulative constraint journal. File permissions are owner-only, SQLite commits use a rollback journal and full synchronization, and table updates/deletions are refused by SQL triggers. New archive registrations and observations compare the journal revision after asynchronous source reads; a competing write causes a refusal instead of silently overwriting it. The local in-process queue only orders that handle; SQLite transactions enforce writes across separate handles/processes.

### Operator workflow

Use Node 24 on the supported POSIX operator host. Create a private directory outside the repository and all Git worktrees. Example paths below are placeholders for **operator-selected storage**, not a claim that local disk is independent/offsite custody.

```sh
node tools/restore-inventory.mjs init /operator/inventory/current.whumpo-restore-inventory REVIEWED_STREAM_ID
node tools/restore-inventory.mjs inspect /operator/inventory/current.whumpo-restore-inventory REVIEWED_STREAM_ID
```

These commands return counts and status, not key material, owner identities, row bodies or local paths. Initialization is exclusive and will not overwrite an existing file, including an incomplete earlier initialization. The full trusted operator API is imported from the same module:

1. `openRestoreInventory({inventoryFile, expectedStreamId, authority})` selects the **current authoritative** source: a recovery source authority from `observeRecoveryAuthority({provider})` (`tools/recovery-authority.mjs`, [the drill](disaster-recovery.md#7-recovery-source-authority)), i.e. the database bound to the active platform Worker while apps and sites share that binding, with the exact current schema. It must not be the recovered candidate. A raw database adapter, a copied authority or the retired `sourceDb` option is refused. Every evidence request observes the authority again inside its ten-second deadline (before the first source read, before anything is committed, and after the verification read); a changed database, Worker version or schema, or a mixed binding, refuses it. These are bracketing observations, so a binding that moves and moves back between them is not detected, and a change landing after the observation before the commit but before the commit itself can leave one conservative event behind a refusal (it only adds holds; see the commit window in the drill). The authority's `account-client` / `injected-client` label records which client the caller wired; it is not remote-target attestation, and the source API client is trusted code. Omit `authority` for a read-only status handle; that handle cannot issue restore evidence. The stream is not bound to one database: use a distinct stream per authority database. No HTTP listener or customer route is provided.
2. `registerArchive({archiveDb, snapshotId, keyBackup})` reads the actual isolated current-schema archive, captures its complete manifest and every record's primary-key identity/SHA-256 digest from the same read transaction, freshly decrypts a branded stored-key-backup proof, and pins the exact manifest and backup metadata. The required manifest key IDs must be present in that backup. The archive adapter must differ from the authority's source database. Registration is explicit operator permission to **consider** those bytes; the restore checker still authenticates material and all constraints. Registration alone never passes recovery. Repeating the exact snapshot ID is idempotent; changed bytes or a different backup require a new ID. A withdrawn ID cannot be registered again.
3. `observe({operationId, selection})` reads an exact constraint from the configured current source. Supported selections are `{kind: 'owner-erased', ownerId}`, `{kind: 'identity-epoch', ownerId}`, `{kind: 'record', table, key}`, `{kind: 'publication-withdrawn', projectId, surface}` and `{kind: 'external-effect', store, effectId}`. Table names/complete primary keys and effect stores come from the current contract. Callers cannot supply a row body, digest, epoch, terminal result or approval boolean. A record read becomes its full row digest or an absence constraint; an external effect is reconciled only by its exact current terminal row. An existing OAuth exchange continues to mean unknown even when a terminal receipt has already been inserted. Missing effects cannot be invented as completed.
4. Keep each operation ID for reply-loss recovery. Repeating the same ID/selection returns its durable receipt; changing the selection under that ID fails. A repeated epoch under a new ID is rejected, because cumulative epoch evidence must advance. A later record suppression supersedes its earlier current-row digest; suppression itself is permanent for that identity.
5. `withdrawArchive({snapshotId})` writes a permanent tombstone, with idempotent readback. Evidence requests for it return unavailable. There is no delete/re-enable method.
6. Pass the handle's `evidenceSource` into `inspectIsolatedRestore`, together with the exact registered manifest and verified stored-key-backup capability. The inventory reads permission and events in one transaction, then compares the registered archive records and previously observed record identities against the configured current source. Missing rows become permanent suppressions; changed rows become exact current-digest constraints. The complete derived batch is appended atomically against the observed journal revision. It rereads the entire source and journal before returning challenge-bound evidence; drift, withdrawal, failed reads, unresolved current effects/rotations, expired observation, or missing source refuse evidence. The verifier performs this source-backed check again before returning its final isolated result. Repeated unchanged reads append no duplicate events. Call `close()` when finished.

### Authority and scope limits

The file contains restricted identifiers and selectors as well as hashes; it is **private operator metadata**, not a public report. It stores no complete application rows, credential values or recovery keys. `.whumpo-restore-inventory` files and their SQLite sidecars are rejected by source/build/release artifact checks. Keep the file, data archives, encrypted key backups and recovery material under separately reviewed custody. No real inventory or recovery material was created by implementation/testing.

This implements durable bounded operator recording plus **on-demand current-source comparison**. It catches changed/missing registered records even when no manual observation was sent. It conservatively compares complete rows, including mutable content: an older copy may remain held until a newly registered current copy is supplied. It does not repair a candidate or certify an arbitrary historical point-in-time restore. Current-source-only rows are not automatically added as constraints, with one fixed exception: the source-declared authority tables (`restoreAuthorityTables` in `tools/restore-inventory.mjs`, currently only `operator_containments`). Unresolved effects anywhere in the source refuse evidence, and both complete source reads must agree.

#### Authority-table derivation (WH-008, October 8, 2026 UTC; source and local SQLite evidence only)

An operator containment (project/account freeze or allowance) created **after** an archive is a current-source-only row. Before this change a candidate restored from the older point passed evidence with the stop silently missing. Now, on every evidence request, each current-source row of a declared authority table whose identity neither the archive's records nor any earlier event names becomes one `record-current` event (table, primary key `{id, scope}` and row digest only; no reason, operator or subject). The candidate lacks the row, so the verifier holds it as `stale-authority`. The protocol, verifier, hold codes, freshness windows and the three `false` activation booleans are unchanged; the held result grants nothing.

Conservative semantics, chosen on purpose:

- **Every retained row counts**, active, lifted or expired alike. A lift or expiry before the first evidence run therefore gives the same hold as one after it; the outcome cannot depend on when, or in which archive order, evidence was first requested. (An active-only rule was rejected: it would verify an old archive after a lift but hold it after a prior observation.) Expiry changes no column, so an expired stop still holds an archive that lacks it.
- **Deterministic and idempotent.** The derivation reads only the current source, so inspecting the old or the fresh archive first yields the same events and verdicts. Repeating a request appends nothing new. A later lift appends one event with the lifted digest (the archived row is also changed, so a containing archive holds too).
- **Fresh archive.** A point taken after the containment contains it. Unchanged, it verifies and adds no event; taken after a lift it verifies against the latest digest.
- **Removal.** This tree never deletes rows (`operator_containment_retained`); the tests delete only through a labelled FIXTURE-ONLY guard drop. An observed row that disappears becomes a permanent `record-suppressed` event (an archive that contained it holds `suppressed-record`; a candidate that never had it verifies once no other current stop remains). A row created and removed with no evidence run in between leaves no trace, so the older archive verifies; the end state is the same as for the observed row. That is historical knowledge held only where an evidence run observed it, not an inspection-order effect.
- **Bound.** Events are bounded at 512 across the stream. More relevant rows than fit (active or retained; the table itself allows 10,000) refuse evidence as `independent-evidence` for the archives that need them: all-or-none, nothing is truncated, dropped or partially appended, and the existing events are unchanged. A point taken after all those rows already contains them, needs no new event and still verifies. There is no purge or compaction; exhausting the 512 events needs a new reviewed stream (see the bounds above).
- **Source lost.** With no readable current source (no `authority`, or one whose database or binding no longer answers or settles) every archive holds `independent-evidence`. Containments created after the last successful evidence run and lost with that source cannot be known to this inventory; recorded events cover only what an evidence run already saw. Closing that needs an authority that survives control-database loss (WH-019).

`operator_session_revocations` and the like need nothing here: a revocation deletes sessions, which the existing `suppressed-record` path already holds. WH-050's `serving` scope lives in the same table on a separate, unmerged tree, so the derivation covers it by construction; that integration was **not** performed or run here. Add any other insert-only authority table to `restoreAuthorityTables` when it merges, together with a case in `tests/restore-inventory-containment.mjs`.

The current source must remain reachable and correctly selected. Its two read attempts share a ten-second observation deadline; cancellation or an adapter that never resolves refuses evidence without wedging the inventory handle. The resulting timestamp starts before the first source read, rather than restamping old data after a slow read. This is not continuous capture of every mutation, a provider reconciliation service, or an independent disaster-time authority when the source is lost. Operators still record external outcomes, epochs, erasures and publication constraints through the supported selectors. A failed observation never permits reuse of an earlier response; any complete batch already persisted remains conservative evidence. WH-008/018/019/059 still own continuous suppression-store integration, disaster-time freshness/coverage, external deletion/resource adapters and whole-platform drills. A current-source absence observation is not proof of account-wide erasure. The API cannot establish that the operator wired the correct source or that a same-user attacker has not replaced the authority after all handles close; independent operation and anti-rollback custody remain deployment requirements. Never restore this authority from the candidate's own backup.

The current bounded interface holds at 256 registered archives, 512 cumulative observations or the evidence/file size bounds. Withdrawals retain their references; there is no purge, compaction, TTL expiry or empty-history replacement to evade those bounds. Reaching them needs a reviewed next current contract and reconciliation before operational admission. All successful checks still keep serving, provider dispatch and key retirement disabled. Physical/offsite key custody, genuinely lost provider outcomes, full GitHub grant reconciliation and child D deployment remain open. Returned refresh credentials and known reviewed grant outcomes have the source/local coverage below.
