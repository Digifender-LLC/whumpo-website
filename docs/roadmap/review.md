# Whumpo baseline review

**Historical review.** The October 1 [alignment](alignment.md), current feature contracts and linked live issues supersede its original execution queue, Stripe deferral and unfinished-compiler assumptions. Preserve the dated evidence below; it is not a current deployment or completion summary.

Reviewed September 30, 2026 against source commit `05443262a88b658c8d72460a75b28facacabec4f` and the repository evidence available at that point. This is a product and implementation review, not a fresh live-environment audit, security scan, accessibility certification or completion declaration. No customer data, credentials, provider settings or public content were changed for this review.

Whumpo has a substantial private-test foundation: a recoverable Chat workspace, conservative publication controls, usable static-site workflows, private content tooling and a separate bounded application runtime. Its main delivery problem is converting those foundations into a small number of dependable customer outcomes. Adding more Cloudflare capabilities before resolving activation, safety, recovery and real-device acceptance would increase the support surface faster than the proven customer value.

The recommended first outcome is a US-eligible invited owner creating, editing, publishing and maintaining a simple business website. CMS publishing and small invitation-only tools are credible subsequent tracks, each with their own readiness gate. This sequencing does not remove requirements from the existing [MVP contract](../mvp.md), authorize spending or override the owner's deferred CMS testing and Stripe decisions.

## Strengths worth preserving

- The architecture separates the control platform, public sites, visitor application host and QuickJS runtime. Private R2, tenant ownership and scoped visitor state are explicit boundaries.
- Drafts and source versions are immutable. Publication, restore, application authority, DNS and destructive operations use separate review and confirmation paths. Server receipts establish outcomes rather than model prose.
- Retries, lost acknowledgments, stale revisions and concurrency receive unusually detailed D1/HTTP/runtime coverage. These are useful reusable patterns for future agents.
- Guided navigation and ordinary deterministic reads avoid model use. Project-first welcome saves checkpoints, keeps optional profile context out of inference unless shared, and hands the saved brief into a scoped first-draft request.
- There are connected website, application and CMS journeys in disposable environments, plus selected real Muse probes. These are a sound starting point for a repeatable release acceptance suite.
- Source ZIPs, retained versions, directory snapshots, CMS article downloads and visitor exports provide concrete portability foundations, while their limits are generally documented.

## Gaps that matter most to customers

**Safety is a release dependency and a usability dependency.** The new fail-closed photo/import holds are appropriate foundations, but uploaded images cannot become useful merely by adding more UI. The scan-results service has no dispatcher/provider adapter. CMS images and generated-source/content coverage have separate gaps. Complete the scoped detection, result authentication, retry/expiry, restricted handling and appeal/reporting operations in [content safety](../content-safety.md), or keep those capabilities clearly unavailable. Do not publish private objects to obtain scanning or let a general building agent approve held material.

**Prove the complete first-use journey on actual devices.** Current evidence is strongest at handler/runtime and synthetic browser levels. Run invitation → human challenge → native passkey → welcome → useful draft → edit → exact review → publication → visitor outcome → recovery with explicitly approved fixtures. Include a lost response, interrupted session and second-device recovery. A 390px screenshot alone does not establish touch targets, virtual-keyboard behavior or passkey dialogs.

**Evaluate useful output, not only valid actions.** The static assembler is deliberately constrained to `launch-page@1`, `site-page@1` and `photo-page@1`; richer brief wording does not create arbitrary design capability. The controlled application form also does not establish that generated fields match the backend's input contract. Build a small maintained scenario set with expected customer outcomes, preserved-edit requirements, clarification cases and unsupported-request handling. Record human quality judgments alongside server correctness, replay safety, latency and provider cost.

**Close reliability and accessibility gaps across the workspace.** Source review found a transient Chat draft/request held in React state/ref, a dashboard loading branch that does not receive its query error, and no transcript `role="log"` or comparable new-message announcement in [workspace.tsx](../../frontend/src/workspace.tsx). These are candidates for targeted investigation, not findings from a fresh interactive test. Existing labeled inputs, Radix dialogs, focus handling in welcome and mobile layouts are useful foundations. Establish keyboard, screen-reader, zoom, contrast, reduced-motion and real-device checks across auth, Chat, review dialogs, publishing and visitor forms; address measured failures without weakening confirmations.

**Make ongoing operation understandable.** A customer needs to know what is live, what is held, what failed, what needs their review and what to do next. CMS and application unfinished-work inventories exist; extend a consistent account/project status model across uploads, provider operations, website publication and support. Keep the intended Chat-first interaction and explicitly requested workflow shortcuts. Publication health currently covers a fixed shared site address, not custom domains, forms, visitor apps or CMS end-to-end availability; label those differences accurately.

**Provide exit, retention and recovery as coherent journeys.** Resource-specific snapshots and exports are not an account export, portable backend bundle or disaster-recovery plan. Customer account/project deletion is not implemented. Several immutable receipt families have lifetime/private-test ceilings. Define retention with deletion tombstones, unresolved-operation handling, legal preservation boundaries and external-resource reconciliation before routine usage reaches those ceilings. Test restore against deleted/revoked visitors so recovery cannot reintroduce erased data.

**Choose a narrow expansion order.** Business-site improvements with direct value include contact/inquiry follow-through, appropriate calls to action, metadata/social previews, approved imagery, custom domains and a small layout catalogue. CMS migration should preserve customer URLs, content and media with explicit exception reporting before promising broad WordPress compatibility. Richer applications should start with validated use cases built on reviewed components, then expand input/presentation/data contracts. None requires turning the control Worker into a general code executor.

**Publish truthful availability and support information.** The landing page qualifies the product as an invite-only preview and names deferred payments/domains. Its CMS and application promises still need to match a discoverable capability status inside the product. Policy/help/abuse/support entry points, contributor-model disclosure and practical limit explanations should be reachable during signup and after a failure. Usage-review support currently shares Chat/onboarding limits and has no configured operator notifications or service commitment; it cannot be the sole future appeal channel.

## Recommended success measures

These are proposed measurements, not claimed baselines or launch targets. Collect only necessary metadata; do not send customer prompts, visitor messages, credentials or private content to analytics. Set numeric thresholds after an initial baseline and owner review.

| Measure | Definition and decision it informs |
| --- | --- |
| First useful outcome | Invited eligible owners reaching a reviewed, usable private draft; elapsed time, abandonment stage and human-rated fit. Reveals whether welcome and first generation solve a real problem. |
| Publish and maintenance success | End-to-end website tasks completed without operator rescue; successful follow-up edit/restore, correct contact/directory state and verified destination availability. |
| Model task quality | Completion, clarification, unsupported-request honesty, preservation of unrequested content and generated-form/backend compatibility across a fixed scenario set. Segment by model/version and component. |
| Reliability | p50/p95 action latency; failed/uncertain request frequency and time to resolution; duplicate dispatch/mutation and stale-review escape counts. |
| Device/accessibility acceptance | Named browser/device/assistive-technology journey passes, plus unresolved severity and regression evidence. Keep simulated viewport checks separate from physical-device runs. |
| Media readiness | Time in quarantine; scanner availability/inconclusive/expiry rates; false-positive corrections; exact coverage by upload route. Approval rate alone is not a safety-quality metric. |
| Retained customer value | Owners returning to make a meaningful site/content/tool improvement, measured over a defined cohort/window; successful inquiries where measurable without reading message bodies. |
| Support and recovery | Time to first response/resolution, cases requiring operator intervention, successful recovery drills and blocked access to help. |
| Economics and capacity | Verified per-operation provider/infrastructure cost, component reuse, premium reconciliation and capacity headroom. Unknown finance remains unknown; metrics do not authorize enforcement or spending. |
