# Low-friction identity and data protection

**Owner-approved direction, October 1, 2026; implementation, activation and customer acceptance remain planned.** WH-113–118 were added against `628c16f`; the October 1 alignment reconciles them with source `2207186` and current recorded recovery evidence. This contract governs workspace owners and future workspace members. Customer-application visitor identity keeps its separate [application contract](../app-data.md).

The WH-113 [shared workspace identity protocol](../workspace-identity.md) now freezes restricted grants, signup/recovery state, kit rotation, partial loss, transport authority and compatible cutover/rollback against `d415398`. This completes the decision deliverable; WH-114/115 implementation and device/live acceptance remain open.

## Product principle and current evidence

Prefer low user friction with strong default protection across Whumpo. Automate protections when possible, ask only for necessary information, preserve ordinary authenticated sessions and explain unfamiliar choices on demand. Extra prompts must protect a concrete boundary. This principle preserves tenant isolation, private R2, content-safety controls, recent authentication for sensitive changes and exact human reviews for publication, activation, provider mutations and spending. Authentication, recovery and support stay reachable without AI.

Current source supports passkeys with required user verification, optional passwords, recovery codes and revocable sessions. Passkey signup needs one passkey; the existing recovery flow issues a normal session. These are implemented behaviors, not acceptance of the new policy. Preserve the historical evidence in [owner recovery](../owner-recovery.md), [onboarding](../onboarding.md) and [MVP](../mvp.md). Source entry points are `src/passkeys.ts`, the authentication/session handlers in `src/index.ts`, and `frontend/src/auth.tsx`.

Current data protection includes private storage and tenant checks, plus server-managed AES-GCM encryption for integration credentials in `src/connection-vault.ts`. Cloudflare documents automatic encryption at rest under Cloudflare-managed keys for [D1](https://developers.cloudflare.com/d1/reference/data-security/) and [R2](https://developers.cloudflare.com/r2/reference/data-security/), checked October 1, 2026. Authorized server code can still read this data. Whumpo has no implemented passkey-based content encryption, and this amendment makes no end-to-end encryption claim.

## Workspace signup, sign-in and maintenance

After activation, every ordinary workspace sign-in uses a verified passkey. Disable password signup, login and password creation in backend routes as well as the UI. Do not introduce email links, SMS or social-login substitutes. Recovery is the explicit restricted exception described below. Device PINs or biometrics can unlock a passkey; Whumpo verifies the resulting proof and does not receive those local unlock secrets. See [WebAuthn user verification](https://web.dev/articles/webauthn-user-verification).

Signup requires **two distinct verified passkey credentials** before workspace access. A repeated credential does not count twice. Recommend independent storage, such as another passkey provider or a security key, without requiring a purchase or attestation of independence. Two credential IDs do not prove independent backups; synchronized copies of one credential still count as one. Test actual provider behavior instead of assuming that a second registration on the same provider is available.

Show short progress for first passkey, backup passkey and recovery-kit save. Preserve completed enrollment when a user cancels the second prompt, changes devices, loses a response or closes the browser. A restricted setup flow may resume enrollment and reach help/sign-out; it cannot expose workspace data, AI, project operations, provider connections or a normal native-session exchange. Enforce this on the server, independently of welcome completion and UI routing. Invitation, eligibility, Turnstile, ownership and replay protections remain intact.

Use optional expandable explanations: what a passkey is, how the device unlocks it, why two are needed, and how synchronized credentials share a provider failure/recovery dependency. Give actionable unsupported-device/provider guidance and preserve progress. Signup remains incomplete if the user cannot supply a second distinct credential; do not silently waive the requirement or prescribe a hardware purchase. Record this usability limitation in the supported-device matrix.

Ordinary valid sessions continue without repeated passkey prompts. Credential changes use the existing sensitive-action authentication boundary. Never block emergency revocation of a compromised key solely to maintain two keys; prompt for a replacement afterward. If no usable credential remains, use restricted recovery. The two-key completion requirement applies to signup and lost-all-keys recovery, not a reason to keep a compromised key active.

Before disabling legacy access, use a staged existing-account transition. Identify password-only and single-passkey accounts through content-free counts, provide resumable setup while current authorized access remains available, and verify replacement access plus the saved recovery kit before retiring legacy credentials. Follow the [frozen transition, pending-account/session and rollback rules](../workspace-identity.md#existing-account-rollout-and-rollback). Cutover must not strand an existing account, silently grandfather password login after activation, or make a retired credential authoritative again. The controlled visitor host is unaffected.

## Downloadable recovery kit and restricted recovery

Offer a high-entropy recovery key as a downloadable plain-text file, with an accessible copy alternative and a printer-friendly view supporting **Print / Save as PDF**. Use browser printing rather than a remote document service. Encourage printing and keeping the kit somewhere safe and independent of the primary device/provider. Require one acknowledgment that it has been saved; do not require a printer, a mandatory PDF workflow, proof of printing or an extra memory-based secret.

The kit identifies Whumpo and the account, records its generation date, gives the manually entered recovery address and concise instructions, and explains that possession can authorize account recovery. It must contain no password, passkey private key, provider token or customer content. Do not put recovery secrets in URLs, QR links, filenames, persistent browser application storage, AI, logs, analytics, screenshots or test evidence. Downloads/printing are explicit local user actions; explain safe handling of the resulting file or paper. Use only synthetic kit values for visual acceptance.

Store only an appropriate verifier for the account recovery key. Preserve the existing rate limits, same-origin boundary and generic rejection behavior. A successful recovery-key check grants a bounded, short-lived replacement-enrollment authority, **never a normal workspace session**. When all passkeys are lost, require two verified replacement passkeys and a saved replacement recovery kit before workspace access. Verify a fresh replacement-passkey assertion before issuing the ordinary session. Browser/native handoffs cannot upgrade incomplete recovery into workspace access.

Preserve review of which old credentials are lost/compromised, revoke prior sessions and affected credentials, and rotate the recovery key with transactional, concurrent-attempt protection. A user who still has a usable passkey can sign in normally and replace a lost key. For recovery-key use, the [partial-loss protocol](../workspace-identity.md#recovery-after-losing-passkeys) requires a new replacement plus a retained credential and fresh replacement assertion; it never restores direct-to-workspace recovery-code login. Keep save-before-rotation: the replacement kit must be available before its secret becomes the only valid recovery key. Interrupted replies, competing attempts, stale selections and abandoned enrollment must resume safely without duplicate credentials or revived sessions.

Recovery-kit replacement/rotation needs the same careful save and lost-response behavior. An old kit must stop working after rotation; historical screenshots or downloads cannot become a second valid recovery route. Broader suspected-compromise handling includes integration-grant review under WH-063 and incident work. Email address knowledge or a support conversation never substitutes for the established recovery proof.

**Account recovery and encrypted-content recovery are separate.** Registering replacement passkeys does not recreate an encryption key from lost credentials. The initial kit recovers account access and must not promise more. Any future client-side encryption must separately design and verify content-key backup, additional-passkey access and recovery before adoption; do not reuse a server-presented recovery secret as a supposedly server-inaccessible content key.

## Protection that fits the product

WH-116 maps each data class to its purpose, readers/processors, storage and transit protection, key custody, retention, backup/export/deletion behavior and recovery failure modes. Build on WH-009 and production inference privacy work, rather than inventing a parallel lifecycle inventory. Keep these distinctions explicit:

| Protection | Whumpo use and limitation | Delivery/status |
| --- | --- | --- |
| Cloudflare-managed encryption at rest and protected transport | Infrastructure protection for D1/R2; it does not prevent authorized platform processing. | Existing provider capability; WH-116 records the actual application paths and gaps. |
| Server-managed application encryption | Credentials and justified sensitive fields can receive additional protection without customer unlock prompts. The authorized service can decrypt them. | Existing connection vault; WH-117 extends only where the classification justifies it. |
| Client-side, passkey-backed encryption | Could protect selected private content from server reads while locked. Compatibility, recovery and processing limitations must be demonstrated. | WH-118 feasibility only; no default vault, mandatory unlock flow or customer promise is approved. |
| Complementary controls | Least privilege, scoped access, tenant checks, short-lived credentials, minimized retention, redacted diagnostics and safe exports reduce exposure where processing needs readable data. | Reuse current boundaries; WH-117 closes identified gaps and verifies them. |

Private files, drafts, chat history, visitor records, provider credentials, operational metadata and public artifacts have different requirements. AI needs selected readable context; publication produces visitor-readable output; current safety, search, image processing, application execution and background integrations need access to their inputs. Document that access and minimize it. Do not claim data stays unreadable to Whumpo or an inference provider after supplying it for processing. Encryption does not replace safety gates or permit confidential content in the contributor/training-enabled test model.

WH-117 uses authenticated encryption and maintained primitives where an additional layer is justified, with tenant/purpose binding, versioned keys, authorized decryption, safe rotation and recovery. Plan existing-data migration, failure readback, backup-key custody and restore/delete reconciliation before enabling changes. Never erase the only working key during migration, mix tenant ciphertexts, or fall back to plaintext after a cryptographic failure. Distinguish expiry/deletion of live keys and data from retained backups; do not promise immediate cryptographic erasure without evidence. Where existing controls are sufficient, record the rationale rather than adding encryption without a threat or usability benefit.

WH-118 evaluates the [WebAuthn PRF extension](https://www.w3.org/TR/webauthn-3/#prf-extension), checked October 1, 2026. Ordinary passkey authentication does not supply a content-encryption key. A possible design uses random data keys protected separately for each authorized passkey; client-only PRF results must not be serialized into authentication requests sent to the server. This remains a candidate to test, not an approved implementation.

The feasibility result must cover supported browsers/devices/providers and native-browser handoffs, normal-sign-in unlock, extra-passkey enrollment, provider sync/restore, lost-all-keys content recovery, revocation/rotation and export. Measure extra prompts, time, failure and abandonment without recording secrets/content. Require reliable recovery and no recurring unlock burden, and explain the limits of compromised clients, delivered application code and previously disclosed data. If these criteria fail, retain the transparent protection baseline and record the limitation; do not silently weaken encryption or gate beta on PRF support. Any adoption requires a separately specified implementation packet and an honest processing/privacy contract.
