# Shared code library without shared customer data

Current planning interface: the [versioned capability planner](capability-planner.md) selects supported configuration and shared helpers before custom source. Its library application handoff records pinned provenance and uses the existing synthetic-check/review lifecycle. Historical slash-command examples below are internal adapters; customer Chat uses natural language.

## Decision

TellUmo should assemble the first site from reviewed, versioned components before asking a model to generate new code. A sign-in flow, contact form or pricing page should normally select an existing component and fill validated configuration. AI handles layout composition, requirements that are not covered, and later customization.

The shared library contains code and synthetic examples. Customer prompts, generated sites, uploads, business content, credentials, database rows and chat history stay in the customer's workspace. There is no cross-tenant similarity search over those artifacts.

## Sources and promotion

Start with platform-authored components, appropriate licensed upstream code, and reviewed ports from owner-authorized projects such as Jarvis. Check license and provenance per component. A customer adaptation stays private by default. Explicit owner consent is required to nominate it for reuse; consent alone does not publish it.

Promotion creates a separate candidate from a synthetic specification, removes customer configuration and identifiers, and requires human code review plus automated secret scanning, dependency/license checks, and security/behavior tests. Pattern matching is insufficient to prove absence of sensitive data. Do not automatically promote generated code based on its popularity, a successful test, or a model's claim that it is generic. Opaque assets and copied data fixtures are excluded.

## Package contract

Each immutable version records:

- Stable component ID, version, artifact digest, source provenance and license.
- Supported runtime/schema versions, dependencies and migration requirements.
- Explicit capabilities: storage, outgoing network, authentication and required secret bindings.
- A schema for non-secret configuration and synthetic test fixtures.
- Verification evidence, reviewer, publication state and replacement/security notices.

Only catalog maintainers publish versions. Customer agents can read approved components and propose private changes, but cannot change the shared catalog. The planner supplies component IDs and validated parameters; a trusted assembler resolves exact versions. Model-provided download URLs, shell install commands and executable parameter strings are not accepted as component references.

## Tenant boundary

An instance belongs to one project and one owner. Configuration, databases, bindings and runtime state are created per instance/tenant. Authentication reads the verified session owner; it never trusts an owner ID generated by a model. Secrets are binding references resolved at runtime, never code substitutions, catalog fields, prompts or build output.

For sign-in, reuse the reviewed authentication implementation and customize a constrained presentation layer. AI styling changes must not alter session validation, cookie settings, password/passkey verification or access checks. Security-sensitive changes require a separately reviewed component version. Sharing code does not imply sharing accounts, sessions or databases.

Store private customizations as a project-owned patch against a pinned base version. Updates are explicit, previewed, tested and reversible. A withdrawn version blocks new installs; existing affected projects receive an update notice and a tested migration path. Do not silently rewrite deployed customer code.

## Retrieval and caching

Catalog retrieval searches only public-to-all-testers metadata and synthetic examples: capabilities, stack and layout style. Cache shared package bytes by immutable digest. Keep customer prompts, completed sites, tool results and filled configuration out of shared caches. Private caches must include owner/project boundaries and respect deletion. Never use a global prompt/response cache for customer requests.

## First implementation slice

1. Extract the existing sign-in presentation and reviewed authentication contract into a platform component, plus static landing, FAQ, pricing and contact layouts.
2. Add an immutable catalog manifest and trusted assembler with a narrow configuration schema.
3. Generate a preview from components with zero model calls when requirements match; show the selected components and allow changes in chat.
4. Use AI only for unsupported requirements or requested private customization.
5. Record component versions in each site version so publishing and restore reproduce the same artifact.

Acceptance tests must verify: two customers using the same component cannot read each other's configuration or data; catalogs and bundles contain no tenant data; hostile configuration cannot inject code; unapproved versions cannot execute; restoring a site restores its exact component versions; authentication remains correct after allowed appearance changes.

## Measuring savings

Track component hit rate, model calls avoided, tokens used per first preview, customization rate and defects. Compare equivalent requests against generation from scratch. Do not promise a percentage reduction until measured. Maintenance and security updates are a shared cost; user-specific model work remains metered normally.

It generates private immutable previews from a project brief without inference. The broader library, authentication components, promotion pipeline, AI customizations and customer-site runtime remain unfinished.

Customer configuration is supplied privately to the assembler and stored only with the owned version. No generated customer material is promoted into the shared catalog. The model selects an allowlisted component contract; it cannot supply executable backend or sign-in code.

Focused edits reference an owned immutable base and send only changed configuration fields. Trusted assembly preserves omitted fields and records base ancestry. ## First dynamic shared implementation

`src/contacts.ts` and `src/contact-page.ts` implement one trusted contact backend used across projects. Shared code contains no customer prompts, site content, messages or credentials. Tenant settings and messages live in project-scoped D1 tables, with server-derived ownership for private reads/deletion and publication checks for public intake. The agent may prepare a settings review, never authorize activation or read visitor messages. Runtime form settings are separate from immutable static artifacts and are not claimed as portable backend exports. See `docs/contact-forms.md` for the full contract and tests.

## Directory CRUD backend

`src/directory.ts` and `src/directory-page.ts` add a second platform-authored dynamic implementation: private listing CRUD with separately reviewed public HTML/JSON snapshots. This demonstrates reusable backend behavior without generating a new backend for every customer. See [directory service](directories.md) for limits and remaining portability/rollback work.

Two platform-authored, MIT-designated source artifacts are available: `line-total@1` and `text-statistics@1`. `/backend-library` lists available references, `/backend-component NAME@VERSION` reads source, digest and a synthetic expected-output check, and `/use-backend PROJECT_ID NAME@VERSION` copies one exact artifact into an owned immutable private backend version. These guided commands perform no inference. Natural-language tools can list/read/copy the same allowlist; read-only library inspection can use the existing bounded model continuation. Copying never executes code or grants publication/application authority. Each project copy still needs its own successful test and normal publication review.

Artifact SHA-256 values are pinned alongside versioned source and verified before use. One atomic D1 batch saves the backend version and immutable provenance association. Replay checks the exact project, component version and digest; a lost commit response reads back the matching receipt. The association is visible when reading the private backend source, cannot be altered or removed while its backend version exists, and follows normal project/version deletion. Identical shared code receives distinct tenant-owned version records. Private customization creates a separate version; it does not change the original or acquire a false catalog provenance record.

Only repository maintainers change the catalog; customers/models cannot supply source URLs, install commands, replacement source or executable configuration through this interface. New copies require an available version; withdrawn versions can only recover an already recorded exact copy. Existing code is never silently replaced. Sign-in reuse remains the existing platform authentication implementation, not a generated authentication helper.

## Private reuse nominations — September 30, 2026

Implemented and deployed in test: migration `0093_backend_nominations.sql` and guided Chat commands let an owner nominate an exact saved backend version for maintainer review. This records permission to inspect; it is neither a publication license nor approval to share customer source. The nomination references the owned immutable version and its verified SHA-256 digest. It stores no second copy of source, customer inputs, secrets or configuration. No model action can nominate code.

- `/nominate-backend VERSION_ID` prepares a ten-minute review, including the exact source-read command, digest, permission terms, exclusions and cancellation command.
- `/confirm-backend-nomination NOMINATION_ID NOMINATE` records explicit consent for that review. Expired or withdrawn reviews cannot be confirmed. A confirmation replay cannot revive withdrawn permission.
- `/backend-nomination NOMINATION_ID` reads current status; `/backend-nominations` lists the owner's retained records.
- `/withdraw-backend-nomination NOMINATION_ID` withdraws a pending review or recorded consent. The version itself stays unchanged. Withdrawal is terminal and repeatable.

The database enforces ownership/digest binding, immutable identity, allowed transitions, at most five open reviews/consents and twenty retained records per owner. Expired reviews no longer occupy an open slot but remain in the retained-record count. These are private-test safeguards, not paid-plan entitlements. Project/version or account deletion cascades the corresponding records. The twenty-record bound is not a lifetime account counter; deletion removes associated records.

Exact guided request replay returns its saved Chat response; request a fresh status read for current state. Lost write acknowledgments recover only the same owner/version record or confirmed terminal state. They do not create another nomination or authorize another action. Extra list arguments are refused. No AI call, backend execution, publication, catalog install or customer unit debit is part of this flow.

Maintainer intake with consent and integrity rechecks is implemented below. Remaining before customer-code reuse: separate synthetic candidate creation, privacy/secret and licensing checks, human review, approved license/provenance, tested immutable publication, withdrawal handling during review and security update notices. The existing catalog remains platform-authored. There is no background reviewer, cross-customer retrieval, source harvesting or automatic promotion. Do not describe nomination as completed screening or available sharing.

### Operator intake inventory and integrity check

`node tools/review-backend-nominations.mjs` lists up to 50 currently consented nominations. Use `--after NOMINATION_ID` with the returned cursor for the next page, or `--inspect NOMINATION_ID` to verify one exact saved source digest privately. This uses the operator's existing Cloudflare authorization and performs no database writes. Keep output private; nomination/version IDs and digests are review metadata, not public catalog entries. No customer endpoint or model tool exposes this operation.

Listing reads only metadata, joins the current project owner and version digest, and excludes pending or withdrawn consent. Inspection repeats those checks, reads at most the existing 8 KiB source limit, hashes source in process, and rechecks current consent afterward. Neither operation prints source, account identity, prompts or business content. A changed/withdrawn/deleted nomination fails inspection. A successful hash comparison establishes integrity at that read, not privacy, licensing, safety or permission to share. The result explicitly lists the remaining human, synthetic-candidate, screening, testing and publication gates.

UUID pagination has no cross-page snapshot guarantee: new records sorting before a cursor appear on a fresh traversal. Recheck consent before every downstream action. This inventory does not implement human source review, review decisions, promotion or a reusable authorization token. A withdrawal after the final read remains possible and must invalidate any later promotion decision; no promotion consumer exists yet.
