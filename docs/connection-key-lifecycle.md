## One current keyring and envelope

`CONNECTION_ENCRYPTION_KEYRING` is the only current configuration binding. It contains bounded JSON with exactly `version: 2`, `active` and `keys`. Each of one to four entries has exactly `id` and `secret`. IDs match `[a-z][a-z0-9-]{0,31}`. Secret material is 32 random bytes encoded as 64 lowercase hex characters. Both IDs and material must be distinct; `active` must name a present entry. Invalid, oversized or unsupported configuration disables provider configuration; the former bare-key binding is not read.

Every new encrypted value has four dot-separated fields:

```
wv2.KEY_ID.BASE64URL_12_BYTE_IV.BASE64URL_CIPHERTEXT_AND_TAG
```

The IV is randomly generated for each write. Web Crypto AES-256-GCM uses a 128-bit authentication tag and a non-extractable imported key. The authenticated data includes the current format, exact key ID and the caller's `whumpo:PROVIDER:PURPOSE:OWNER:RECORD` context. Only GitHub/Cloudflare and token/PKCE purposes are admitted; bounded owner/record identifiers cannot introduce separator ambiguity. All providers use this one primitive.

Plaintext is a nonempty, well-formed UTF-8 string of at most 8,192 bytes. Canonical unpadded base64url, exact IV/tag/byte bounds, the current envelope marker and strict key identity are required on reads. Decryption looks up precisely that ID; it never tries other keys or old formats. Relabelling ciphertext to another key ID fails authentication even if separately supplied material is identical. A changed owner/provider/purpose/record fails too. The old `v1` envelope and old context namespace are rejected; no reader, conversion or plaintext fallback remains.

`connectionKeyringMetadata` returns only version, active ID and retained IDs. `connectionCiphertextKeyId` validates an envelope's structure, but does not authenticate its body or grant rotation/restore authority. Neither helper proves that key material matches a historical key or that deployment/account custody is correct. The immutable registration/write-policy implementation below binds key IDs to material; retirement still requires independent custody evidence.

## Existing provider lifecycle integration

GitHub and Cloudflare read only the new keyring binding. Token and PKCE writes use its active key, including GitHub staging and Cloudflare retained revocation work. Pending PKCE encrypted with a retained key remains readable by the exact callback; any resulting token is sealed with the configured active key. These are current-format key instances, not compatibility paths.

Unknown/missing keys, malformed envelopes and authentication failures stop decryption. Direct HTTP reads return a bounded 503 response explaining that platform recovery is required; callbacks use the existing failed-authorization redirect without exposing cryptographic details. These known failures do not enter the generic exception logger. No provider request may be sent using an unavailable credential.

Disconnect still removes local use authority immediately. If cleanup cannot decrypt, it retains the encrypted revocation obligation and current lease rather than claiming the provider token was revoked. A later admitted cleanup with the exact key can complete the existing token revocation. Account recovery does not reconstruct a lost platform key. Provider expiration, configuration presence and a successful JSON parse are not proof of remote revocation or safe key retirement.

## Reviewed current-key storage operations

`src/connection-rotation.ts` supplies platform-maintenance functions, with no customer HTTP/Chat tool or automatic startup initialization. Workspace-scoped databases are rejected. Review, rotation and batch IDs are bounded identifiers; review references are operator records, not customer approval. `initializeConnectionKeys` admits an empty current database explicitly. `registerConnectionKeys` records only an immutable ID/material fingerprint and review reference. IDs cannot be rebound, material cannot be registered under a second ID, and registry deletion is blocked pending custody proof. No key material is stored in D1.

`beginConnectionRotation` binds the expected policy revision, target key and review to one durable rotation ID. Registration alone does not change writes. Activation and the journal commit together; repeated/lost replies read the exact existing result. A key identity can be activated only once, so returning to an earlier ID cannot readmit stale Workers. The supplied current keyring must retain the previous active key. One rotation is running at a time.

Token/PKCE insertion and ciphertext replacement check the active key in SQL at commit. Runtime writes additionally verify the material fingerprint against the immutable registry. New OAuth flows use this admission; callbacks acquire an exact exchange record before requesting a provider token. Active-key changes are refused while any exchange remains unsettled. A response that arrives after disconnect/sign-out can still be encrypted for cleanup under its admitted key. Saving the encrypted token and releasing that key hold is one transaction. A lost save acknowledgment reads immutable token identity/expiry, so intervening legitimate ciphertext rotation cannot cause an already saved token to be revoked accidentally.

An unreadable, redirected, failed or lost token response may have an unknown outcome. Its exchange record has no automatic TTL and survives flow deletion/disconnect. Another consent attempt for that owner/provider is refused; it never retries a possibly completed provider exchange automatically. The operator maintenance report counts unresolved exchanges and flags those older than ten minutes. This age is an attention threshold, not permission to forget an issued token. Child C must supply independent outcome/custody reconciliation; no self-service or automatic repair is claimed here.

`rotateConnectionBatch` reads at most 20 current records from the four fixed stores. Each replacement authenticates the exact owner/provider/purpose/record with the retained source key, then encrypts under the registered target. An atomic batch inserts a receipt and transient ciphertext-only guard, matches every snapshotted record column (including state/expiry/claim/cancellation/revocation lease), changes only ciphertext, counts successful replacements and removes the guards. An interrupted transaction leaves neither partial replacements nor guards. Cloudflare/GitHub token identity and expiry remain immutable. A concurrent deletion, newer authorization, disconnect or revocation causes that snapshot to be skipped; it cannot resurrect or regress the record. Existing staging and revocation claims are preserved.

The journal's exact batch ID resolves duplicate/lost acknowledgments. No cursor advances past an unprocessed stale-key record; each bounded continuation selects remaining records again. A later rotation fences stale batches at the same storage boundary. Completion requires zero remaining records under other keys; it does not authorize deletion of any retained key. Receipts report only IDs, counts, byte totals and measured crypto elapsed time. They contain no owner, credential, plaintext, ciphertext or fingerprint. Transient guards contain ciphertext and owner identity only for their transaction.

## Retirement and candidate boundary

`connectionKeyRetirementStatus` reports live references, unsettled exchanges and active-key status without exposing record contents. `retirementAllowed` remains false, and deleting a registered identity is rejected even with zero live references. Every permitted backup/restore source and independent deletion/revocation record must be reconciled by child C before a retirement path is admitted. Data archives cannot reconstruct Worker secrets. An unknown provider outcome remains unresolved after a database restore, rather than inheriting an old activation claim.

The current schema contains seven additional tables (163 total), including the exact OAuth outcome receipts below. Fixtures initialize the whole schema and explicit synthetic policy. There is no migration, old reader or automatic key bootstrap. Child D must review the exact current test database/key custody, initialize the current target and deploy matching bindings together. This source has not changed deployed keys, the database, provider consent or Cloudflare spend.

### Measured local overhead

A synthetic four-record rotation retained **432 encrypted bytes before and after**, with equal-length source/target IDs. Its two-record PKCE completion batch issued **17 SQL statements**, with local D1 reporting **61 rows read / 13 rows written**, including journal/guard/trigger work. The runner measurement includes local proxy/serialization work; it is not Cloudflare Worker billed CPU, excludes the separate D1 process, and must not be converted into provider cost. Child D retains deployed resource/CPU and current headroom acceptance. SQLite lacks D1 row-cost metadata and is labelled accordingly by the test. No new service or paid upgrade is selected.

## Exact OAuth outcome custody — October 2, 2026 UTC

The current exchange record now pins the configured OAuth client ID in addition to owner, provider, state hash, token ID, key ID and policy revision. Its matching terminal `connection_oauth_outcomes` receipt records only these identities, the dispatch/settlement times, a bounded reason, state and HTTP status. No provider body, error description/URL, authorization code, access token or client secret enters the receipt. The new table is classified with owner connection metadata (163 current tables total); account-closure inventory counts it separately from unresolved dispatches.

`src/connection-oauth-response.ts` reads the direct response from the one admitted token dispatch, with a 16 KiB bound, strict UTF-8/JSON and a ten-second body deadline. Confirmed GitHub token-endpoint errors are restricted to the documented four reasons on HTTP 200/400. Cloudflare accepts the six RFC 6749 token errors on HTTP 400, plus `invalid_client` on HTTP 401. A denial permits only `error`, `error_description` and `error_uri` string fields. Unknown fields, duplicate/escaped duplicate names, mixed token/error bodies, unknown reasons, redirects, unsupported statuses, oversized/malformed/stalled bodies and transport loss retain the hold. The provider response is never retried to manufacture a rejection for an earlier unknown attempt.

A direct rejection saves an immutable terminal receipt, releases that exact hold and removes only its matching OAuth flow in one D1 transaction. This restricted custody can finish after sign-out; it cannot activate credentials or confer workspace access. Lost commit acknowledgments read back the exact receipt. Failed/rolled-back persistence retains the hold. Successful encrypted vault custody remains the other permitted hold release; SQL rejects deleting an unresolved exchange with neither matching custody nor outcome receipt.

When encrypted token saving fails, an authenticated successful direct revocation can record `revoked` (GitHub 204 / Cloudflare 200). Cloudflare still requires success for every known access/refresh token. GitHub's single-access-token revocation does **not** settle an exchange response containing a refresh token: the available documentation does not prove that operation revoked the refresh credential. The existing GitHub success path deliberately discards refresh tokens and uses only expiring access credentials; full refresh-grant custody/reconciliation remains required before real connection acceptance. No refresh, broader grant deletion or arbitrary operator-supplied token is introduced as an automatic repair.

The isolated restore verifier now accepts these receipts only when the separately selected independent evidence service records the exact outcome ID and complete row digest. A candidate's own receipt or missing dispatch row cannot settle independently recorded unknown work. Truly lost token responses still require an authenticated provider reconciliation path; the initial unknown provider account may not be identifiable from the Whumpo owner alone. Provider settings advice, lease expiry, client-secret changes, key rotation and local row deletion are not revocation evidence. No generic manual-unblock endpoint is added. Child C/D and parent WH-117 remain open for independent custody, remaining provider outcomes and deployment acceptance.

## Encrypted operator key backup

**WH-117C source checkpoint, October 2, 2026 UTC.** `tools/connection-key-backup.mjs` creates and reads one current `.whumpo-key-backup` file format for the connection keyring. This is operator tooling; it has no customer/Chat endpoint, provider client, secret-binding writer, database export or deployment path. It does not back up CMS material or invoke any deferred CMS capability.

The capsule uses Node Web Crypto AES-256-GCM with a fresh random 12-byte IV, a 128-bit authentication tag and a separate 32-byte random recovery key. Authenticated metadata binds version `1`, scope, test environment, backup ID/time, current keyring version, active key ID and the exact key ID/material fingerprints. Decryption uses the real current vault validator and compares the recovered fingerprints with the authenticated header. Unknown formats, malformed/truncated/noncanonical bytes, substituted metadata and missing/wrong keys fail. A recovery key equal to a contained platform key is refused. This is a distinct backup wrapping key, not the customer's account recovery kit or a password-derived key.

Files must be regular, singly linked, owned by the executing POSIX user and readable only by that user. Recovery and capsule directories must be private, separate and non-nested; both must be outside every checkout returned by the repository's current Git worktree inventory. Symlinks (including parent-path aliases), hard links, public permissions and writes over existing files fail. New files use exclusive creation and mode `0600`, then file/directory synchronization. A failed or uncertain write never deletes or overwrites an existing key or capsule. Creation immediately reopens and decrypts the saved capsule. It returns metadata only. These checks do not prove separate physical media, offsite retention or protection from another process running as the same operator.

### Operator workflow

Run these tools from the current local Git checkout on a POSIX host, using Node.js 24 and the repository dependencies. These commands are prepared for the coordinated testing cutover. **No real recovery key or capsule was created by the implementation checks.** Replace the uppercase placeholders with operator-selected absolute paths; do not paste key contents into Chat or use a literal secret in a command argument/environment variable. Directory setup and the choice of independent storage belong to the operator. The recovery file and capsule must be in different private directories outside all repository checkouts.

```sh
node tools/connection-key-backup.mjs init --recovery-key-file /ABSOLUTE/PRIVATE-RECOVERY/recovery.key
node tools/connection-key-backup.mjs create --keyring-file /ABSOLUTE/PRIVATE-SOURCE/connection-keyring.key --recovery-key-file /ABSOLUTE/PRIVATE-RECOVERY/recovery.key --backup-file /ABSOLUTE/PRIVATE-BACKUPS/current.whumpo-key-backup --backup-id REVIEWED_BACKUP_ID
node tools/connection-key-backup.mjs verify --backup-file /ABSOLUTE/PRIVATE-BACKUPS/current.whumpo-key-backup --recovery-key-file /ABSOLUTE/PRIVATE-RECOVERY/recovery.key --expected-digest INDEPENDENTLY_RECORDED_SHA256
```

`init` writes the random recovery key directly to the private file and prints no value. The operator must place that key in the selected independent password-manager/offline custody and independently retain the encrypted capsule plus its exact metadata digest. Do not treat two directories on this workstation or an ignored `.secrets` directory as disaster-recovery acceptance. Losing the recovery key prevents decrypting this capsule; lost account passkeys cannot recreate it. Do not remove existing required material until independent retention, permitted-restore sources and live/uncertain references have been reconciled.

`verify` works in a fresh process using only the capsule, separate recovery file and independently recorded ciphertext digest. The metadata report includes backup ID, digest, active/key IDs and `readbackVerified`; it always reports `independentCustodyAccepted: false` and `retirementAllowed: false`. It never prints key material, file paths, encrypted payloads or raw failures. The caller retains only paths and metadata in the process-local capability, not a cached plaintext keyring. Trusted operator consumers receive recovered material in memory only; JavaScript strings cannot promise secure memory erasure. No plaintext recovery file is emitted by decryption.

The [isolated restore checker](restore-admission.md) now requires this capability and the version-2 independent evidence binding to the same backup ID/digest/key IDs. Copied reports, direct keyring parameters, mismatched independent backup registration and lost/replaced files fail. Actual credential decryption still checks registered material and owner/provider/purpose/record context. It rechecks the stored backup after data/object/evidence readback, and still never grants serving, dispatch or retirement. Permitted-source inventory operation and actual independent custody remain required; passing local file checks alone cannot close child C/D or the parent.
