## What the test covers

It runs the sites Worker's default export (`m.host`) and the real `reviewHosting`, `confirmHosting`, `refreshHosting` and `disconnectHosting` from the shared fixture bundle. `maintainHosting` is bundled separately from `src/domain-hosting.ts`, because the shared fixture does not export it and was not edited; it uses only the raw database, as the scheduled job does ([src/index.ts:644](../src/index.ts)). It runs on SQLite by default and on local D1 with `--d1`. Cloudflare and DNS calls go to a recording stub, and global `fetch` throws.

1. **Regression (owner join).** Owner A publishes a site and connects a custom hostname. A `GET /` on that hostname returns 200 (control). After the project is moved to owner C, `GET` and `HEAD /` and a photo path on the custom host return 404, and the `domain_connections` row is byte-for-byte unchanged, so the refusal can only come from the owner join. The project host `https://<project>.whumpo.site/` still serves the identical publication (control: the publication was not lost), and moving the project back to A serves the custom host again.
2. **Characterization of S6-1 (below).** It is written to exit 0 while the defect exists and print `S6-1 reproduced`. Once S6-1 is fixed, those assertions will fail and should be inverted into a regression.

## Finding

### S6-1 (low) A transferred project's custom-domain connection stops hourly hosting maintenance for later batches

The finding ID is provisional. The B-series may already continue past B7 on `main`, which this stale base cannot see; assign the next free ID when this is registered.

- **Cause.** `maintainHosting` selects up to 80 connections ordered by `checked_at ASC` and refreshes them four at a time with `Promise.all` ([src/domain-hosting.ts:91-95](../src/domain-hosting.ts)). `refreshHosting` first calls `owned()` ([:75](../src/domain-hosting.ts)), which requires `c.user_id=? AND p.owner_user_id=?` and throws `DomainError(404)` otherwise ([:12](../src/domain-hosting.ts)). That call sits **outside** the `try` that turns every other check failure into a fail-closed state ([:80-88](../src/domain-hosting.ts)). Once the project's owner is no longer the connection's `user_id`, the first batch rejects and the loop never reaches later batches. `runMaintenance` records the `hosting` job as `failed` ([src/maintenance.ts:13](../src/maintenance.ts)).
- **Why it repeats.** The orphan row is never updated, so its `checked_at` stays the oldest and it is in the first batch of every run. Only the three rows that share its batch are re-checked each hour. A successful check grants at most two hours of serving ([src/domain-hosting.ts:87](../src/domain-hosting.ts)), and serving requires `serve_until>now` ([src/site-host.ts:33](../src/site-host.ts)), so another tenant's connection whose turn comes later than that lapses and its custom domain returns 404.
- **No owner can clean it up.** The connection's `user_id` cannot be changed ([schema/platform.sql:2359-2361](../schema/platform.sql)). `refreshHosting` and `disconnectHosting` ([src/domain-hosting.ts:57-58](../src/domain-hosting.ts)) refuse the old owner (the project join fails) and the new owner (`c.user_id` fails). The provider hostname is never deleted, and the row stays `active`. The project cannot be deleted while the connection exists (`ON DELETE RESTRICT`, [schema/platform.sql:293](../schema/platform.sql)).
- **Not a tenant leak.** The owner join at [src/site-host.ts:33](../src/site-host.ts) stops the orphan from serving, and section 1 asserts that. The impact is availability for other tenants plus a stranded provider resource.
- **Reproduction (written, not executed):** `node tests/boundary-custom-domain-owner.mjs` (and `--d1`). The test orders the batches explicitly: the orphan first, three of tenant B's connections with it, and B's fourth, published connection in batch two with its window lapsed. It then asserts that `maintainHosting` rejects with 404, B's fourth connection keeps its old `checked_at` and `serve_until` and its domain stays 404, exactly three provider reads happen, and the old and new owner get 404 from refresh and disconnect with no provider delete. The **control** repeats the identical arrangement with the project moved back to A: the run resolves, and B's fourth connection is renewed and serves 200.
- **Remediation (owner decision; not implemented):** isolate per-connection failures in `maintainHosting` (for example `Promise.allSettled`), and decide how an ownership change should end a connection. Options are failing closed in SQL (clear `serve_until`, move it to `disconnecting` so cleanup can target the exact `provider_id`), or requiring operator reconciliation before a transfer. Suggested owner: domain-hosting maintainers, with the operator transfer procedure.
