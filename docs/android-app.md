# Native Android owner app

**Accepted roadmap and frozen native contract — refreshed October 4, 2026 (WH-081; first accepted September 30).** Android application code, native authentication, `/api/mobile/v1` routes, signing, FCM delivery and Android customer acceptance are **planned and not implemented or configured**. The existing mobile web workspace remains available. Source inspection used `b4671f9`; this is not a deployed-release claim. The canonical backlog records no Android execution issue; live issue and dependency state was not re-checked in this offline refresh, so confirm it before claiming WH-082+ work. Execution issues and claims remain a separate coordination step.

**Status key.** *Implemented* means present in current source and covered by existing web checks. *Planned* means specified here or in [the v1 contract](mobile-api-v1.md) with no runtime. *Frozen* means the wire shape is fixed by the offline [reference](../tools/prototypes/mobile-v1.mjs), [fixtures](../tests/fixtures/mobile-v1/) and [contract test](../tests/mobile-v1-contract.mjs), which prove shapes and rules only, not routes, devices or customers.

The [F6 roadmap lane](roadmap/README.md#f6--native-android-owner-experience) and [canonical task packets](roadmap/backlog.json) own sequencing. This document defines the intended product and its boundaries. Keep existing feature contracts authoritative when adapting their behavior to Android.

## Outcome and first beta

**October 1 identity amendment:** Adopt the [shared workspace identity and data protection contract](roadmap/identity-and-data-protection.md). WH-081 consumes WH-113; WH-083 consumes WH-115. The **web** runtime is implemented (passkey-only sign-in, two-passkey signup, saved kit, restricted recovery, `__Host-whumpo_session` sessions, one principal at HTTP/Chat/provider admission) and was activated on the private test platform October 2 per [identity-web](identity-web.md); native sessions, the native handoff and Credential Manager are **planned**. Native/browser handoffs cannot bypass completion: an enrolling or recovering account is refused a native session. The native shell can proceed against the frozen contract while shared identity acceptance continues; physical-device acceptance remains separate. Customer-application visitor identity is unaffected.

**October 1 direction amendment:** [Chat is the primary owner surface](roadmap/chat-first-experience.md), with Projects/Activity supporting the conversation and Settings for infrequent account work. WH-081 consumes WH-105's current-version interaction contract; WH-084 uses WH-106's durable definitions, answers and receipts for the admitted native subset frozen in the [v1 contract](mobile-api-v1.md#operations) (nine field types, six bindings, no attachments, views or cards). The web side of WH-106–110 (maintained forms, renderer, bounded composition, views, routine journeys) is implemented and accepted for its original scope per [chat-interactions](chat-interactions.md); native rendering is **planned**. Unsupported versions/forms/views fail explicitly with `client_update_required`; there is no summary renderer or browser downgrade. Full custom-view parity remains deferred, and the Android shell/identity foundations do not wait for the web renderer.

An invited owner can sign in, request a project change, inspect the result, explicitly approve an eligible action, and recover an interrupted connection without duplicate work. The first private beta includes native Chat, projects, activity, review controls, photo intake, Android sharing and push notifications. Native implementation can proceed alongside the web roadmap; admission of real customers depends on WH-048 and the Android-specific WH-087 gate.

**October 29 platform amendment:** the [platform ADR](android-app-platform.md) selects Kotlin Multiplatform with Compose Multiplatform, shipping Android first. On Android this is still Kotlin and Jetpack Compose, so the rules below are unchanged. Shared code moves into a `:shared` module so that a macOS desktop target (and iOS, if it is ever scoped) can reuse it. The owner app UX is specified in [android/app-ux.md](android/app-ux.md).

Use Kotlin and Jetpack Compose, with ViewModels and repositories separating presentation, protected local state and remote operations. Start a maintained Android project under `android/` during WH-082, using a pinned Gradle wrapper and compatible Kotlin/Compose/JDK toolchain. Keep Android tooling separate from the Node 24/pnpm 11 web toolchain. The minimum/target Android matrix is an [owner decision](mobile-api-v1.md#open-owner-decisions) recorded by WH-082 with the checked platform documentation date; use current stable tooling and APIs without old-platform shims, and check Play requirements when preparing the release. [Android architecture recommendations](https://developer.android.com/topic/architecture/recommendations), [passkey prerequisites](https://developer.android.com/identity/passkeys/create-passkeys).

## Existing services and the frozen interface

The [WH-105 v1 interaction decision](chat-interactions.md) is delivered for the web and consumed here: bounded definitions, field/binding IDs, answer versus effect receipts, current actor/project admission and strict rejection of noncurrent clients. Its handlers are installed as `/api/chat/interactions/v1/*` in [`src/index.ts`](../src/index.ts); native reaches them only through `/api/mobile/v1/interactions/*`.

Current web transport (**implemented**): the principal comes from the `__Host-whumpo_session` cookie via [`src/workspace-identity`](../src/workspace-identity/http.ts) (`workspaceIdentity`), every non-GET `/api/*` request must carry an exact `Origin`, and the welcome gate returns `409 onboarding_required` for `/api/chat`, `/api/chat/*` and `/api/workspace/*` only. The gate is not total today: `onboardingComplete` also treats an owner who already has any project as complete, and `POST /api/projects` now returns the same `409 onboarding_required` (with the support link) until `onboardingComplete` is true, so a direct call can no longer create a first project and open Chat without the welcome (WH-207). A fresh account is refused before any project, welcome or activity row is written; the 20-project quota, `Origin` and identity checks are unchanged. Because `onboardingComplete` still treats an owner with any existing project as complete, whether to remove the route or that project-existence fallback remains an open owner decision. Native must not rely on or call direct project creation, and first workspace entry stays the browser welcome. There is **no native bearer API**, so a native client cannot use any existing route (it has no cookie and no `Origin`). `resolveIdentity` and the WebAuthn challenge check currently accept only `client:'web'`.

**Frozen (planned runtime):** a narrow `/api/mobile/v1` boundary, specified in [mobile-api-v1.md](mobile-api-v1.md), implemented by WH-083/084/085/086 over the existing domain handlers, ownership checks, receipts, quotas and review gates. It is not a generic proxy and accepts no internal Chat command string.

## Native identity and browser handoff

Consume the [WH-113 shared authority and handoff contract](workspace-identity.md). It fixes restricted versus ordinary sessions, actual proof freshness, account epochs, five-minute handoffs/sixty-second exchange codes, and incomplete/revoked-identity denial. WH-081/083 add transport adapters; they must not create another enrollment, kit or recovery authority model.

Use Credential Manager passkeys for returning owners; adding or removing a passkey is a browser journey under the existing recent-authentication rules (the native app only reauthenticates for a sensitive control). Bind challenges to their operation, intended client and a short expiry; consume them once. Verify RP ID, user verification, current credential authority and the server-configured signing-certificate origins. Publish Digital Asset Links for the approved package/signing identity on `whumpo.com`; debug identities must not acquire test/release authority. App Links handle only explicitly supported destinations. [Credential Manager association](https://developer.android.com/identity/credential-manager/prerequisites), [verified App Links](https://developer.android.com/training/app-links/verify-applinks).

Native session secrets belong in Android Keystore-protected application-private storage and are excluded from device backups, logs, URLs and model context. Reuse authoritative server-side session revocation and account recovery: revoking sessions or removing compromised credentials must invalidate Android access too. Preserve the existing seven-day absolute session expiry and ten-minute passkey freshness window unless the shared identity contract is explicitly amended; the exact native bearer, handoff and revocation rules are frozen in [mobile-api-v1](mobile-api-v1.md#auth-and-session-model). Creating a browser-return token must not make an old authentication look fresh. Do not add silent indefinite refresh.

Browser cookie authentication retains its Origin/CSRF checks. Native routes accept only their explicitly supported authentication mechanism, with bounded requests and rate limits; a user agent, package header or absent Origin is not proof of native authority. Review handlers must receive the same authenticated owner/session context and recheck current authority at commit time.

Signup, invitation, US eligibility, Turnstile, welcome and recovery use trusted browser journeys, updated by WH-113–115 for two-passkey completion and restricted recovery. The app starts a short-lived handoff with state, a PKCE S256 challenge and an allowlisted verified HTTPS return URI. Complete browser authentication and required identity enrollment before returning a one-time code; exchange it using the app-held verifier, bind it to the initiating flow/account, and reject replay, wrong state, wrong redirect or expiry. One-key signup and incomplete recovery cannot exchange into an ordinary native session. Never put a session, recovery key or provider credential in the return URL. Lost-all-keys recovery needs two verified replacement passkeys, a saved rotated kit and fresh passkey verification before return; it must not revive a pre-recovery session. No password fallback is planned. Ordinary valid sessions gain no recurring unlock prompts.

Preview tabs use a browser session independently of the native bearer session. Never inject the native token into browser cookies, query strings, generated content or arbitrary navigation headers. A missing browser session leads to ordinary sign-in and an allowlisted return to the requested preview. Provider consent remains in the established browser workflow.

## Interrupted work, reviews and media

The beta is online for remote operations. Protect and persist unsent drafts, the original submitted payload/revision/request ID, and pending prepared upload bytes under the signed-in account. Preserve these through process death and rotation; purge private state and cancel local work on logout/account change. Expired/revoked sessions cannot submit retained work until the appropriate owner authenticates again. Do not cache an unrestricted offline copy of the workspace.

After a lost response, read the committed result using the same operation identity. Offer an explicit retry with the original payload and ID only when appropriate; changed content needs a new request. Do not automatically resend inference requests or approvals on reconnect, notification receipt or app launch. Backgrounding the app is not cancellation, and a request receipt does not promise that arbitrary long-running work survives a Worker deadline. Test interrupted server execution and show unresolved outcomes honestly.

Reviews show the exact project, artifact/version, proposed effect and required disclosures before confirmation. Refresh current review state, enforce expected revision/expiry/recent authentication, and preserve server replay receipts. Stale, foreign, withdrawn or unsupported reviews cannot expose an enabled approval. Notifications and model replies never grant approval authority. Only the four frozen controls (private website save, website publication, bounded application activation and application data restore) are admitted, and each must be verified individually; every wider control stays in the browser until a reviewed contract amendment.

Use the current Android [photo picker](https://developer.android.com/training/data-storage/shared/photo-picker). An unavailable required API makes photo intake unsupported on that device; do not implement a legacy document-picker path. Support only existing admitted image formats and bounded streams; validate granted content URIs and MIME/bytes. Match the current photo preparation contract: at most 10 MiB input, orientation-correct resize within 1600 × 1600, flattened baseline JPEG within the server's 1 MiB limit, with server-side metadata stripping and validation retained. Persist the exact prepared bytes, name and upload ID for retry; do not regenerate different bytes under the same ID. Avoid broad storage permissions and release temporary URI grants/files when no longer needed.

Uploading is not publication or safety approval. Distinguish pending storage, stored-but-held, approved and blocked media. Never read/render held remote bytes or attach them to a version. The documented current photo pipeline has no production detection adapter; real uploads remain held until the existing safety work is accepted. Synthetic clear verdicts prove local plumbing only. Customer-facing photo use therefore inherits WH-017 through WH-048. Keep [R2 private](https://developers.cloudflare.com/r2/buckets/public-buckets/); Android receives neither bucket credentials nor public-bucket access.

## Push delivery and cost

WH-086 selects Firebase Cloud Messaging as the Android provider. Send through the [FCM HTTP v1 API](https://firebase.google.com/docs/cloud-messaging/send/v1-api) from a trusted Worker adapter using a narrowly scoped server credential. No Firebase authentication, database, analytics or model dependency is implied. Treat registration tokens as private delivery addresses, not authentication. Bind registration and preferences to the current owner/device session; support token rotation, explicit opt-in, invalid-token cleanup and server-side withdrawal after logout, revocation or account closure.

Derive notification events only from committed owner-operation receipts: completion, attention-required failure, or pending review. Atomically persist an outbox entry with the event or use a replay-safe reconciliation cursor and unique event identity to recover the commit-to-enqueue gap. Recheck ownership, active registration, preferences and subject relevance at dispatch. Use generic lock-screen copy and opaque event IDs; exclude project names, message text, source, photos and credentials. An open fetches current authenticated state; deleted, expired or wrong-owner destinations show a safe unavailable state. Duplicate events must not repeat the underlying operation.

Implement bounded delivery under the D1-owned job/receipt design in WH-052: leases/fencing, per-owner fairness, finite attempts, deadlines, obsolete-event expiry, cancellation and sanitized backlog diagnostics. Retry only proven safe failures under that ADR. FCM acceptance does not prove display, and FCM is not an exactly-once business effect; a lost send acknowledgement must not become blind redispatch. Retain uncertain outcomes for diagnosis, with Activity/current server state providing readback. An expired lease never authorizes repeating project work or invoking AI.

Request notification permission in context and keep every core workflow available when denied. Handle foreground/background receipt, token renewal, delayed delivery and lack of Google Play services without a notification-dependent workflow. The initial device acceptance matrix targets Play-enabled Android devices. [FCM Android setup and permission behavior](https://firebase.google.com/docs/cloud-messaging/android/get-started).

**Public pricing checked September 30, 2026:** FCM is listed as no-cost in [Firebase pricing](https://firebase.google.com/pricing). Whumpo's Firebase project, sender permissions and account entitlement are unverified. Existing [Worker execution](https://developers.cloudflare.com/workers/platform/pricing/) and [D1 operations/storage](https://developers.cloudflare.com/d1/platform/pricing/) still incur applicable costs, including retry and polling overhead; no new recurring minimum is authorized here. Reuse existing services. A new or faster [Cron Trigger](https://developers.cloudflare.com/workers/configuration/cron-triggers/) requires the ADR's measured latency/cost and activation review. No Queues, Workflows, paid analytics or plan upgrade is introduced by this roadmap.
