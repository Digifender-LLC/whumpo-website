October 3, 2026. **Source and local acceptance; not deployed.** This extends the routine adapter in [#98](https://github.com/zemdregon/whumpo/issues/98). It does not close that child, parent #95, or full journey audit #99. The deployed platform remains the [photo release](chat-routine-release.md).

## Customer flow

An owner can ask for GitHub or Cloudflare connection controls in Chat. The model selects one fixed provider and an owned project, or an account-level handoff. Within a saved website task, only its exact project is admitted. The maintained card shows saved authorization status and explicit connect, refresh and disconnect controls. Settings reuses those controls. Rendering the card does not start OAuth, query repositories/zones, use inference, or change a website.

Connecting performs the existing passkey reauthentication and provider-specific start handler. Approval happens on the provider website. OAuth start atomically saves an immutable navigation link alongside its one-time state. The link binds the interaction ID/digest to that exact provider, owner, session and hashed state. Callback navigation uses this independent locator and a fixed same-origin destination, including after the authorization state has been consumed or replaced. It cannot accept a model-supplied return URL. A handoff returns to Chat; direct Settings consent returns to Connections. A card older than the current message page is read separately through the same owner-scoped interaction handler. The workspace URL retains only its validated interaction UUID, so reload and another tab can reopen the same card without storing status or authorization state in browser storage.

The callback query is navigation, never success evidence. The card refreshes saved metadata. Active authorization, expired authorization, pending consent, unresolved token-exchange custody, revocation pending, missing configuration and missing feature inclusion remain distinct. Saved authorization does not establish provider availability or permissions for a particular operation. A failed read hides the old status and offers a read-only retry. Refresh/reload does not start OAuth or invoke the model.

## Authority and current protocol

- `interaction.requestConnection` accepts exactly `kind`, `operation`, `projectId` and `provider`. Provider is `github` or `cloudflare`; project is an owned UUID or null. No generated scopes, credentials, URLs, confirmation or automatic effects.
- The existing interaction envelope/digest, cancellation receipt, seven-day payload retention and account/project guards apply. No new approval store or model-owned state machine.
- `POST /api/connections/{provider}/start` requires the current JSON body `{ "handoff": null }` for direct controls or `{ "handoff": { "interactionId": "UUID", "definitionDigest": "SHA256" } }` for Chat. Missing/old bodies are rejected. There is no compatibility reader.
- A Chat start requires an exact current maintained card for that provider. Ownership, open/unexpired state, absence of replacement, current identity, editing inclusion and connection inclusion are checked again in the OAuth-state INSERT. Late dismissal or project transfer prevents a start.
- Hiding/dismissing a card is not provider revocation. Already-started OAuth and uncertain credential custody keep their existing lifecycle; use Disconnect to cancel/revoke. Removed card payload cannot be reconstructed through a status request.
- Return navigation reads the immutable link only for the current owner, exact original session and current project ownership. A repeated callback can return to its original card; foreign, unknown or expired navigation links cannot supply a Chat target. Existing token-exchange, staging, expiry, cancellation, revocation and unknown-outcome rules remain authoritative.
- `connection_chat_links` is the sole return-locator reader. Links are immutable, contain no raw OAuth state/code/token/verifier, and grant no authorization. They expire at the originating card’s seven-day retention deadline; hourly maintenance removes at most 100 expired links. Account/interaction/project deletion cascades them. Card dismissal removes its payload immediately but retains this bounded navigation metadata; dismissal, OAuth expiry or link cleanup does not erase credential recovery obligations. The superseded OAuth-state locator columns and triggers are removed. The lifecycle catalogue records the current schema; no migrations, alternate readers or dual protocols.
- Neither the handoff nor the task context contains credentials. The task can offer consent; current task context does not yet include a connection observation, so it must not invent consent outcomes. The existing ordinary connection-status Chat tool remains available for fresh account-level metadata.
