## Shared entry boundaries

The [platform dispatcher](../src/index.ts) checks exact Origin for mutating requests, except the separately authenticated Stripe webhook. Protected owner routes resolve the current session before their resource-specific ownership checks. Authentication routes, request limits and onboarding admission have separate gates. A valid session is not universally a recent session: credential changes and selected destructive/recovery controls explicitly require the short freshness window; ordinary exact reviews use their own expiry, revision and ownership predicates.

[Plain Chat](../src/chat.ts) accepts natural language. [Typed Chat controls](../src/chat-controls.ts) accept closed action schemas and review identifiers; the model adapter can prepare allowed actions but cannot call human confirmation verbs. A literal slash command in conversation is not authorization. A review displayed in Chat remains subject to the underlying service's ownership and current-state checks.

The [visitor gateway](../src/app-gateway.ts) uses a project-specific origin and cookie, separate from owner authentication. [Public site serving](../src/site-host.ts) and [controlled application serving](../src/app-host.ts) resolve approved public state. Private R2 objects are served through bounded membership/approval paths. The [QuickJS runtime](../src/runtime/worker.ts) has a separate service boundary, no platform bindings or host callbacks, and bounded execution and memory; generated source does not execute in the control Worker.

## Findings and remediation ownership

Severity is calibrated to the concrete prerequisites, including private testing. Static confidence is medium; no race was reproduced during the scan.

### A1 — Credential mutation after session revocation (medium)

`src/index.ts:500–517` checks session freshness before awaited work, then replaces a recovery code or admits passkey/session deletion without checking that same session in the committing statement. An attacker with a previously compromised fresh session could resume the request after the owner recovers the account. Recovery-code replacement can install a new attacker-known recovery credential; delayed passkey removal can delete retained keys and the recovered session.

**Owner:** authentication maintainers (`src/index.ts`, `src/passkeys.ts`). **Required fix:** guard the durable admission by the same session hash, owner, expiry and freshness; return a replacement code only if that guarded write succeeds. **Regression:** pause each old mutation, recover/change password through another request, resume it, and prove the new recovery credential, retained passkeys and new sessions survive. Include freshness expiring between admission and commit. Existing competing-recovery tests do not cover this gap.

### A2 — GitHub staging token enters cross-owner revocation (low)

`src/github-connection.ts:26–30,56–75` stores a new token as `revoking` while awaiting the provider's user response. Another tenant's disconnect invokes global cleanup and can revoke that staged token. Reconnection can also retire the old working token before detecting failed replacement. No token disclosure or arbitrary active-token revocation was demonstrated.

**Owner:** provider connection maintainers. **Required fix:** distinct staging state/lease; atomic replacement admission before retiring the old credential; owner-scoped interactive cleanup and an atomic claim for global revocation. **Regression:** two synthetic owners and a paused fake provider; disconnect A while B connects, and prove B's token survives. Failed replacement must preserve the old connection; abandoned staging must eventually revoke safely. Live GitHub setup is not needed for these regressions.

### A3 — Visitor deletion intent survives an account switch (low)

`web/visitor.js:30–43` stores only request ID and document revision, then retries deletion automatically with the current cookie. `src/app-lifecycle.ts:9–18` binds a previously unseen request to the current visitor. If A's first request never commits, a fresh B login in another tab and matching revision allow A's retained intent to delete B. An account change between review and initial submission shares the same missing binding. An already committed A receipt correctly rejects B.

**Owner:** visitor lifecycle and controlled visitor UI maintainers. **Required fix:** server-issued deletion review bound to the exact actor/project/revision; confirmation must consume that review. Recover an unknown delivery through read-only receipt/status checks; do not automatically first-dispatch a destructive operation on page load. **Regression:** switch identity before first submit and before an uncommitted saved request resumes; B remains intact, while A's genuinely committed lost-response deletion remains recoverable. Test same-browser tabs with benign synthetic records only.
