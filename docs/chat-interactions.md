## Wire objects and digest

### WH-108 receipted model continuation contract — October 3, 2026 UTC

Custom service/presentation forms now use the deployed `agent.task-continue@1` binding. **Save and continue** first commits the immutable answer receipt, then explicitly requests one owner Chat continuation keyed by that submission. A saved draft, ordinary read, page reload or receipt replay never dispatches inference. An unavailable model leaves the answers saved and continuation not started; the owner may explicitly continue later or stop it.

The continuation shares the current standard-AI request, internal inference budget and bounded one-inspection loop. Its claim commits atomically with the Chat turn and reservations. Context contains the issuing task's original request, declared question meanings and submitted answers, plus only the pinned project's current metadata. Other projects, conversation history, private drafts/defaults, profile and provider context are excluded. The model may answer, inspect that website, prepare a reviewed edit, or save its first private website through existing handlers. A first private website uses the existing first-only creation contract; changing an existing website requires its exact review. It cannot change project, invoke account/provider operations, publish, spend, approve or recursively present another form.

Current task revision, immutable submission, project ownership, feature admission and continuation state are checked at claim, dispatch and final commit. Continuation turns have `ai_context_allowed=0`, keeping their answer-bearing replies out of unrelated later Chat history. A lost acknowledgment recovers the same receipt; it never restarts dispatch. Failure keeps the answer snapshot. Reconciliation uses the existing Chat/cost receipts and fences closed work; an unknown provider cost remains unknown even when a closed work attempt is resolved. Pending review references come from the existing task-linked domain receipts, not model assertions.

This extends the current continuation table and current-schema guards; it does not introduce a second inference ledger, old-schema reader or migration overlay. Current verification is recorded in [model continuation evidence](verification.md#custom-form-model-continuation--october-3-2026-utc). The [coordinated test cutover](chat-test-release.md#verified-model-continuation-release--october-3-2026-utc) is verified separately. Continuation start/finish timestamps measure observed operation duration, including recovery delay; internal inference receipts retain token evidence and subscription-shadow/unknown cost basis. No real API price or provider-only latency is inferred. Maintained account intake and deterministic content-preview adapters retain their own declared handoffs.

### WH-108 custom composition implementation contract — October 3, 2026 UTC

The current custom adapter composes public website-planning questions for an owned project. `site.services@1` and `site.presentation@1` declare the use of the answers. The agent selects a bounded subset/order of question intents, stable field IDs, requiredness and simple conditions; the server supplies question wording, types, options and limits. This is composition of individual questions, not a fixed whole-form template. Arbitrary model-authored wording, credential questions and executable bindings are not admitted by this adapter. The gallery-photos question adds the approved same-project resource selector described below, deployed in the later scoped platform update. Broader composition and multi-turn task acceptance remain in WH-108's original scope; the separately receipted submitted continuation is implemented above.

The issued `custom@1` definition carries its purpose and each field's question ID. Both the client and storage adapter reconstruct and compare the admitted definition. Unknown intents, purpose mismatches, altered labels/options, custom destinations, source bindings and undeclared effects refuse. Form creation and answer submission use existing current identity/feature checks, owned project guards, expiry, digest/revision checks, exact receipts and draft retention. The submission operation saves information only. The current **Save and continue** control then explicitly starts the separately receipted follow-up described above; receipt recovery never starts it.

Corrections preserve the project/task and immutable earlier submissions. A stable field ID cannot be reassigned to another question, and a retained question cannot silently change IDs. Only matching retained fields carry user/suggested defaults. Prose changes remain suggestions for explicit owner review. Hidden values are excluded from submitted snapshots.

Submitted-answer inspection uses the existing bounded owner Chat lookup. It must select an exact interaction, task, project, submission and nonempty subset of fields; private drafts/defaults and unselected answers stay out of inference. Current ownership, feature admission, unreplaced submission and pending owner-turn state are rechecked before returning the minimized projection. The visible form states that submitted answers may be used for website planning; existing Contributor testing/data-use restrictions still apply. Catalog approval constrains what is asked, not what a user may type, and is not a sensitive-content detector.

The source adapter is connected through `requestInformation`, `replaceInformation`, `proposeAnswers` and the current `readSubmittedAnswers` inspection. Verification is recorded in [custom composition evidence](verification.md#custom-chat-composition--october-3-2026-utc). This does not close WH-108. The old `readSubmittedIntake` action/reader has been removed; the dated checkpoints below describe its historical evidence, not an active compatibility path.

The [shared TypeScript protocol](../src/chat-interactions/protocol.ts) defines the closed v1 structural subset; [synthetic fixtures](../tests/fixtures/chat-interactions.json) are readable examples. It uses Web Crypto and the maintained bounded canonical encoder. The [transport reader](../src/chat-interactions/input.ts) limits actual streamed UTF-8 bytes to 32 KiB before parsing. The former Node-only prototype was removed. Protocol validation alone grants no authority: domain storage and the current workspace capability enforce ownership, admission and exact state.

An issued element contains exactly:

```text
{ version: 1, id: UUID,
  scope: { accountId, actorId, conversationId, projectId: UUID|null, taskId, originTurnId },
  createdAt: UTC timestamp, expiresAt: UTC timestamp,
  definition: { version: 1, kind: "form"|"view", template, title, summary,
    presentation: "inline"|"panel"|"dialog", purpose?: declared custom purpose, fields: [...], cards: [...],
    submitBinding: "interaction.answers@1"|null,
    continuationBinding: "site.content-prepare@1"|"agent.task-continue@1"|null },
  definitionDigest: SHA-256 hex }
```

All scope IDs are server-resolved UUIDs. The current owner account supplies both account and actor; future members retain a distinct actor. Current `chat_conversations` and `chat_interaction_tasks` record the logical conversation/task identities introduced by WH-106. Origin turn must belong to the same account/conversation. V1 drafts/submissions belong to the issuing actor; another member cannot take over by knowing the ID. An explicitly authorized reassignment creates a new interaction and preserves prior receipts. Project can be null only for account-wide reads or intake that needs no project resource. Scope is association, not a bearer authorization token.

Hash the entire issued object except `definitionDigest`: sorted object keys recursively, array order preserved, JSON strings/numbers and UTF-8 bytes, no Unicode normalization. Reject non-JSON/non-finite values. Changing scope, target, revision, field order/labels/defaults, conditions, template, bindings, timestamps or presentation requires **a new interaction ID and digest**; old snapshots retain their meaning. Digest equality is integrity evidence, not proof that a client is entitled to issue an element. Production reads use the stored server-issued object, never a client-resealed replacement.

Maintained adapters propose owned target references. The current custom adapter proposes purpose-bound question descriptors; it cannot send arbitrary definitions or wording. The server verifies references, rebuilds saved defaults/provenance from owned state, selects permissible bindings, assigns scope/identity/time, validates, and persists the issued object. A model cannot assert `saved` provenance, choose another actor/conversation, extend a deadline, or mint an active review by computing a hash.

### Limits and fields

| Item | v1 bound |
| --- | --- |
| Complete issued element / definition / submitted answers | 32 KiB / 24 KiB / 16 KiB UTF-8; complete mutation body at most 32 KiB |
| Structural complexity | At most 10 container levels and 1,024 total visited JSON values, including arrays; no recursive components |
| Fields / cards / options | 12 fields in the structural vocabulary; at most **8** when mapped to `site.content-prepare@1`, matching the compiler's eight-operation bound. 8 cards, 12 options per choice; 20 rows per card; server output at most 32 KiB per element |
| Text | Title 100, summary 400, field label 80, help 240; short answer at most 200, long answer at most 2,000 UTF-16 code units; downstream field limits may be stricter |
| Identifiers | Field/content/card/choice: `[a-z][a-z0-9-]{0,39}`, reserved prototype names forbidden; owned IDs UUID; digest 64 lowercase hex |
| Conditions / groups | One equality condition per field against an earlier unconditional boolean or single-choice field; at most three flat numbered groups. No AND/OR trees, expressions or dependency cycles |
| Active work | At most 5 open forms per conversation, 20 per account, one automatic presentation per turn. Do not silently cancel old forms to fit a quota |
| Drafts / expiry | Draft revision CAS; no more than one accepted draft save per second per interaction, bounded existing account rate limits as well. Issued answer window at most 7 days; no heartbeat extension |

Every field has exactly `id,type,label,help,required,binding,constraints`, with optional `default,when,source,group,questionId`. A `custom@1` definition requires a declared `purpose`; runtime admission additionally requires exact catalog question IDs and reconstructed wording/limits. These metadata fields are not accepted on maintained templates. `binding` is always `answer.value@1`; `id` is its key in the submitted snapshot. No model-authored endpoint, path expression or action payload appears in a field.

| Field type | Closed constraints and value |
| --- | --- |
| `text`, `long-text` | `{maxLength}`; plain string. Empty allowed only when optional. Render as text, including markup-like input; never interpret labels/help/answers as HTML. |
| `choice`, `multi-choice` | `{options:[{id,label}]}`; one option ID or unique option IDs. Required multi-choice is nonempty. |
| `boolean` | `{}`; true/false, including false as a complete answer. |
| `number` | `{min,max,step}`; finite value within ±1 billion and the step grid. No string coercion. Currency/spending is not implied by a numeric field. |
| `date` | `{}`; actual `YYYY-MM-DD` Gregorian calendar date with a year from 1 through 9999, no timezone conversion. |
| `datetime` | `{zone}` with an explicit supported IANA timezone; value is an exact UTC ISO instant with milliseconds. UTC and local calendar years must be from 1 through 9999. Renderer displays the zone and resolves ambiguous/nonexistent local times explicitly before submission. |
| `resource` | `{collection:"projects"|"photos",multiple,maxItems}`; UUID or unique UUID array, at most five. Picker queries a registered server collection, never arbitrary search/URLs. |
| `attachment` | Same shape, collection fixed to `photos`; references existing cleared project photos only. New uploads use the existing trusted photo flow and safety checks before a selectable reference exists. |

Optional `default` is `{value,provenance:"saved"|"user"|"suggested"}`. Saved text also has `source:{binding:"site.content@1",contentId,revision}`. The server verifies that source; suggested values are visibly suggestions. User-provenance defaults may retain incomplete draft values, including blank required text; saved-site and suggested defaults must satisfy the field's complete value rules. Defaults are not silently inserted on submission: the client submits the values the customer actually reviewed. An omitted required visible field fails validation. Reject answers for unknown or hidden fields, duplicates, missing owned resources, unsafe/removed photos, invalid dates and wrong types. Returning to a form may restore a hidden draft locally, but submitting it while hidden is rejected. `when:{fieldId,equals}` never executes code.

The full vocabulary is protocol scope. Clients implement the current admitted controls; a missing type or binding rejects the interaction with an explicit update-required result. There is no degraded form or read-only compatibility renderer. There are no password, passkey, recovery-key, OAuth-token, payment, file-byte, SQL or executable fields. Sensitive information accidentally entered in ordinary text follows content/privacy handling; field names alone cannot detect secrets or establish safe model processing.

Before issuance, the adapter also validates the proposed purpose/questions against its maintained task and content/privacy policy; a text field asking for a recovery key is still prohibited. Such a request must use the trusted identity flow instead. The offline structural checker cannot prove that arbitrary natural-language questions are safe; WH-108 must test semantic credential-solicitation rejection and context minimization, independently of schema validity.

## Submission, state and operation identity

WH-106 reserves versioned handlers for create/read/list, save-draft, submit, cancel and read-receipt. WH-108 wraps them in bounded agent capabilities. Exact HTTP/native route names belong to their implementations; this decision freezes the shared payload, not nonexistent routes.

All writes carry `{version:1,requestId,interactionId,definitionDigest,expectedAnswerRevision,operation,answers?}`. `operation` is `save-draft`, `submit` or `cancel`; only the first two accept answers. Actor/account/project/target are resolved from current authority and stored scope, never accepted as override fields. Response supplies current definition digest, answer revision, interaction state and operation receipt. Readback authenticates the caller again. Request hashes include operation, digest, expected revision and exact answers using the same canonical encoding. New corrections use a new request ID.

Persist domain states separately:

| Layer | States and invariants |
| --- | --- |
| Interaction | `open → submitted | canceled | expired | superseded`; immutable terminal snapshot. Client dismissal changes presentation only and leaves open answers resumable. Explicit cancel ends collection; expiry ends authority, not retention. |
| Draft | Monotonic `answerRevision`, CAS and current digest. Each save replaces the complete draft snapshot. Partial means required answers may be missing, not a patch merged with defaults. An empty object clears all answers; omitted keys stay absent. Text can retain empty/whitespace values while editing; a cleared single resource selection omits its key, never stores an empty UUID. Every provided value must still be correctly typed and applicable. Submission requires all visible required answers and their nonempty rules. Invalid saves return field errors without replacing valid state. Concurrent edits fail visibly; no last-writer-wins overwrite. |
| Submission | Immutable submission UUID, request hash and answer snapshot; exactly one accepted snapshot per interaction. Correction creates a linked replacement interaction and new submission, preserving previous receipts. |
| Continuation | Null for information-only intake. When the definition has an admitted continuation binding, a separate operation UUID is deterministically associated with the submission; `not-started → pending → succeeded | failed | unknown`. Explicitly requested preview preparation can run once after collection; no model run on read/render. |
| Domain effect | Existing proposal/apply/publication/provider/job identity and result. These remain authoritative even if a form is canceled or a Chat reply fails. |

Uniqueness on `(accountId, requestId)` plus immutable hash gives same-ID/same-payload readback; changed bytes get `409 request_conflict`. Current identity/ownership still applies to retries. Commit answer revision, immutable snapshot, submission identity and the required continuation record atomically with current digest/state/expiry checks. Information-only definitions create no continuation record; their current read/history/export reports null, not a pending or successful job. Claiming admitted work remains a separate explicit operation. Expired, revoked or superseded state cannot win through a stale preflight. A duplicate request may read its committed receipt, but cannot initiate fresh work after expiry/revocation. Production must test interleavings in disposable D1; the offline schema reference does not prove this transaction.

Draft save/cancel require current open revision. A cancel racing submission has one database winner. After submission, **stop further work** may suppress an unstarted continuation; it cannot roll back a private save, undo publication, cancel an already-dispatched provider mutation or release an uncertain funding reservation. Report the actual domain outcome and use its reviewed recovery procedure.

On transport loss, keep the exact original request and read receipt/current state first, including after reload or navigation. Never auto-resend from session storage, service workers, background sync or native reconnect. An explicit retry reuses the exact identity only when the domain contract permits it. Pending/unknown operations retain their identity and show status/recovery; never label a timeout failed-and-safe-to-repeat. Unsupported/malformed returns `400`; validation `422` with bounded field IDs/codes; stale/digest/request conflict `409`; unauthenticated `401`; unavailable foreign scope generic `404`; identity/eligibility/policy denials use an allowlisted reason without foreign data.

Task context is a bounded pointer record: task UUID/revision, selected project, at most five open interaction IDs, five pending domain review references and one 1,000-character untrusted summary. No credentials, full visitor inbox or hidden permanent conversation memory. Changing selected project is visible; old forms stay associated with their original project. Explicit retarget creates a fresh definition after reads/admission; it cannot reuse an answer/request/review under a different scope. Task summaries never override the current domain state.

## Shared authority and eligibility

At issue/read/draft/submit/continue/confirm/dispatch, consume WH-122's shared operation admission (WH-090 retains cumulative feature acceptance) over WH-113 identity, current owner/member/project rights, stable feature ID, actual configuration/consent, implementation/readiness and current resource/review/funding policy. Registry metadata is not that resolver. Do not reconstruct eligibility from plan labels, form claims, stored grants or a cached view.

| Actor/state | Required behavior |
| --- | --- |
| Anonymous, enrollment, recovery or incomplete welcome | No interaction/workspace/model authority. Use trusted authentication/progress/welcome routes; never render a credential form from the model. |
| Ordinary current owner, eligible feature | Allow only the binding's admitted operation and owned scope. Existing recent-auth requirements apply at sensitive effects; viewing or routine answers add no repeated unlock prompt. |
| Future member with read only | Authorized read bindings/history only; no draft, submit, model maintenance, prepare, apply or layout mutation without explicit member permissions. Account-wide history is not automatically project-shared. |
| Revoked member/session, removed project permission | Deny current reads and writes; close/clear client-held private state on detection. A saved form/view/receipt ID is not continuing access. |
| Downgraded/expired feature, missing consent or unready adapter | Deny new privileged continuation/effect; display current reason. Preserve owner-only permitted history/export/revocation/uncertain readback and security/recovery. No automatic unpublish or destruction. |
| Guest feedback/customer visitor | No workspace bindings, owner inference or maintainer credentials, even with a valid visitor account or expiring review link. |

Standard owner assistance remains unlimited fair use with zero customer-credit debit; existing internal testing capacity and safety apply. Advanced spending, provider consent and real payment changes keep separate explicit approval/funding paths. Monitor mode does not disable safety or authorization. Per-feature/module bindings added later must register their own stable IDs, field schemas, lifecycle and admission requirements, rather than laundering a new feature through `core.editing` intake.

## Presentation, saved views and current clients

Inline is default. Panels/sheets/dialogs are hints; the renderer can choose an accessible mobile layout. One dialog at a time, no stealing focus from the composer, no automatic reopening after dismissal. Labels/errors have programmatic associations; retain tab order, visible focus, touch targets, safe areas and keyboard space. Status updates use bounded polite announcements. Required/optional/default provenance and project are visible; **Cancel**, **Resume**, correction and answer-in-Chat remain available.
