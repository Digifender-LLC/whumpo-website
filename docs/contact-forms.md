# Contact forms and private inbox

The first reusable dynamic capability is a platform-authored contact form, shared as implementation code while each project's settings and visitor messages remain separate. It runs on the existing workspace Worker and D1 database. No new paid service, outbound email provider, arbitrary customer code, or AI processing is involved in submission handling. Optional owner notices (WH-036, below) are implemented provider-neutrally and stay off: no provider is implemented, selected or enabled.

## Customer flow

1. Publish a saved website version.
2. Ask the agent to enable a contact form for the project. It prepares an exact review.
3. Confirm that review with its approval button within ten minutes.
4. The public host adds a Contact link to that live version. It opens a Whumpo-hosted form at `https://whumpo.com/contact/PROJECT_ID`.
5. Open Dashboard → Contact inbox to read messages. This panel does not copy visitor content into chat history or model context.
6. Ask the agent to disable the contact form. Confirming the disabling review stops new intake. Existing messages remain private until deletion or expiry.

Chat accepts natural language; slash-shaped strings in internal handlers and older fixtures are implementation details, not customer commands. See [natural-language Chat](natural-language-chat.md).

Publishing, restoring or unpublishing advances the publication revision and disables the previous form. Publication reviews disclose this effect. A fresh review is needed to activate intake for the new live version, including restoration of the same saved HTML. Contact settings are a hosted runtime capability: they do not alter the immutable site artifact, its checksum, private preview or static source ZIP.

## Review and transaction boundary

`contact_reviews` pins owner, project, desired enabled state, settings revision, publication revision and ten-minute expiry. D1 confirmation triggers recheck ownership, current settings, expiry, current publication for enablement, and the confirming chat turn. They atomically advance settings and record a content-free activity event with the chat receipt. Replays do not reapply changes. The model can prepare `contactReview` with an exact project ID and boolean; it cannot confirm, read the inbox or supply arbitrary backend code.

The public host joins the active setting into its existing publication read. The only injected markup is a fixed platform-authored link. Its sandbox permits opening that link in a separate browsing context; generated scripts and forms remain disabled. The destination has its own restrictive CSP and denies framing. Both the link and form require an active setting matching the current publication. The database rechecks this relationship at submission insertion, protecting against publication/disable races after bot verification.

[Saved service settings](project-service-clients.md) can also prepare this same independent contact review from the current saved configuration. The complete current schema includes immutable provenance, full current-target checks at confirmation and submission-time blocking for later known holds on the linked configuration. Critical direct disable reviews remain available. Test release `03b74965-16b8-4a41-8848-33cb1e21867f` records the earlier deployment of this capability; it does not establish deployment of the pending current identity/schema cutover. See the linked evidence for its local and live scope.

## Submission boundary

The public form accepts only name (1–100 characters), email (up to 254) and message (1–2,000), plus a random submission ID, settings revision and Turnstile token. POST requires exact Origin, URL-encoded input, unique allowlisted fields and a streaming 32 KiB body bound. The existing Workers rate limiter uses a separate contact/IP key. Deployed environments fail closed without Turnstile configuration.

Server-side Siteverify validates success, the platform hostname, `contact` action and exact project `cdata`. The response is bounded to 8 KiB, redirects are rejected and the request has a ten-second timeout. Local development alone can omit the challenge. Incoming visitor data and verification responses are not logged. No uploaded attachments, sender-selected recipient, email delivery or model processing is supported.

Database guards allow at most 20 accepted submissions per project in an hour, 100 per project and 1,000 platform-wide while receipts are retained. Once 500 receipts are retained platform-wide, an account already retaining 100 is refused until its receipts expire (fair share, WH-075). One connection may make at most 10 submission attempts per project per UTC day, counted before verification and stored only as a hashed per-day key ([capacity and fairness](capacity-and-fairness.md#wh-075-first-slice-fairness-fixes--october-4-2026-utc)). Concurrent submissions cannot bypass these caps. The capacity limit is shared across all plans during this test. Expired receipts may occupy capacity until daily cleanup; deletion does not recycle the allowance. Rate limiting is an application control, not an account-wide Cloudflare billing cap.

A minimal receipt stores submission ID, project, request hash and timestamps. Duplicate payloads reuse that receipt; different payloads using the same ID fail. Receipts survive owner deletion of message content until expiry, preventing retry resurrection and quota recycling. After the receipt's retention window, a newly bot-verified submission is treated as new. No automatic POST retry is performed after an uncertain response.

## Inbox and retention

Authenticated `GET /api/projects/PROJECT_ID/inbox` joins the project owner and returns only that project's unexpired messages, at most 100. Foreign projects return 404. `DELETE /api/contact-messages/MESSAGE_ID` checks authenticated ownership and Origin; the UI requires an explicit deletion confirmation. Deletion is idempotent and does not reveal foreign-message existence.

All submitted text is rendered with `textContent`, including names and email addresses; it is never interpreted as HTML or instructions. Closing the panel clears its content and invalidates pending reads. The AI's history and workspace context contain no automatic visitor-message read path. A customer manually pasting visitor content into chat is a separate action, subject to the existing AI-provider disclosure.

Messages become inaccessible at 30 days. Daily 03:17 UTC maintenance removes expired message rows and minimal receipts; physical deletion can therefore lag visibility expiry until that run. This is application retention, not a guarantee about provider backup retention. Project/account operator cleanup cascades through settings, reviews, messages and receipts. Customer-wide account deletion remains a separate unfinished lifecycle requirement.

## Owner notification delivery (WH-036, provider-neutral)

October 4, 2026. **Implemented in source with local synthetic-provider tests only; no provider exists, nothing is deployed, no email can be sent, and no live canary has run.** The private inbox above remains the source of truth: a notice is only a signal, never a copy. Visitor submission, Turnstile, per-client limits (WH-075), operator containment (WH-050) and safe rendering are unchanged, and the public form still says no email is sent automatically (true while the gate below is closed).

What exists (`src/contact-notifications.ts`, tables in `schema/platform.sql`, classified in `docs/data-lifecycle.json` as `contact-notifications`):

- **Reviewed destination.** `contact_notification_destinations` holds at most one owner-named address per project, starting `unverified`. The owner's explicit submission of the exact address is the review; it is strict single-mailbox input, never visitor-supplied. A destination becomes `verified` only when a short-lived code, delivered through the same selected provider, is entered. The code is accepted only if the provider accepted that exact notice (database-checked `accepted` verification outbox row), it expires after one hour, locks after five wrong guesses, and a new request supersedes the old code. With no provider configured, `requestContactVerification` returns `provider_not_configured`, stores nothing, and the destination stays unverified forever. Verification notices are limited to 3 per destination and 10 per account per day so an unverified address cannot be used to mail a third party (no open relay: recipient is the owner's verified address, the sender is platform-fixed at the provider, and no visitor text reaches any header, subject or body).
- **Content-free notices.** The provider interface receives only `{outboxId, idempotencyKey, kind, projectId, recipient}` (plus the verification code for verification). A `new_message` notice means "you have a new message, read it in Whumpo". It never includes the visitor's name, email, message or any AI output. The outbox stores no visitor content.
- **Outbox** (`contact_notification_outbox`, `runContactDelivery`). One row per message and destination, keyed by a unique idempotency key (`message:<submission>:<destination>`; `verify:<destination>:<code>`), so replays, duplicate submissions and concurrent drains cannot create a second row. The attempt is claimed before sending and the same key is sent on every retry, so a provider timeout (10 seconds, treated as retryable) or replay is deduplicated by the provider rather than producing a second message. Retries use exponential backoff (5 minutes doubling to a 6-hour cap) and stop after 6 attempts (`failed`/`exhausted`); a non-retryable rejection is `failed`/`rejected`. Only messages received after verification and within 24 hours are queued (enabling a provider never back-fills). At most 10 notices an hour and 50 a day per destination (database trigger backstop); excess messages stay in the inbox only. A deleted message, suppressed destination, contained project (WH-050 `contact` scope) or expired notice is cancelled, not sent.
- **States and irreversibility.** `queued`, `accepted` (provider accepted; says nothing about the inbox or reading), `failed`, `cancelled`, `bounced`, `complained`. `failed`, `cancelled`, `bounced` and `complained` are final by trigger. `accepted` can only become `bounced` or `complained`. `applyContactDeliveryEvent` records a hard bounce, complaint or unsubscribe idempotently: it writes a permanent per-account row in `contact_notification_suppressions` (never updated or deleted except with the account), which atomically makes the destination final-`suppressed` and cancels unsent notices. A suppressed address cannot be re-added, re-verified or removed-and-re-added to resume delivery. Webhook intake with provider signature verification is not implemented, because it is provider-specific.
- **Retention and holds.** Outbox rows expire 30 days after creation in the daily `contacts` maintenance job, which skips projects inside a WH-132 preservation hold; owner removal of a destination and direct outbox deletion are refused for held projects. Backlogs are reported by `tools/maintenance-inventory.mjs` (`contact_notification_outbox`, `contact_notification_queue`).

### Activation gate (all required, none done)

`runContactDelivery` does nothing unless `CONTACT_NOTIFICATION_PROVIDER` names a provider implemented in `implementedContactNotificationProviders` (currently empty) and `CONTACT_NOTIFICATION_REVIEW` records the review reference, the same gate as `src/support-delivery.ts`. Before any provider is implemented or enabled the owner must approve, with evidence:

1. The provider choice, with current list pricing, free-tier limits, minimum commitments and overage behaviour re-verified on the provider's official pages (the research below is unverified), and any recurring charge recorded here.
2. The exact sender identity and DNS changes: sending domain, SPF/DKIM/DMARC records, any return-path/bounce domain, and who controls that DNS. Whumpo has not chosen a sender address or domain and none is invented here. No customer DNS is changed.
3. The provider's idempotency/deduplication behaviour, its bounce/complaint/unsubscribe event delivery and signature scheme, and its suppression behaviour, mapped onto `applyContactDeliveryEvent`.
4. A trigger (scheduled job or queue consumer) reviewed against `docs/background-jobs.md` and `docs/job-envelope.md`, and the owner-facing UI/Chat review for entering and verifying an address (not wired yet; there is no route, Chat command or Dashboard control for destinations).
5. Updated customer-facing disclosure, because the form's "no email is sent" statement and the site agent text change.
6. A live canary only to explicitly approved addresses.

## Transactional email provider research

Written October 4, 2026 from general knowledge without network access. **Everything below that names prices, limits, product availability or exact DNS record values is unverified and must be checked on the linked official pages before any decision.** Nothing here is a recommendation to purchase or enable a service.

**Cloudflare Email Routing is inbound only.** It receives mail for a domain and forwards it to an existing verified inbox or to an Email Worker ([Email Routing](https://developers.cloudflare.com/email-routing/)). It is not an outbound transactional delivery service and is not a candidate provider for contact notices. Email Workers can forward or reply to inbound messages and, through a `send_email` binding, send to destination addresses verified in Email Routing ([Email Workers](https://developers.cloudflare.com/email-routing/email-workers/)); that verified-destination restriction and its limits (including any per-message or daily caps) are unverified and would not let Whumpo mail arbitrary owners without each owner verifying an address at the Cloudflare account that owns the Routing zone, which is not Whumpo's customer-account boundary. Cloudflare has also announced or previewed a separate outbound email sending product; its availability, pricing and sender requirements are unverified (check the Cloudflare developer documentation before relying on it, and `docs/cloudflare-capability-roadmap.md`).

Common requirements across all candidates (unverified; the standards themselves are [SPF RFC 7208](https://www.rfc-editor.org/rfc/rfc7208), [DKIM RFC 6376](https://www.rfc-editor.org/rfc/rfc6376), [DMARC RFC 7489](https://www.rfc-editor.org/rfc/rfc7489)):

- The sending domain publishes SPF (or a provider-managed return-path), DKIM selectors the provider gives, and a DMARC policy. Records are created at the domain owner's DNS. For a Whumpo-owned sending domain that is a Whumpo DNS change needing explicit approval; sending on behalf of a customer domain would be a customer DNS change and is out of scope.
- Large mailbox providers have published bulk-sender expectations (authentication, low complaint rates, easy unsubscribe for marketing mail, announced 2024; verify current rules). Owner notices to a self-verified address are transactional, not marketing, but a provider's acceptable-use policy and suppression behaviour must still be matched: `applyContactDeliveryEvent` treats a hard bounce, complaint or unsubscribe as permanent suppression, which should equal the provider's own suppression semantics.
- Verification of the destination must use the same provider and sender that will deliver notices; the code flow above proves reachability and consent for that exact path.
- A new account may start in a restricted sandbox (for example SES) that can only mail pre-verified recipients, which the verification flow still satisfies but which limits launch.
- The service must support an idempotency key or equivalent deduplication window long enough to cover Whumpo's retry schedule (6 attempts over roughly 2.5 hours); if it does not, Whumpo cannot promise exactly-once-per-key delivery and a provider-side message-ID reconciliation step must be designed first.

Open decision for the owner: provider, sender domain/address, who owns its DNS, spending ceiling and the minimum monthly commitment tolerated. Until decided, the research above is only an input to that review.
