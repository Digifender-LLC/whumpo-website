# Contact forms and private inbox

The first reusable dynamic capability is a platform-authored contact form, shared as implementation code while each project's settings and visitor messages remain separate. It runs on the existing workspace Worker and D1 database. No new paid service, outbound email provider, arbitrary customer code, or AI processing is involved in submission handling. Optional content-free owner notices (WH-036, below) use Cloudflare Email Service, chosen by the owner. They are implemented in source and stay inactive until the owner completes the activation steps.

## Customer flow

1. Publish a saved website version.
2. Ask the agent to enable a contact form for the project. It prepares an exact review.
3. Confirm that review with its approval button within ten minutes.
4. The public host adds a Contact link to that live version. It opens a Whumpo-hosted form at `https://whumpo.com/contact/PROJECT_ID`.
5. Open Dashboard → Contact inbox to read messages. This panel does not copy visitor content into chat history or model context.
6. Ask the agent to disable the contact form. Confirming the disabling review stops new intake. Existing messages remain private until deletion or expiry.

Chat accepts natural language; slash-shaped strings in internal handlers and older fixtures are implementation details, not customer commands. See [natural-language Chat](natural-language-chat.md).

Publishing, restoring or unpublishing advances the publication revision and disables the previous form. Publication reviews disclose this effect. A fresh review is needed to activate intake for the new live version, including restoration of the same saved HTML. Contact settings are a hosted runtime capability: they do not alter the immutable site artifact, its checksum, private preview or static source ZIP.

## Review and transaction boundary

`contact_reviews` pins owner, project, desired enabled state, settings revision, publication revision and ten-minute expiry. D1 confirmation triggers recheck ownership, current settings, expiry, current publication for enablement, and the confirming chat turn. They atomically advance settings and record a content-free activity event with the chat receipt. Replays do not reapply changes. The model can prepare `contactReview` with an exact project ID and boolean; it cannot confirm, read the inbox or supply arbitrary backend code.

The public host joins the active setting into its existing publication read. The only injected markup is a fixed platform-authored link. Its sandbox permits opening that link in a separate browsing context; generated scripts and forms remain disabled. The destination has its own restrictive CSP and denies framing. Both the link and form require an active setting matching the current publication. The database rechecks this relationship at submission insertion, protecting against publication/disable races after bot verification.

[Saved service settings](project-service-clients.md) can also prepare this same independent contact review from the current saved configuration. The complete current schema includes immutable provenance, full current-target checks at confirmation and submission-time blocking for later known holds on the linked configuration. Critical direct disable reviews remain available. Test release `03b74965-16b8-4a41-8848-33cb1e21867f` records the earlier deployment of this capability; it does not establish deployment of the pending current identity/schema cutover. See the linked evidence for its local and live scope.

## Submission boundary

The public form accepts only name (1–100 characters), email (up to 254) and message (1–2,000), plus a random submission ID, settings revision and Turnstile token. POST requires exact Origin, URL-encoded input, unique allowlisted fields and a streaming 32 KiB body bound. The existing Workers rate limiter uses a separate contact/IP key. Deployed environments fail closed without Turnstile configuration.

Server-side Siteverify (`src/turnstile.ts`, shared with anonymous WH-127 module forms) validates success, the platform hostname, `contact` action and exact project `cdata`. The response is bounded to 8 KiB, redirects are rejected and the request has a ten-second timeout. Local development alone can omit the challenge. Incoming visitor data and verification responses are not logged. No uploaded attachments, sender-selected recipient, email delivery of message content or model processing is supported.

Database guards allow at most 20 accepted submissions per project in an hour, 100 per project and 1,000 platform-wide while receipts are retained. Once 500 receipts are retained platform-wide, an account already retaining 100 is refused until its receipts expire (fair share, WH-075). One connection may make at most 10 submission attempts per project per UTC day, counted before verification and stored only as a hashed per-day key; anonymous submissions to [public module forms](shared-modules.md#records-and-forms-module-wh-127--october-4-2026-utc) count against the same per-connection allowance ([capacity and fairness](capacity-and-fairness.md#wh-075-first-slice-fairness-fixes--october-4-2026-utc)). Concurrent submissions cannot bypass these caps. The capacity limit is shared across all plans during this test. Expired receipts may occupy capacity until daily cleanup; deletion does not recycle the allowance. Rate limiting is an application control, not an account-wide Cloudflare billing cap.

A minimal receipt stores submission ID, project, request hash and timestamps. Duplicate payloads reuse that receipt; different payloads using the same ID fail. Receipts survive owner deletion of message content until expiry, preventing retry resurrection and quota recycling. After the receipt's retention window, a newly bot-verified submission is treated as new. No automatic POST retry is performed after an uncertain response.

## Inbox and retention

Authenticated `GET /api/projects/PROJECT_ID/inbox` joins the project owner and returns only that project's unexpired messages, at most 100. Foreign projects return 404. `DELETE /api/contact-messages/MESSAGE_ID` checks authenticated ownership and Origin; the UI requires an explicit deletion confirmation. Deletion is idempotent and does not reveal foreign-message existence.

All submitted text is rendered with `textContent`, including names and email addresses; it is never interpreted as HTML or instructions. Closing the panel clears its content and invalidates pending reads. The AI's history and workspace context contain no automatic visitor-message read path. A customer manually pasting visitor content into chat is a separate action, subject to the existing AI-provider disclosure.

Messages become inaccessible at 30 days. Daily 03:17 UTC maintenance removes expired message rows and minimal receipts; physical deletion can therefore lag visibility expiry until that run. This is application retention, not a guarantee about provider backup retention. Project/account operator cleanup cascades through settings, reviews, messages and receipts. Customer-wide account deletion remains a separate unfinished lifecycle requirement.

### What exists

Source: `src/contact-notifications.ts` (outbox, runner, reviews), `src/contact-email.ts` (Cloudflare adapter and the only activation path), `tools/contact-suppression-reset*.mjs` (operator reset). Tables are in `schema/platform.sql` and classified in `docs/data-lifecycle.json` as `contact-notifications`.

- **Destination setup.** `contact_notification_destinations` holds at most one owner-named address per project, starting `unverified`. It can be set in two ways:
  - **Exact Chat review.** The agent can prepare `contactNotificationReview` only with the exact address the owner gave. The reply pins that normalized address for ten minutes, and the separate confirmation button applies it in the chat-turn transaction (`contact_destination_reviews`, trigger `contact_destination_review_apply`). Replays, other owners, expired reviews and suppressed addresses are refused by the database. The model cannot confirm.
  - **Dashboard control.** Dashboard → Contact inbox → Email notices sets the address after a confirmation dialog showing it exactly (`PUT /api/projects/ID/contact-notifications`). The same panel removes it, sends a verification code and accepts the code. It can also hand the same request to Chat as a review.
  - **Verification.** Neither path verifies. A destination becomes `verified` only when the owner enters an 8-character code delivered through the same provider and sender. The code is accepted only if the provider accepted that exact notice (database-checked `accepted` verification outbox row). It expires after one hour, locks after five wrong guesses, and a new request supersedes the old code. While delivery is inactive, a code request returns `provider_not_configured` and stores nothing, so a destination cannot become verified. Verification notices are limited to 3 per destination and 10 per account per day. The recipient is the owner's own address, the sender is fixed, and no visitor text reaches any header, subject or body, so there is no open relay.
- **Content-free notices.** The adapter receives only `{outboxId, idempotencyKey, kind, projectId, recipient}` plus the code for verification. It sends plain text from `Whumpo <notify@whumpo.com>` with one `X-Whumpo-Notice-Id` header (the outbox id). A `new_message` notice says a message arrived and links to `https://whumpo.com/workspace/inbox`. It never includes the visitor's name, email, message, the project name or any AI output. The outbox stores no visitor content.
- **At most one provider call per notice attempt.** The outbox has one row per message and destination, keyed by a unique idempotency key (`message:<submission>:<destination>`; `verify:<destination>:<code>`). Replays, duplicate submissions and concurrent drains therefore cannot create a second row. Cloudflare Email Service documents no idempotency key ([Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), last updated September 16, 2026, read October 4, 2026), so delivery is at most once per call:
  - The attempt is claimed, and counted against the spending ceiling, in one transaction before the call.
  - A timeout (10 seconds), a throw, `E_INTERNAL_SERVER_ERROR` or an unknown error code is **uncertain**: the notice becomes `unknown-outcome` (reason `uncertain`, held at most 72 hours and then `unresolved`) and is never resent.
  - Only documented refusals that certainly did not send are retried with exponential backoff (5 minutes doubling to a 6-hour cap; at most 6 attempts, each its own journal envelope, then `failed`/`exhausted`; a refused attempt waits as `deferred`). These are `E_RATE_LIMIT_EXCEEDED`, `E_DAILY_LIMIT_EXCEEDED`, `E_SENDER_NOT_VERIFIED` and `E_SENDER_DOMAIN_NOT_AVAILABLE`.
  - Other documented errors are `failed`/`rejected`.
  - `E_RECIPIENT_SUPPRESSED` writes a permanent Whumpo suppression with reason `provider`.
- **Queueing.** Only messages received after verification and within 24 hours are queued, so activation never back-fills. At most 10 notices an hour and 50 a day per destination (all templates, so a verification notice counts) are queued by a guarded `INSERT ... SELECT`; a database trigger backs this up. Excess messages stay in the inbox only. A notice is cancelled, not sent, when its message was deleted, its destination is suppressed, the project is contained (WH-050 `contact` scope) or it has expired.
- **States and irreversibility (WH-156, schema batch 3e).** Contact notices are rows of the shared outbox `notification_notices` with the frozen states: `queued`, `dispatching`, `deferred`, `accepted` (the provider accepted it, which says nothing about delivery or reading), `delivered`, `unknown-outcome`, `bounced`, `complained`, `failed`, `cancelled`, `unresolved`. The transitions are a database trigger ([notifications](notifications.md#shared-outbox-wh-156-schema-batch-3e)); `failed`, `cancelled`, `bounced`, `complained` and `unresolved` are final, `accepted` can only become `delivered`, `bounced` or `complained`, and nothing leaves `unknown-outcome` for a send state.
- **Suppression and unsubscribe.** `applyContactDeliveryEvent` records a hard bounce, complaint or unsubscribe idempotently. Provider suppression at send time does the same. Either writes a permanent per-account row in `contact_notification_suppressions`, which atomically makes the destination final-`suppressed` and cancels unsent notices. Removing and re-adding the address cannot resume delivery.
  - Cloudflare publishes bounce and complaint events only through Queues event subscriptions ([event subscriptions](https://developers.cloudflare.com/email-service/platform/event-subscriptions/)). The owner did not choose Queues, so asynchronous event intake is not implemented.
  - Instead, Cloudflare's own account suppression list feeds Whumpo: a hard-bounced or complained recipient is suppressed by Cloudflare, and the next send to it throws `E_RECIPIENT_SUPPRESSED`. This requires the sending domain's **Drop suppressed recipients** setting to stay off, which is the default ([suppressions](https://developers.cloudflare.com/email-service/concepts/suppressions/)).
  - Unsubscribe is the owner removing the address in the Dashboard. Every notice says how.
- **Operator-reviewed reset.** `node tools/contact-suppression-reset.mjs --input PRIVATE.json [--apply DIGEST]` follows the operator-containment pattern: a local CLI, `status` and `reset` actions, a preview first, then an apply pinned to the exact preview digest. A reset names the exact current suppression (account, address and suppression time); stale or changed state is refused by the database. It inserts an immutable audit row (`contact_notification_suppression_resets`) whose trigger removes that one suppression and the final-suppressed destination. Nothing is sent or re-verified: the owner must set the address and verify a new code again. Inside a safety preservation hold the reset is refused. The tool does not touch Cloudflare: the operator must also confirm the address is absent from the Email Service suppression list, or the next send re-suppresses it.
- **Spending ceiling.** `notification_send_ledger` (one row per provider and UTC day, shared by every notice kind) counts provider calls per UTC day, in the same statement batch that records the attempt's intent. A call is refused before it reaches the provider (`cancelled`/`ceiling`; nothing is queued while over) when the 32 most recent UTC days would exceed the ceiling, so any billing cycle of up to 31 days stays within it.
  - The ceiling is 14,285 calls: floor($5 / $0.35 per 1,000). This assumes none of the 3,000 included emails are available, because that quota is account-wide.
  - Every call counts, including rejected and uncertain ones. The day's ceiling can only be lowered.
  - Counters are content-free and removed after 40 days by the daily `contacts` job.
- **Retention and holds.** An unsent notice expires 24 hours after creation (the hourly pass cancels it with its envelope). Finished notices are removed 30 days after their outcome and `unresolved` evidence after 90 days (interim defaults pending an owner decision) by the daily `contacts` maintenance job, which skips projects inside a WH-132 preservation hold; the schema refuses to delete an open notice. Owner removal or replacement of a destination (Dashboard or confirmed Chat review) cancels its unsent notices, is refused while an attempt is in flight (`409`) and is refused for held projects, as is direct outbox deletion. Backlogs are reported by `tools/maintenance-inventory.mjs` (`notification_notices`, `notification_queue`, `notification_unknown`).

### Cloudflare Email Service facts and cost flags (read October 4, 2026; require verification)

- Email Sending is in **public beta** and **available on the Workers Paid plan only** ([overview](https://developers.cloudflare.com/email-service/), [beta changelog](https://developers.cloudflare.com/changelog/post/2026-04-16-email-sending-public-beta/)). Whumpo's account plan and entitlement require verification.
- Pricing ([pricing](https://developers.cloudflare.com/email-service/platform/pricing/), last updated June 9, 2026): 3,000 outbound emails included per month, then **$0.35 per 1,000**. Hard-bounced emails count; API rejections, including suppressed recipients, do not. No minimum commitment is listed. These are beta prices that require verification before activation. At the configured ceiling the maximum charge is about $5 per month. Cloudflare's budget alerts are notifications, not caps.
- Limits ([limits](https://developers.cloudflare.com/email-service/platform/limits/), last updated September 25, 2026): new accounts start with a conservative daily quota that grows with reputation (`E_DAILY_LIMIT_EXCEEDED` is retried). There are at most 50 recipients and 5 MiB per message. Before a sending domain is onboarded, mail can go only to verified destination addresses.
- DNS ([send emails](https://developers.cloudflare.com/email-service/get-started/send-emails/)): onboarding `whumpo.com` requires Cloudflare DNS for the zone. Cloudflare adds MX and SPF records on the `cf-bounce` subdomain, a DKIM TXT record and a DMARC TXT record at `_dmarc.whumpo.com`. If `whumpo.com` already publishes DMARC, review the merge before onboarding. **This is a Whumpo DNS change requiring explicit owner approval.** No customer DNS is involved.
- Binding ([send bindings](https://developers.cloudflare.com/email-service/configuration/send-bindings/)): `send_email` entries can restrict `allowed_sender_addresses`. Whumpo's binding should allow only `notify@whumpo.com`. It must not use a destination allowlist, because owner addresses vary.
- Inbound Cloudflare Email Routing is a separate product and is still not used for outbound notices.

## Transactional email provider research

Written October 4, 2026 from general knowledge, before the owner chose Cloudflare Email Service (above). The rows below were kept as the comparison input to that decision. **Everything below that names prices, limits or exact DNS record values is unverified.**

**Cloudflare Email Routing is inbound only.** It receives mail for a domain and forwards it to an existing verified inbox or to an Email Worker ([Email Routing](https://developers.cloudflare.com/email-routing/)). It is not an outbound transactional delivery service and is not a candidate provider for contact notices. Email Workers can forward or reply to inbound messages and, through a `send_email` binding, send to destination addresses verified in Email Routing ([Email Workers](https://developers.cloudflare.com/email-routing/email-workers/)); that verified-destination restriction and its limits (including any per-message or daily caps) are unverified and would not let Whumpo mail arbitrary owners without each owner verifying an address at the Cloudflare account that owns the Routing zone, which is not Whumpo's customer-account boundary. Cloudflare's separate outbound product, Email Sending in Cloudflare Email Service, was verified on October 4, 2026 and selected (see above).

Common requirements across all candidates (unverified; the standards themselves are [SPF RFC 7208](https://www.rfc-editor.org/rfc/rfc7208), [DKIM RFC 6376](https://www.rfc-editor.org/rfc/rfc6376), [DMARC RFC 7489](https://www.rfc-editor.org/rfc/rfc7489)):

- The sending domain publishes SPF (or a provider-managed return-path), DKIM selectors the provider gives, and a DMARC policy. Records are created at the domain owner's DNS. For a Whumpo-owned sending domain that is a Whumpo DNS change needing explicit approval; sending on behalf of a customer domain would be a customer DNS change and is out of scope.
- Large mailbox providers have published bulk-sender expectations (authentication, low complaint rates, easy unsubscribe for marketing mail, announced 2024; verify current rules). Owner notices to a self-verified address are transactional, not marketing, but a provider's acceptable-use policy and suppression behaviour must still be matched: `applyContactDeliveryEvent` treats a hard bounce, complaint or unsubscribe as permanent suppression, which should equal the provider's own suppression semantics.
- Verification of the destination must use the same provider and sender that will deliver notices; the code flow above proves reachability and consent for that exact path.
- A new account may start in a restricted sandbox (for example SES) that can only mail pre-verified recipients, which the verification flow still satisfies but which limits launch.
- The service must support an idempotency key or equivalent deduplication window long enough to cover Whumpo's retry schedule (6 attempts over roughly 2.5 hours); if it does not, Whumpo cannot promise exactly-once-per-key delivery and a provider-side message-ID reconciliation step must be designed first.
