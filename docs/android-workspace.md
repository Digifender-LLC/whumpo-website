# Native workspace transport (WH-084)

**October 7, 2026: server source, Android browsing/plain Chat, and exact application/restore review controls are implemented and locally verified.** `src/mobile/workspace.ts` admits the closed workspace, Chat, history, review and maintained-form subset of [the current native contract](mobile-api-v1.md). It creates no native copy of domain authority or storage. The client scope below is narrower than the server operation set; installed-device acceptance is separate from both. Photos, sharing, push, native information forms and specification/site review renderers remain later work; an identity-only or browsing client declares no unsupported control or field capability.

## Current admission

The shared Android bearer resolver supplies the ready-account principal. Each workspace request uses `admitWorkspace` and `workspaceBindings`, so every database batch repeats identity, credential, epoch and expiry admission in the committing transaction. Storage/service/provider calls retain the existing guarded transport. Cookie and Origin refusal, global non-mobile bearer refusal and address/session limits remain unchanged. Sensitive controls also use the shared recent-authentication gate and authorization limiter.

`GET /bootstrap` reports an incomplete welcome without exposing workspace data. Every other workspace operation requires the existing `onboardingComplete` predicate. Restricted enrollment/recovery principals cannot reach this layer. The default and hard minimum build is **4**; `MOBILE_MINIMUM_BUILD` can raise it but cannot lower it. Older builds cannot be re-enabled by stale configuration. There is one current response shape, with no legacy parser.

Projects, Activity and history are bounded owner-scoped reads. Cursors encode positions bound to owner, exact route and search; they grant no authority. Project and Activity ordering includes the immutable ID as a timestamp tie breaker. Activity preserves existing IDs such as `domain:<turn UUID>` as bounded opaque ASCII keys. Versions return at most 25 existing saved-version identities with allowlisted browser preview paths. Native bearers never enter the browser preview request. These preview paths currently require an existing browser cookie; without it the API returns 401 JSON. The automatic browser sign-in and allowlisted return bridge is not implemented or accepted here. Native review UI must not claim that missing-browser-session journey is complete.

## Chat and result recovery

`POST /chat/messages` calls `sendConversation` with only the original request ID, expected conversation revision and bounded text. Slash-prefixed text is still ordinary text; the adapter cannot reach a private command interpreter. `POST /reviews/confirm` is a separate closed route over `sendChatControl`. Natural-language model proposals retain the existing domain review boundary.

A saved turn matches the original canonical text/control and expected revision. A same-ID exact replay returns that saved result; changed input conflicts. New sends retain the shared conversation revision and pending-turn gate. Success means the request has a durable turn status, not that an arbitrary downstream operation succeeded. The app must resolve a lost reply using `GET /chat/turns/{requestId}` and show completed/pending/failed/uncertain honestly; opening the app or refreshing history never resends a mutation.

Recent history uses `readChat`; older/search pages use `chatHistory`. Current receipt-derived review metadata is offered only from the matching saved turn/domain readers. Historical prose creates no control. Exact turn readback uses `readSavedChatTurn`, including its final identity and saved-reply consistency check.

## Four exact review controls

- **Specification apply:** the current proposal digest and expected specification revision, full browser comparison/preview and an actual passkey proof younger than ten minutes. Approval saves the private specification/version.
- **Site confirmation:** current publication comparison, immutable saved version and publication revision. The adapter excludes unpublish even though the shared control type could represent it.
- **Application enable:** the exact linked server receipt and current shared presentation, complete verified source (8192 UTF-8 bytes maximum), SHA-256 and all effect/limit disclosures. Application disable is excluded. The client must show the full source and disclosure before advertising `application.confirm`.
- **Application data restore:** exact linked receipt, restore point, document count, program/roster/offline eligibility and an actual fresh passkey. This restores documents without enabling the application or publishing a visitor page.

The server derives the control from current domain metadata and compares it to the exact submitted control again before the shared handler executes. Every domain handler retains its atomic ownership, safety, quota, expiry and revision guards. Unsupported capabilities receive no enabled control; unknown controls never fall through to another handler. Code is never truncated to create approval metadata. The build-3 review shape includes `artifact:null` for other reviews and `{kind:"application-source",source,digest}` for application enable.

## Durable information forms

The adapter calls the existing list/read/resources/mutate/receipt/continue/stop/reconcile functions directly. It accepts no client-created definition, view or dispatch instruction. A current form must need only the declared native field and binding subset, have `kind:"form"`, and contain no cards. The same capability check applies to read, resource lookup, new mutation and continuation. Attachment, photo, connection, custom-view and card definitions fail closed; a generic form never creates review approval.

Drafts, answer revisions, immutable submission/request identities, exact digest conflicts, resource ownership, retention tombstones and continuation readback remain owned by WH-105/106. A repeated committed mutation may read its exact shared receipt after cancel has erased its envelope; it cannot execute again or change the saved payload. Submitting information alone does not dispatch continuation. The existing WH-105 error codes/field IDs are wrapped in the mobile envelope with bounded fixed messages, never raw provider or SQL text.

## Android browsing and plain Chat (build 3)

The initial build-3 client declared `controls:[]`, `fieldTypes:[]` and `bindings:[]`. It implements the ready-account bootstrap/welcome gate, Chat refresh/search/older pages, exact saved-turn readback, explicit plain-text sends, and owned Projects/Activity paging. Pages request ten items and retain at most 200 loaded history/list entries. Search is bounded to 100 characters; outgoing Chat is 1–1000 characters. A bounded 1 MiB workspace response accommodates complete 20,000-character assistant replies; identity responses retain their smaller 64 KiB bound. Unknown envelopes, malformed ordered history, foreign browser destinations and unexpected enabled review authority are refused.

Before sending, `NativeWorkspaceController` seals the original request ID, conversation revision and exact trimmed text in the account's no-backup pending slot. Duplicate taps share one current action. Startup, reconnect, history refresh and browser return never resend a mutation. A lost acknowledgement retains that original request and offers an explicit status check. Only a missing exact readback offers **Resend exact original request**, which preserves all three original values. A missing request can be released for a different draft only after a fresh missing receipt and a strictly newer conversation revision prove its old payload cannot start; null, equal and lower revisions refuse release. Known pending/uncertain results are not presented as successful completion. A known uncertain turn requires an explicit acknowledgement before a different request can be composed.

A known acceptance clears only the exact submitted draft, never a newer edit or another account's draft. Session authorization fences every response against the active account and identity generation. Revocation/sign-out erase the account's protected state; a late private result cannot populate a subsequent account. The superseded shell-only project/activity repositories and local-only account authority adapter were removed.

Review/form notices open only the build's fixed `/workspace/` website through a Custom Tab. The browser has its own ordinary sign-in and receives no native bearer. At build 3 the app offered no review approval, form mutation, native version preview or claimed authenticated-preview return. Build 4 adds the application/restore subset below. Nine-field durable forms, specification/site review renderers, project detail/version screens and the signed-out browser-preview bridge remain WH-084 source work. Photos/sharing and push remain separate work. This slice does not complete WH-084.

`NativeWorkspaceTest` exercises encrypted custody, lost acknowledgement/restart, duplicate taps, exact explicit replay, account changes, stale-revision release, onboarding, uncertain results and mismatching readback. Actual loopback HTTP tests cover current capability headers, real large Chat replies, encoded query/cursor transport, exact one-shot POST behavior under `503 Retry-After: 0`, real prefixed Activity IDs, malformed ordering and unsupported approval authority. The full Android command in [android-build](android-build.md#workspace-client-verification-october-7-2026) passed 69 JVM tests, zero lint issues in both flavors, both debug APKs and both instrumentation APKs. No emulator, installed-device, signed association, real inference/provider or native customer acceptance was exercised.

## Android exact application and restore reviews (build 4)

The current capability header declares only `application.confirm` and `app.restore`; form field and binding lists remain empty. Pending reviews are refreshed explicitly. The screen shows every server disclosure, exact review/project/expiry, complete saved application source in a selectable scrollable text region, and its verified SHA-256. Source is bounded to 8192 UTF-8 bytes and is never truncated. Unknown/extra control fields, unsupported enabled controls, changed code/digest and foreign preview paths are refused. Specification/site reviews direct the owner to the ordinary website without claiming a private-preview return journey.

Approval requires a visible acknowledgement bound to a fingerprint of all displayed metadata, every disclosure line, the complete source/digest and exact control. Restore additionally requires the literal `RESTORE` and actual current passkey proof. The passkey button only verifies identity; it never resumes an approval. Before dispatch the controller rereads the current review and requires the same fingerprint and expiry. It persists the original approval request ID, conversation revision and exact control in a separate encrypted pending slot, under the same single-flight gate as ordinary Chat. A restart containing both slots blocks all new dispatch and permits separate explicit readbacks.

Receipt recovery checks the original ID, revision and shared control label; it remains available when the review expired or disappeared. Completed/failed/uncertain/pending results remain distinct, and approval readback never erases an unrelated Chat draft. Only a missing receipt plus a freshly read unchanged review allows an explicit same-request retry. Releasing a missing older approval requires another missing readback and a strictly newer conversation revision. Neither reauthentication, navigation, restart nor refresh automatically repeats a mutation.

The paired build-4 `account_closing` response uses the exact current `{code,message,next,browserPath}` error with HTTP 409, `next:"browser"` and `/workspace/account`. It immediately freezes native workspace authority, clears screen state, erases drafts and pending work, and destroys their old key. Only logout identity and a durable closure marker are resealed; the marker is written before any retained bearer, including after restart. Late draft writes are refused. The owner can open the fixed account-status path on the build's validated origin through a Custom Tab, without a bearer, or sign out. Cleanup failures remain frozen with an honest failure message, and independent cleanup/key-invalidation attempts continue even when one directory cannot be erased. An ordinary/faulty 401 revokes local authority; the exact current fresh-passkey 401 preserves the still-valid session.

`NativeApprovalTest`, the real-controller closure tests, `AccountClosureStorageTest`, and the actual HTTP adapter tests cover complete-source/digest binding, typed restore/fresh proof, missing/lost approval replies, unchanged exact retries, dual-slot restart, duplicate taps, save failures, account changes, closure during approval recovery, stale missing release, key rotation, interrupted marker/bearer writes, deletion failures and spoofed closure paths. HTTP tests consume the canonical server error fixture as test resources. See the build-4 record in [android-build](android-build.md#review-and-closure-client-verification-october-7-2026). This source slice does not complete WH-084 or establish installed-device, signed association, real passkey/App Link or provider acceptance.
