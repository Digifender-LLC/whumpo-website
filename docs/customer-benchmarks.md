## Reproducible offline baseline

Run `node tools/benchmark.mjs` with Node 24 and the existing locked dependencies. It uses the connected site/app suites and several focused suites listed in [customer-benchmark.json](../tests/fixtures/customer-benchmark.json). There is **no live mode** or arbitrary script/model argument. The child environment reuses the [verification profile](verification.md) credential allowlist, empty temporary home, disabled dotenv/metrics and local-only D1/R2 bindings. Live-test flags are removed even when inherited from the calling shell. The model replies are scripted; application handlers, database transitions, publication reviews and the app suite's QuickJS execution are real local code.

| Fixture family | Synthetic user intent | Objective checks and their limits |
| --- | --- | --- |
| Bakery site | Welcome brief → private draft → reviewed publication → edit/restore/withdrawal | Valid saved config, private-before-confirmation, context exclusion, exact restore bytes and replay. Does not score visual appeal. |
| Precise edits | Change theme, headline, then opening hours | Exact unrequested-field preservation, ancestry and invalid-envelope rejection. Provider output is supplied, not generated by a real model. |
| Visitor application | Private member notebook and task-list workflow | Real bounded runtime, separate program/page reviews, form/backend input compatibility, owner/visitor boundaries and recovery. |
| Application build | Generate and test a note-saving function, then prepare approval | Expected state/result, failed-test denial, model assurance replaced by authoritative receipt, unknown test holds and concurrent replay. |
| Page design | Form for an approved `input.note` program | Correct source context, immutable program/page revisions, private receipt exclusion and stale/foreign denial. Fixture setup includes synthetic runtime results; distinguish it from actual QuickJS evidence above. |
| Conversation | Underspecified business tool and unavailable always-on FFmpeg workload | One scripted essential question, honest unsupported reply, no project/draft/activation and replay. Verifies handling, **not** whether a model independently chooses a good question/refusal. |
| Failure/recovery | Invalid proposal, lost provider reply, contention and lost admission acknowledgement | Failed-call cost retained, uncertain effects held, no duplicate dispatch, no customer standard-AI debit. Expected fault cases passing are not successful customer generations. |

Each family is one harness execution with dependent steps and sometimes several synthetic accounts. Do not count every assertion, turn, retry or acknowledgment as an independent quality sample. The script records a whole-family assertion result; a failed family leaves individual criteria unknown, rather than guessing which assertion failed. A retained transcript is not treated as proof of a useful result.

## Evidence and cost accounting

Every run writes an ignored private directory `.secrets/benchmarks/RUN_ID/` containing:

- `report.json`: suite/version/digest, Git commit and dirty flag, source digest, Node version, start/finish, per-family status, duration, checks and aggregate inference receipts.
- `sources.json`: exact SHA-256 manifest for source, harnesses/tools, complete current schema, compiler locks, controlled visitor assets, configuration and dependency lock. A before/after comparison rejects drift during the run. This fingerprints the checked source; it does not attest every installed package or the deployed service.
- Bounded per-family logs for failed-assertion diagnosis. They contain synthetic test details only; they are not published automatically or passed to a model.

`recordFixtureBenchmark` selects only inference metadata from each disposable database: role, state, model, cost basis, usage and reservation/observed estimates. It never selects customer identifiers, provider credentials, prompts, replies or generated source. Acknowledgments and all recorded failed/uncertain attempts stay in the report. Released reservations are identified as undispatched. Fixtures with independent transport counters cross-check the number of dispatched receipts; where a counter is absent, it is **null**, not evidence of exhaustive transport coverage. The runner records a failed/missing report rather than dropping that family from its denominator. A closed evidence validator also rejects incomplete fields, incorrect role/state totals, omitted uncertain/acknowledgment receipts, contradictory transport counts, fabricated real-model scores and shadow estimates presented as actual expense. Missing independent counters remain null. Compiler lock files participate in the before/after source fingerprint.

`totalTaskCost` requires six explicit categories: inference, acknowledgments, tools, safety, infrastructure and allocated platform/subscription expense. Every category must be verified, explicitly not used, or unknown. A single unknown produces `totalMicros: null`; known subtotals remain visible. Reject duplicate/missing categories, negative/fractional amounts and arithmetic overflow. Future real measurements must link “verified” inputs to trusted provider/operation records; the calculator does not authenticate an invoice.

For the present offline run, actual costs are unknown. Scripted token counts and the current `subscription-shadow` estimates remain labeled synthetic/shadow; neither is an OpenCode invoice or per-task subscription allocation. Tool/runtime counts are not dollar costs. No external scanner runs; that is not evidence that real safety processing will be free. Local runtime/DB resources and subscription allocation still need measurement. The report deliberately cannot populate an eligible candidate in [the routing planner](pricing-and-model-policy.md#route-selection-implementation--september-29-2026).

For real task comparisons, aggregate **all** attempts belonging to the fixture session—including failed generations, repairs, inspections, acknowledgments, tool calls and safety—then divide the complete cohort cost by validated successful outcomes. Report failures and unresolved cost coverage alongside that ratio. Do not compare only the cheapest successful calls, double-count acknowledgment inference, substitute reserved amounts for paid expense, or allocate unrelated customer work. Unknown output/reasoning/cache/tool pricing prevents a complete total. Standard customer charges remain zero independently of provider expense.

`harnessDurationMs` includes setup, fixture auth, database/runtime calls, assertions and teardown. It is **not** provider or customer latency. Real runs must time user admission → acknowledgment (if delivered) → usable result/review and each provider attempt separately. Count late/discarded acknowledgments in cost even if they were never shown. Include acknowledgment timing cases from `tests/ack-timing.mjs` when admitting a live route.

## Real-provider scoring protocol

The offline baseline always reports `realProviderSamples: 0`, no model-quality score and `rankingEligible: false`. Historical individual Muse checks remain dated evidence in their feature docs; this report does not relabel them a current comparative benchmark.

Before a real cohort, freeze:

1. Fixture version, exact synthetic brief/starting artifacts, selected model/provider/protocol, route/rate IDs, prompt/source digest, output/time/call ceilings, data classification and budget review. Pin model revisions when the provider exposes them; otherwise state that model-ID weights can change.
2. A reproducible initial state per fixture with no real users, secrets, private code, visitor content or provider tokens in prompts. Include varied landscaping, bakery, local-service, portfolio and bounded-app briefs; matched edits and deliberately ambiguous/unsupported requests. Keep forbidden-content tests benign and separate from real scanning acceptance.
3. The rubric below **before** responses are seen. Preserve all attempts and failures; never silently rerun until a desired result appears. Hold out a subset of briefs from prompt tuning. Models may assist draft review but cannot be the sole success adjudicator.
4. An exact budget/data review for any paid benchmark, new provider or route switch. Existing Muse subscription testing authorization is not permission for paid API fallback or account billing changes. Stop at limits or uncertain expenditure; no automatic alternate model.

| Measure | Required evidence | Scoring |
| --- | --- | --- |
| Validated useful draft | Server validation, intended artifact saved, exact private/review state, human usefulness review | Pass/fail/unknown; schema success alone is insufficient |
| Intent preservation | Diff against frozen baseline plus requested change checklist | All unrequested facts/structure preserved; inspect semantic equivalents manually |
| Application compatibility | Actual QuickJS input/state/result plus real form submission with matching keys/types | Passing synthetic execution and matching page contract; no fabricated activation |
| Clarification | Missing essential fact identified with one understandable question, no unnecessary setup | Human review; distinguish optional improvement from blocking uncertainty |
| Unsupported work | Accurate capability boundary and useful next step, no claimed deployment/purchase | Human review tied to authoritative resource receipts |
| Action honesty | Every claimed mutation/completion maps to current owned receipt or confirmed resource state | Contradictions fail; uncertain claims stay unknown, not assumed true from fluent prose |
| Recovery | Same request/review identity after lost acknowledgment; no duplicate model/provider/tool mutation | Durable record and exact before/after state, not a model's assurance |
| Latency/cost | Complete measured call/event timeline and reconciled expense categories | Show distribution, sample size and unknown coverage; no ranking with missing costs |

Report successful tasks/attempted tasks by family, failure reasons, independent brief count, model/version/prompt identity, total calls, p50/p95 with sample size, cost completeness and a binomial uncertainty interval for independently sampled binary outcomes. Very small samples are exploratory; p95 from one or two samples is a maximum, not reliable tail latency. Keep human aesthetic/usefulness judgments separate from deterministic assertions and record reviewer disagreement. Do not extrapolate these toy workloads to arbitrary applications.
