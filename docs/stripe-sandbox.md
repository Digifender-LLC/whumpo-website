## Authority and recovery contract

- Accept only test keys and objects; pin Stripe API `2026-10-28.endive` (see D17), USD, server catalogue amounts, quantity one, fixed Whumpo return URLs and the one approved Stripe hosted destination (`invoice.stripe.com` receipts). No user-selected customer, price, return URL or entitlement values.
- Create a durable owner/customer and checkout intent before provider writes. Retry the same intent only inside the bounded idempotency window. Uncertain older writes remain held for operator reconciliation. Leaving the payment form is not proof of an expired Checkout session.
- One pending checkout per owner. Existing nonterminal subscriptions block another purchase. Customer ownership, session metadata, saved price, subscription and invoice relationships must all agree. Never infer ownership from email.
- Signed webhook payloads only supply identifiers. Retrieve provider state before acting. Duplicate or reordered deliveries add no additional entitlement. Authenticated Refresh can reconcile a missed event from saved checkout/customer identities.
- Paid invoices create immutable coverage for the exact **invoice line service interval**, not the invoice's accounting period or the return date. Annual coverage ends at its recorded anniversary; it does not manufacture a thirteenth calendar-month grant. Calendar-month grants are removed. Standard AI stays unlimited fair use with zero customer credit debits; sandbox subscriptions mint no advanced credits or resource-wallet funds.
- Coverage selects the highest current paid interval; an account without one uses Explore. Invalid plan identities fail explicitly. Existing published sites remain online; new publication uses the current plan. A failed renewal cannot extend coverage. End-of-period cancellation preserves the already-paid interval. Invoice history and account/export access remain available.
- In-app billing management permits payment method updates, end-of-period cancellation and resume, and retry of a failed invoice only; invoice history links to Stripe's hosted receipts. Subscription changes, promotions, taxes, trials, automatic resource purchases and domain redemption are not activated. The hosted billing portal is retired.
- No raw webhook bodies, payment details, secret values or hosted session URLs in logs. Credentials stay in ignored operator files and platform Worker secrets, never customer-site Workers or model context.

## Operational setup and bounded recovery

Run `node tools/stripe-sandbox.mjs SECRET_DIRECTORY --configure` with ignored `stripe-test.key`. It verifies test mode, retains stable resource identities in `stripe-setup.json`, saves `stripe-webhook.key` privately and writes `stripe-catalog.json` (`{version:1,prices}`; a catalogue that still carries `portal` is accepted and the field ignored). Install the test key, signing secret and catalogue JSON as platform-only `STRIPE_TEST_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_SANDBOX_CATALOG`. The publishable key is not a secret: it is the public Worker var `STRIPE_TEST_PUBLISHABLE_KEY` in `wrangler.jsonc` (listed in `tools/secret-custody.mjs` `publicVariableNames`). The server exposes it through `GET /api/billing/subscription` only if it matches `pk_test_`; any other value disables in-app checkout. A lost setup reply older than 20 hours requires inspection; the tool does not blindly create replacement resources.

Checkout expires after one hour. A saved open session can be refreshed to establish expiry; resuming returns the session's client secret to its owner (never logged or stored). A saved session that is hosted-mode or will not return its secret is expired and the order closed, and the owner chooses a plan again with a new order; Stripe refuses to expire a session that has a payment in flight, so this cannot double-charge; an unknown session/customer write beyond its bounded replay window requires operator reconciliation. Customer history above ten subscriptions requires operator review. Refresh recovers current/latest invoice coverage; arbitrary historical backfill is not implemented. Invoice history shows the most recent 24 verified paid invoices; unpaid invoices are not listed.

The current schema uses invoice-only coverage. The October 1 pre-release reset removes the old credit checkout, calendar grants, unit balances and metered request path. There are no old-Worker compatibility readers. Resource-wallet/advanced credit fulfillment and full financial reconciliation remain open under WH-042/043; this is not real-money launch readiness.

## Custom payment flow — October 31, 2026

The owner asked to move every payment, subscription and Stripe surface off Stripe's prebuilt UI onto Stripe's custom payment flow (individual UI components). Decisions:

- **D14. Elements with the Checkout Sessions API** (`ui_mode: 'elements'`, `@stripe/react-stripe-js/checkout`), not the Subscriptions or Payment Intents route. Stripe recommends it for new integrations and it keeps the order state machine, one-pending-order rule, idempotency, webhook handling and invoice coverage unchanged. `startSubscription` now returns `{clientSecret,testMode:true}`; the page confirms with `checkout.confirm({redirect:'if_required'})` and `return_url` (`/workspace/?checkout=returned&session_id={CHECKOUT_SESSION_ID}`) is only the fallback for redirect-based methods and 3D Secure reloads. The server-side `redirect_on_completion` parameter was not sent: it could not be verified against a live sandbox response, and the client `redirect` option is documented and typed in `@stripe/stripe-js` 10.
- **D15. Three prebuilt surfaces replaced.** Hosted Checkout became Whumpo's checkout page; the homepage pricing table became Whumpo's plan cards; the billing portal became in-app routes (`GET /api/billing/payment-method`, `POST /api/billing/payment-method/setup|complete`, `POST /api/billing/subscription/cancel|resume|retry`). They have the same authority as the routes they replace (session, exact Origin, onboarding gate) and are registered in the boundary audit. They accept no customer, subscription or invoice id from the client; the one client-supplied value, the setup session id, is verified against the caller's customer and `metadata.owner` before anything is written. Updating the payment method is a `mode=setup` Checkout Session with the Payment Element; completion verifies ownership, then sets the customer and subscription default. Retry pays the latest open invoice of the caller's own subscription. The card brand and last four are read from Stripe on demand and stored nowhere. The portal configuration in Stripe was not deleted; `catalog.portal` is no longer required.
- **D16. Invoice and receipt links to `invoice.stripe.com` stay.** They are documents, not a payment flow.
- **D17. One API pin, `2026-10-28.endive`,** for every request, because the client SDK train (`@stripe/stripe-js` 10.x, `@stripe/react-stripe-js` 7.x) is tied to the API version and `ui_mode: 'elements'` needs it. Field reads were migrated to the shapes Stripe documents for that line: subscription `current_period_end` is read from the subscription item, an invoice's subscription from `parent.subscription_details.subscription`, paid state from `status === 'paid'` (no `paid` flag), a line's price from `pricing.price_details.price` (a price id, compared with the saved price id), and a line's subscription and proration from `parent.subscription_item_details`. The legacy locations remain readable, so a replayed older payload still verifies. **These shapes were verified against Stripe's documentation and typed fixtures only, not against real sandbox responses** (see Verification below). An existing webhook endpoint keeps its older, immutable `api_version`; events only supply identifiers and state is re-fetched at the pin, so the setup tool no longer insists on a match.
- **D18. Sandbox only.** `sk_test_`, `pk_test_`, no live key, no real money, no plan or price change. The browser refuses any key that is not `pk_test_` and the server never exposes one. Card entry is allowed only on a local dev host with Stripe's published test cards (`4242 4242 4242 4242`; 3D Secure `4000 0025 0000 3155`; decline `4000 0000 0000 9995`). Live acceptance on whumpo.com belongs to the owner.
- **D19. Stripe.js loads only where a card is collected.** The checkout component is a lazy chunk imported by the subscription panel, and `@stripe/stripe-js/pure` defers the script until `loadStripe`. The landing page loads no Stripe script (the live browser probe now fails on any Stripe request). Claims that existed only in the Stripe table were removed (seven-day trial, payment method required, Enterprise contact); copy follows the plan catalogue.

### Checkout gate (owner decision Q-007, D20-D23)

The owner chose to keep the live keys and block checkout for now. `catalog()` in `src/stripe-billing.ts` refuses unless `STRIPE_CHECKOUT_OPEN` is exactly `'true'`; the variable is unset in every Worker config, so every Stripe route (checkout, refresh, cancel, resume, payment-method read/setup/complete, retry, and the webhook) answers 503 with no Stripe call and no row written. The status route reports `enabled:false` and the UI says plainly that checkout is not open yet, with no buttons. Lock 2 is unchanged: only `sk_test_`/`pk_test_` keys are accepted and every object read must have `livemode===false`, so setting the variable still cannot charge a live key without a reviewed code change. No live-mode support was added. `STRIPE_SECRET_KEY` and `STRIPE_PUBLISHABLE_KEY` (live) are read by no code here. Tests turn the gate on explicitly (`STRIPE_CHECKOUT_OPEN:'true'` in their env) and `tests/subscriptions.mjs` proves the closed behavior for each route. If a separate gate PR lands first, merge it and keep one copy of the check.

### Content Security Policy

`frontend/public/_headers` adds only what Stripe.js needs: `script-src https://js.stripe.com https://*.js.stripe.com`, `frame-src https://js.stripe.com https://*.js.stripe.com https://hooks.stripe.com`, `connect-src https://api.stripe.com`. `style-src 'self'` is unchanged and `form-action 'self'` is unchanged: card confirmation runs inside Stripe's frames and cards use `redirect: 'if_required'`, so no form is posted from Whumpo's document to Stripe. Whether `style-src 'self'` and `img-src 'self' data:` are enough for the live Payment Element has **not** been proven in a real browser here (see below); if it is not, report the exact violated directive rather than loosening it blindly.
