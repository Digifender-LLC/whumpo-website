# Data protection and processing contract

**WH-116 / [#81](https://github.com/zemdregon/whumpo/issues/81), October 2, 2026 UTC; decision source review `bfe03a0`, with the WH-117A source extension below.** This decision extends the one [lifecycle catalogue](data-lifecycle.json). It records current controls and the required WH-117 implementation. It does not deploy encryption, activate a provider, approve retention windows or claim full backup restoration. All environments remain private testing environments.

## Decision

Retain managed D1/R2 protection, current identity/tenant checks, private object serving and narrowly selected processing. Strengthen the existing provider-credential vault with a current key-versioned format, controlled rotation and isolated restore checks. Do not add blanket application encryption to every content column or require customers to unlock a vault during ordinary work. For the current server-readable product, broad additional encryption would leave the authorized processing Worker able to read the same data while adding key-loss and recovery complexity. Restricting who can invoke those reads, minimizing what leaves the platform and preserving current authority are necessary controls regardless of encryption.

This is a concrete baseline decision for the admitted classes, not a promise that every future data type is suitable for it. The catalogue's planned classes cannot gain storage/processing simply by sharing a profile. Their implementing packets must register exact tables/objects, readers, provider eligibility, key requirements and acceptance before admission. Confidential beta inference remains unavailable under the [current privacy handoff](inference-privacy.md). Client-only/passkey encryption remains WH-118 feasibility; ordinary passkeys are authentication, not a content-key backup.

## Key custody and recovery

[Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/), checked October 2, provide encrypted bindings that authorized Worker code can access. Hiding the value in configuration/UI is not protection from that Worker or an operator able to replace its code. Keep encryption material out of D1, R2 object metadata, exported source, customer exports, model context and diagnostic logs. The existing vault shares its binding between customer-provider adapters; this decision selects no new Secrets Store, KMS or paid service.

Use **one current ciphertext format**, with a bounded explicit key ID and authenticated owner/provider/purpose/record context. Several admitted key versions during a reviewed rotation are instances of that current format, not old-format readers. Encrypt new writes only with the active key; decrypt only an explicitly retained matching key. Unknown IDs, malformed ciphertext, context substitution and authentication failure must stop the operation. Never try every key or fall back to plaintext. Obsolete test encodings may be reset after revocation/uncertain-operation custody is resolved.

Rotation must persist exact input identity and use compare-and-swap updates. An interrupted batch resumes from saved current rows; a concurrent token refresh/revocation cannot be overwritten by a stale re-encryption result. Retain a key until every admitted live ciphertext, OAuth/staging/revocation obligation and permitted backup/restore source using it is accounted for. Expiry of a local session, key label or job lease proves none of that. Do not delete a key needed to revoke a still-valid remote token. Bind key lookup to the current invocation/configuration; a globally cached client must not silently retain a retired secret after a binding change.

Account recovery under WH-115 restores account authority only. It cannot reconstruct a lost platform encryption key, lost client key, erased object or expired backup. For readable server content, recovery can expose only the data still present and permitted by current ownership/policy. For encrypted credentials, a missing key means a visible unavailable/reconciliation state; reconnecting is a separate approved action and does not establish that an old remote token was revoked.

## Backup, deletion and current restore

[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/), checked October 2, documents automatic history and up to 30 days on Workers Paid (seven on Free), with no additional Time Travel charge. This is a documented service capability, not a verified bookmark inventory or successful Whumpo restoration. D1 history does not contain Worker secret values, private R2 bodies, external-provider state or independent deletion suppressions. No matching point-in-time snapshot across those systems is assumed.

Each admitted restore must identify the exact current schema/compiler/cipher format, retained key IDs and required independent revocation/deletion evidence **before enabling serving or dispatch**. Reconcile removed accounts, credential/session epochs, withdrawn publications, preservation obligations, consumed invites, cancelled jobs and external uncertain results. Metadata or ciphertext that can be read is not thereby current authority. Missing keys, suppressions or external reconciliation keep affected operations unavailable. Do not restore old application binaries, data encodings or a legacy authentication policy.

The current platform does not have complete account export/closure or an independently operated restore-suppression service. WH-117 must demonstrate its bounded key/data checks on synthetic isolated fixtures and refuse incomplete evidence. WH-008/018/019/059 retain whole-platform restoration, deletion execution and operator acceptance. This handoff does not turn a local test into those completed capabilities.

Retention proposals LC-01–09 remain proposals. Deleting live content/key material does not erase provider history, public downloads, customer backups or provider training use. Export remains a class-specific allowlist; encrypted credentials are excluded as well as plaintext secrets. Future export packages need minimized scoped data and expiring authenticated access under their own acceptance.

### Existing controls to retain

Managed storage encryption is sufficient as the current infrastructure layer for server-readable drafts, conversations, ordinary profile/preferences, owned application data and bounded operational metadata when combined with the declared readers. Additional blanket encryption would not block the authorized processor or its selected model; it is not selected without a more specific exposure/benefit. Public approved artifacts are intentionally readable and do not need a misleading private-content encryption promise. Public-key/verifier records use authentication-specific formats; re-encrypting them is not a substitute for epoch/replay checks. Credentials justify application encryption because a database-only disclosure should not immediately supply reusable provider access.

Provider-managed storage remains within the existing configured products. Extra ciphertext bytes, rotation writes/reads and CPU must be measured in WH-117 and recorded in resource accounting; current account headroom is not known here. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) and [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) must be refreshed before estimating those changes. R2 SSE-C is not selected: it introduces a separate key-loss dependency without removing authorized service access ([R2 SSE-C](https://developers.cloudflare.com/r2/examples/ssec/), checked October 2). No new paid tier, storage service, key service, provider or customer hardware is requested.
